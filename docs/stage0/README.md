## 3. Приёмочные проверки AT-G-01…AT-G-05 на данный момент

## 4. Решения владельца

Все три решения приняты владельцем. Места в `docs/design/`, которые от них зависят, помечены «Решение владельца (OD-n)».

### OD-1. Структурированные вопросы Codex

Факт: `item/tool/requestUserInput` приходит только на экспериментальной поверхности: `initialize.capabilities.experimentalApi` вместе с `turn/start.collaborationMode {mode: "plan"}` либо фича `default_mode_request_user_input` в статусе under development; типы `ToolRequestUserInput*` помечены EXPERIMENTAL. На стабильной поверхности модель отвечает «request_user_input ... unavailable in Default mode», а `collaborationMode` без opt-in отклоняется (CX §3, §7 р. 1; `question.jsonl`, `question_default_mode.jsonl`). ТЗ §10.4: экспериментальные части изолировать и не включать без необходимости.

| Пункт | Содержание |
| --- | --- |
| Решение | Разрешить экспериментальную поверхность изолированно. Адаптер Codex включает `experimentalApi` в `initialize.capabilities` и фичу `default_mode_request_user_input` (при запуске `--enable default_mode_request_user_input`); вопросы работают в обычном режиме и в plan mode. Включение только внутри адаптера Codex, версия CLI закреплена, при каждом обновлении CLI контрактные тесты по сгенерированной схеме и образцам |
| Матрица | Структурированные вопросы Codex: PASS на 0.164.0 (экспериментальная поверхность, одобрено владельцем); AT-G-04 этим не блокируется. Тем же включением доступны `thread/backgroundTerminals/list` и `clean` (решение контролёра в §6) |
| Остаётся риском | фича в разработке: CLI предупреждает «Under-development features enabled»; смысл `isBlocking: false` не документирован (ход при этом ждал ответа с флагом `waitingOnUserInput`); экспериментальные типы могут меняться в любой версии |
| Отклонено | не включать экспериментальное: вопросы Codex BLOCKED, AT-G-04 BLOCKED |

### OD-2. Прерывание Claude Code

Факт: документированный SIGINT останавливает ход за 35 мс (`result` с `subtype: error_during_execution`, `terminal_reason: aborted_tools`), убивает дерево Bash, но процесс CLI затем выходит с кодом 0. Прерывание с сохранением процесса работает только через `control_request` `interrupt` с `cancel_queued: true`, форма которого выведена из упоминаний в документации (UNDOCUMENTED) (CC §3.1, §7 р. 1; `interrupt.jsonl`).

| Пункт | Содержание |
| --- | --- |
| Решение | Документированный SIGINT и `--resume`: прерывание завершает ход и процесс CLI, исполнение переходит в `stopped(user_stop)`, продолжение = явный resume, то есть новое исполнение. Это согласуется с §7.3: после остановки пользователем очередь и так на паузе. Недокументированный `control_request` `interrupt` не используется |
| Матрица | Прерывание Claude Code: PASS на 2.1.310 (решение контролёра в §6): запрос = отправленный сигнал, подтверждение = `result` с `terminal_reason: aborted_tools`, фактическая остановка = выход процесса. Задержка продолжения (около 1 с старта нового процесса) относится к resume, а не к прерыванию. AT-G-02 этим не блокируется |
| Отклонено | `control_request` `interrupt`: форма не документирована, §10.5 запрещает опираться на недокументированный управляющий протокол |

### OD-3. Конфигурация владельца в сессиях хаба

Факт: пробы запускали оба CLI изолированно: Claude Code с `--setting-sources project`, `--strict-mcp-config` и белым списком окружения (CC §2.1, §2.2); Codex с переопределениями `-c`, `--disable`, guard-правилами и проверкой `config/read` до первого хода (CX §2.1).

| Пункт | Содержание |
| --- | --- |
| Решение | Сессии хаба наследуют собственную конфигурацию агента владельца: плагины, MCP-серверы, CLAUDE.md/AGENTS.md, правила, режим разрешений и песочницы, как если бы владелец запустил CLI сам (ТЗ §15 «штатные локальные настройки агента»). Хаб показывает действующий режим разрешений каждой сессии и позволяет владельцу переопределить его на сессию (ТЗ §11: более широкая автоматизация есть явная настройка с видимым текущим режимом). Воркер всегда сохраняет исключения: маршрут разрешений (наш prompt tool и маршрутизация одобрений) остаётся подключённым, входящие межсессионные сообщения Claude Code отклоняются (решение контролёра в §6) |
| Запуск CLI | Флаги изоляции проб не передаются: у Claude Code `--setting-sources project` и `--strict-mcp-config`, у Codex переопределения `-c`, `--disable` и guard-правила. Передаются всегда: Claude Code `--permission-prompt-tool` с нашим MCP-сервером в `--mcp-config` и настройки отказа межсессионных сообщений; Codex `approvalsReviewer: "user"` в `thread/start`, как в пробах. Переопределение режима на сессию: Claude Code `--permission-mode`, Codex `approvalPolicy` и `sandbox` в `thread/start` |
| Действующий режим | Claude Code: `system/init.permissionMode` (приходит с первым вводом); Codex: `approvalPolicy` и `sandbox` в ответе `thread/start` |
| Следствия | С режимом владельца запросов разрешений может не быть (у владельца в Codex `approval_policy = "never"`, `sandbox_mode = "danger-full-access"`); действия, разрешённые настройками или правилами владельца без запроса, показываются как `auto_approved_by_cli_policy`. MCP-серверы, хуки, плагины и инструкции владельца доступны агенту хаба. Нативная история пишется в каталоги владельца и видна в его CLI (Codex с `source: "vscode"`). Второй вход не нужен (AT-G-05) |
| Матрица | Статусы не меняются, но сняты в изоляции: на этапе 2 smoke-проверки повторяются с унаследованной конфигурацией, цикл разрешений и вопросов с режимом сессии, переопределённым на запрос подтверждений |
| Отклонено | изоляция, как в пробах; отдельный каталог конфигурации (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) со своим входом |

## 5. Выводы для воркера

Выводы, верные для обоих CLI на закреплённых версиях. Отображение на автоматы: [`docs/design/README.md`](../design/README.md), «Контракт адаптера».

| # | Вывод | Основание |
| --- | --- | --- |
| 1 | Очередь FIFO держит воркер, следующий ввод пишется только после сигнала конца хода (Claude Code: `result`; Codex: `turn/completed` и `thread/status/changed` → `idle`). Оба CLI вливают ввод, записанный во время хода, в текущий ход: Claude Code при вызовах инструментов (`priority: next` по умолчанию), Codex всегда (`turn/start` при активном ходе). Вмешательство отправляется только явно: `priority` или `turn/steer`. Codex дополнительно сверяет `turn.id` ответа с известными ходами: совпадение с активным ходом означает, что обычная отправка стала вмешательством | CC §3.2, §4.3, §7 р. 3; CX §4.3, §7 р. 4 |
| 2 | Процессы инструментов уходят из группы процессов CLI (собственные группы и сессии) и переживают SIGKILL CLI или Node-обёртки. `killpg` и PID недостаточно: нужна cgroup v2 на исполнение (решение контролёра в §6) | CC §5, §7 р. 2; CX §6, §7 р. 3, р. 11 |
| 3 | Ни одна нативная история не гарантирует полноту: `not_accepted_proven` недостижим, сверка после сбоя даёт только положительное доказательство (Claude Code: транскрипт внутреннего формата; Codex: `thread/items/list` по `clientId`). Повтор нашего ID ни один CLI надёжно не дедуплицирует: Claude Code в живом процессе молча отбрасывает повтор UUID, Codex создаёт новый ход. Автоматического повтора нет | CC §4.4, §6; CX §4.4, §7 р. 5 |
| 4 | Отказ API повторяется минутами без итога хода: Claude Code до 10 повторов, больше 3 мин (настраивается `CLAUDE_CODE_MAX_RETRIES`), Codex без предела (`unbounded_connection_retries`). Нужна видимая фаза «повтор запроса к модели» из `system/api_retry` и `error {willRetry: true}` и предложение прерывания по порогу, без автоматических действий | CC §3.1, §7 р. 8; CX §3, §7 р. 6 |

Codex: ID выдаёт сервер (`thread.id`), resume = `thread/resume` в новом процессе, прерванный ход хранится как `interrupted`. Оба возобновляются после SIGKILL | CC §3.1, §5; CX §3, §6 |
| 6 | Запросы разрешений CLI не истекают (Claude Code документировано; у Codex в запросе нет поля срока) и закрываются только очисткой хода: Claude Code MCP `notifications/cancelled`, Codex `serverRequest/resolved`, который приходит и после нашего ответа. Поздний ответ оба CLI молча игнорируют, поэтому «решение не применено» устанавливает адаптер по наблюдённому закрытию, а не по отказу CLI | CC §4.2; CX §4.2, §7 р. 9 |
| 7 | «Остановлено» относится к ходу. Прерывание Claude Code (SIGINT, OD-2) убивает дерево Bash и завершает процесс CLI. У Codex запущенная команда продолжает работать, её элемент завершается поздним фактом; она показывается как фоновая работа и останавливается `thread/backgroundTerminals/clean` или `force_stop` cgroup исполнения (решение контролёра в §6) | CC §3.1, §5; CX §3, §6 |

Codex: ответ `initialize`, затем ответ `thread/start` | CC §3.1 (диагностика), `diagnostics.jsonl`; CX §2, §6 |
| 9 | Закрепление версии и контрактные тесты: версия Claude Code меняется часто, форма аргументов prompt tool не документирована; `codex app-server` целиком experimental, схема генерируется из CLI. Воркер запускает закреплённый бинарник, отключает автообновление, сверяет версию и пропускает неизвестные события с диагностикой | CC §7 р. 7, р. 9, р. 11; CX §2, §7 р. 2 |
| 10 | Фоновые работы: у Claude Code наблюдаемы документированно (`system/background_tasks_changed` с полным списком `tasks`, только фоновые задачи Bash). У Codex на стабильной поверхности их не видно, тред при живой команде переходит в `idle`; список даёт экспериментальный `thread/backgroundTerminals/list`, включённый решением OD-1. Учёт обоих CLI не покрывает процессы, которые команда отсоединила сама, поэтому отсутствие работы дополнительно проверяется по cgroup исполнения | CC §3.2, `background.jsonl`; CX §5, §7 р. 3, `background.jsonl` |

Выводы OpenCode 2.1.4 (OC = [opencode.md](opencode.md)) другие в трёх местах. Интерфейс это локальный сервер с HTTP и SSE, а не поток в stdio. Replay нет, поэтому всё, что потеряно в разрыве, читается из проекций одним путём сверки. База эксклюзивна, поэтому у canterlot своя база и один вход в неё. Остальное совпадает: ввод только после конца хода, положительное доказательство приёма, полноты истории нет, инструменты в своих группах процессов. Только на настоящей модели можно проверить реальный поток, тело отказа Go и `Retry-After`: это чек-лист смоука, а не код.

## 6. Решения контролёра

Приняты без отдельного решения владельца:

- Сверка Claude Code после сбоя может разбирать нативный транскрипт: разбор закреплён за версией CLI, принимается только положительное доказательство, для неизвестных версий CLI разбор отключён (ТЗ §7.2).
- Воркер по умолчанию отключает входящие межсессионные сообщения Claude Code (`crossSessionInbound: refuse` и запрет `SendMessage`/`ListAgents`); проверка на этапе 2.
- Удержание процессов: cgroup v2 на исполнение (systemd user scope); ADR на этапе 1.
- Статус прерывания Codex: PASS на 0.164.0. `turn/interrupt` даёт запрос, подтверждение и конец хода; команды, пережившие ход, показываются как фоновая работа и останавливаются через `thread/backgroundTerminals/clean` (экспериментальный, включён в рамках OD-1) или `force_stop` cgroup исполнения. Точная политика для команд, выполнявшихся в прерванном ходе, является задачей этапа 2 с отдельным тестом.
- Статус прерывания Claude Code: PASS при OD-2. SIGINT различает запрос (сигнал отправлен), подтверждение (`result` с `terminal_reason: aborted_tools`) и фактическую остановку (выход процесса), как требует §10.2; задержка продолжения относится к resume, а не к прерыванию.
- Возможный запуск хода без ввода пользователя после того, как фоновая задача Claude Code завершилась и CLI уведомил модель: остаётся недоказанным риском, проверка на этапе 2.
