## 2. Матрица возможностей

Статусы перенесены из отчётов без изменений (CC §3, CX §3, §5). По §25.9 описанное ограничение не является PASS: PARTIAL означает, что обязательство не выполнено на документированной (Claude Code) или стабильной (Codex) поверхности интерфейса.

## 4. Решения владельца

Статус всех трёх: **ожидает ответа**. После ответа здесь фиксируется выбранный вариант, затем обновляются матрица (§2), AT-G (§3) и места в `docs/design/` с пометкой «Ожидает решения владельца (OD-n)».

### OD-1. Структурированные вопросы Codex

Факт: `item/tool/requestUserInput` приходит только на экспериментальной поверхности: `initialize.capabilities.experimentalApi` вместе с `turn/start.collaborationMode {mode: "plan"}` либо фича `default_mode_request_user_input` в статусе under development; типы `ToolRequestUserInput*` помечены EXPERIMENTAL. На стабильной поверхности модель отвечает «request_user_input ... unavailable in Default mode», а `collaborationMode` без opt-in отклоняется (CX §3, §7 р. 1; `question.jsonl`, `question_default_mode.jsonl`). ТЗ §10.4: экспериментальные части изолировать и не включать без необходимости.

| Вариант | Последствие для матрицы |
| --- | --- |
| а) Разрешить изолированное включение экспериментальной поверхности только в адаптере Codex | Вопросы Codex: PASS на экспериментальной поверхности при закреплённой версии и контрактном тесте схемы; AT-G-04 может закрыться. Два пути: plan mode меняет поведение агента (свои инструкции режима, агент планирует, а не исполняет), вопросы доступны только в нём; фича `default_mode_request_user_input` оставляет обычный режим, но находится в разработке, а флаг `isBlocking: false` в ней не документирован |
| б) Не включать | Вопросы Codex: BLOCKED, адаптер объявляет `structured_questions: unavailable` с причиной; AT-G-04 BLOCKED; эксплуатационный релиз не принимается без изменения объёма (§10.2, §19) |

### OD-2. Прерывание Claude Code

Факт: документированный SIGINT останавливает ход за 35 мс (`result` с `subtype: error_during_execution`, `terminal_reason: aborted_tools`), убивает дерево Bash, но процесс CLI затем выходит с кодом 0. Прерывание с сохранением процесса работает только через `control_request` `interrupt` с `cancel_queued: true`, форма которого выведена из упоминаний в документации (UNDOCUMENTED): квитанция `control_response` за 8 мс, `result` за 29 мс, процесс жив, следующий ввод исполнен (CC §3.1, §7 р. 1; `interrupt.jsonl`).

| Вариант | Последствие для матрицы |
| --- | --- |
| а) Документированный SIGINT | Каждое «Стоп» завершает исполнение; следующий ввод требует resume (новый процесс `--resume`, около 1 с старта); отдельного подтверждения прерывания нет, есть конец хода и выход процесса. Прерывание: PASS на документированной поверхности при принятой владельцем семантике «остановка хода завершает исполнение» (изменение фиксируется решением, §10.2); AT-G-02 закрывается без недокументированных механизмов |
| б) `control_request` `interrupt` | Исполнение и процесс сохраняются, есть квитанция и отмена очереди CLI. Прерывание: PASS только при контрактном тесте формы на каждую закреплённую версию и проверке capability `interrupt_receipt_v1`; смена формы в новой версии сломает прерывание без документированного сигнала. §10.5 запрещает опираться на недокументированный управляющий протокол из другой обёртки; здесь форма не из обёртки, но остаётся недокументированной |
| Без решения | Прерывание PARTIAL, AT-G-02 BLOCKED |

### OD-3. Конфигурация владельца в сессиях хаба

Факт: пробы запускали оба CLI изолированно: Claude Code с `--setting-sources project`, `--strict-mcp-config` и белым списком окружения (CC §2.1, §2.2); Codex с переопределениями `-c`, `--disable`, guard-правилами и проверкой `config/read` до первого хода (CX §2.1). Изоляция документированными средствами неполная. Claude Code: Bash подгружает снимок `~/.bashrc`, транскрипты пишутся в `~/.claude/projects`, открыт входящий межсессионный сокет (CC §2.2, §7 р. 5, р. 6). Codex: глобальный `~/.codex/AGENTS.md` грузится всегда, пользовательские `.rules` с `allow` исполняют команды вне песочницы без запроса (перекрыто guard-правилами только в доверенном проекте), `-c` не адресует пути с точками, треды видны в истории Codex владельца с `source: "vscode"` (CX §2.1, §7 р. 7, р. 10).

| Вариант | Последствие для матрицы |
| --- | --- |
| а) Наследовать конфигурацию владельца: плагины, MCP-серверы, CLAUDE.md/AGENTS.md, правила, режим разрешений и песочницы | Матрица снята в изоляции и требует повторной проверки разрешений, вопросов и инструментов. Режим владельца в Codex (`approval_policy = "never"`, `sandbox_mode = "danger-full-access"`) убирает запросы разрешений; MCP-серверы владельца (в том числе физический KVM), хуки и плагины доступны агенту хаба; стартовый режим §11 «запрашивать подтверждения там, где их требует харнесс» становится настройкой владельца |
| б) Изоляция, как в пробах | Матрица действует как есть. Остаточные связи из факта выше остаются; межсессионный сокет закрывается флагами воркера (решение контролёра в §6), пользовательские правила Codex перекрываются guard-правилами; нативная история пишется в домашний каталог владельца |
| в) Отдельный каталог конфигурации (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) со своим входом | Настройки и история владельца не затрагиваются; нужен второй локальный вход в каждый CLI (для Codex `account/login/start` с device code), AT-G-05 должна объяснять «нужен вход» для каталога воркера до задачи; матрицу нужно перепроверить в новом каталоге |

## 5. Выводы для воркера

Выводы, верные для обоих CLI на закреплённых версиях. Отображение на автоматы: [`docs/design/README.md`](../design/README.md), «Контракт адаптера».

| # | Вывод | Основание |
| --- | --- | --- |
| 1 | Очередь FIFO держит воркер, следующий ввод пишется только после сигнала конца хода (Claude Code: `result`; Codex: `turn/completed` и `thread/status/changed` → `idle`). Оба CLI вливают ввод, записанный во время хода, в текущий ход: Claude Code при вызовах инструментов (`priority: next` по умолчанию), Codex всегда (`turn/start` при активном ходе). Вмешательство отправляется только явно: `priority` или `turn/steer`. Codex дополнительно сверяет `turn.id` ответа с известными ходами: совпадение с активным ходом означает, что обычная отправка стала вмешательством | CC §3.2, §4.3, §7 р. 3; CX §4.3, §7 р. 4 |
| 2 | Процессы инструментов уходят из группы процессов CLI (собственные группы и сессии) и переживают SIGKILL CLI или Node-обёртки. `killpg` и PID недостаточно: нужна cgroup v2 на исполнение (решение контролёра в §6) | CC §5, §7 р. 2; CX §6, §7 р. 3, р. 11 |
| 3 | Ни одна нативная история не гарантирует полноту: `not_accepted_proven` недостижим, сверка после сбоя даёт только положительное доказательство (Claude Code: транскрипт внутреннего формата; Codex: `thread/items/list` по `clientId`). Повтор нашего ID ни один CLI надёжно не дедуплицирует: Claude Code в живом процессе молча отбрасывает повтор UUID, Codex создаёт новый ход. Автоматического повтора нет | CC §4.4, §6; CX §4.4, §7 р. 5 |
| 4 | Отказ API повторяется минутами без итога хода: Claude Code до 10 повторов, больше 3 мин (настраивается `CLAUDE_CODE_MAX_RETRIES`), Codex без предела (`unbounded_connection_retries`). Нужна видимая фаза «повтор запроса к модели» из `system/api_retry` и `error {willRetry: true}` и предложение прерывания по порогу, без автоматических действий | CC §3.1, §7 р. 8; CX §3, §7 р. 6 |
| 5 | Native ID и resume. Claude Code: ID задаёт воркер (`--session-id`), resume = новый процесс с `--resume`, прерванный ход не продолжается. Codex: ID выдаёт сервер (`thread.id`), resume = `thread/resume` в новом процессе, прерванный ход хранится как `interrupted`. Оба возобновляются после SIGKILL | CC §3.1, §5; CX §3, §6 |
| 6 | Запросы разрешений CLI не истекают (Claude Code документировано; у Codex в запросе нет поля срока) и закрываются только очисткой хода: Claude Code MCP `notifications/cancelled`, Codex `serverRequest/resolved`, который приходит и после нашего ответа. Поздний ответ оба CLI молча игнорируют, поэтому «решение не применено» устанавливает адаптер по наблюдённому закрытию, а не по отказу CLI | CC §4.2; CX §4.2, §7 р. 9 |
| 7 | «Остановлено» относится к ходу. Прерывание Claude Code убивает дерево Bash; у Codex запущенная команда продолжает работать, её элемент завершается поздним фактом. Полная остановка = остановка исполнения через cgroup | CC §3.1, §5; CX §3, §6 |
| 8 | Готовность при старте. Claude Code до первого ввода кадров не выдаёт (`system/init` приходит только с ним); признак старта: MCP-сервер разрешений получил от CLI `initialize` и `tools/list`. Codex: ответ `initialize`, затем ответ `thread/start` | CC §3.1 (диагностика), `diagnostics.jsonl`; CX §2, §6 |
| 9 | Закрепление версии и контрактные тесты: версия Claude Code меняется часто, форма аргументов prompt tool не документирована; `codex app-server` целиком experimental, схема генерируется из CLI. Воркер запускает закреплённый бинарник, отключает автообновление, сверяет версию и пропускает неизвестные события с диагностикой | CC §7 р. 7, р. 9, р. 11; CX §2, §7 р. 2 |
| 10 | Фоновые работы наблюдаемы только у Claude Code (`system/background_tasks_changed` с полным списком `tasks`, только фоновые задачи Bash). У Codex на стабильной поверхности их не видно, тред при живой команде переходит в `idle`; освобождение рабочего каталога для Codex возможно только остановкой исполнения | CC §3.2, `background.jsonl`; CX §5, §7 р. 3, `background.jsonl` |

## 6. Решения контролёра

Приняты без отдельного решения владельца:

- Сверка Claude Code после сбоя может разбирать нативный транскрипт: разбор закреплён за версией CLI, принимается только положительное доказательство, для неизвестных версий CLI разбор отключён (ТЗ §7.2).
- Воркер по умолчанию отключает входящие межсессионные сообщения Claude Code (`crossSessionInbound: refuse` и запрет `SendMessage`/`ListAgents`); проверка на этапе 2.
- Удержание процессов: cgroup v2 на исполнение (systemd user scope); ADR на этапе 1.

## 7. Недоказанные гарантии и непроверенное

| CLI | Что не доказано | Основание |
| --- | --- | --- |
| Claude Code | прерывание без выхода процесса возможно только в недокументированной форме (OD-2) | CC §3.1 |
| Claude Code | самый ранний признак приёма (`command_lifecycle queued`) не документирован: окно неопределённости 1,4–2,5 с у свободного агента | CC §4.1 |
