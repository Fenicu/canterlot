# Автоматы состояний и протоколы восстановления

Поведенческая спецификация, которую ТЗ v1.0 требует до вертикального среза (§26) и как поставку репозитория (§21 п. 4): автоматы состояний, правила идемпотентности и протоколы восстановления. Здесь нет SQL-схемы, структуры модулей и `.proto`: только поведение и общий словарь. `§N` ссылается на раздел ТЗ, `AT-*` на приёмочную проверку §25.

## Документы

| Файл | Содержание |
| --- | --- |
| [delivery.md](delivery.md) | Идемпотентность, доставка пользовательского ввода, очередь разговора (паузы и удержания), прерывание, запросы разрешений и вопросы |
| [execution.md](execution.md) | Жизненный цикл исполнения, фаза агента, связь с машиной, владение рабочим каталогом, принадлежность процессов и потеря сопровождения, работа без хаба и заполнение журнала машины |
| [streams.md](streams.md) | Сеанс потоков воркер-хаб, исходящие команды хаба, журналы машины и durable ACK, подписки браузера, текстовые блоки, публикация вложений |
| [recovery.md](recovery.md) | Протоколы по шагам: restart хаба, restart управляющей службы, смерть сопровождения, перезагрузка машины, reconnect с потерянными ACK, удаление разговора, restore с новым поколением |

## Соглашения

- Имена состояний, событий, команд и причин: английские идентификаторы `snake_case`, рядом русское описание. Код, `.proto` и UI-строки берут имена отсюда.
- **Предложение**: конкретный выбор там, где ТЗ оставляет механизм исполнителю; рядом одна строка обоснования. Изменение оформляется кратким ADR (§1.1).
- **Зависит от этапа 0**: поведение конкретного CLI, которое подтверждают прототипы (`docs/stage0/`). До их результатов адаптер моделируется абстрактно (см. «Контракт адаптера»).
- Таблица переходов: `из | событие | условие | действие | в`. Места хранения в столбце «действие»:

| Метка | Где | Граница надёжности |
| --- | --- | --- |
| `LS` | локальное хранилище браузера (например, IndexedDB) | только устройство; не подтверждение сервера |
| `PG-tx` | одна транзакция PostgreSQL хаба | центральный commit |
| `CJ` | журнал управляющей службы воркера (один на машину) | fsync на машине, контрольные суммы |
| `SJ` | журнал сопровождения (один на исполнение) | fsync на машине, контрольные суммы |
| `BLOB` | blob storage хаба | durable-публикация по неизменяемому ID |
| `MF` | внешний контрольный манифест хаба (§18.1) | вне восстанавливаемого набора PG/blobs |

- **Поздний факт**: событие или статус, относящийся к уже терминальному объекту или старому поколению. Общее правило (§9.1): поздний факт дополняет историю своего объекта, но не возвращает его в нетерминальное состояние и не меняет более новое поколение.
- Сеть и CLI не вызываются под открытой транзакцией; команда уходит воркеру только после commit своего `PG-tx` (§14).
- Служебные факты (доступность машины, heartbeat, счётчики) хранятся отдельно от пользовательского ввода и никогда не становятся элементами ответа (§5).

## Идентичности и поколения

§5 требует различать идентичность инсталляции, поколение восстановления, поколение исполнения и подключение. Ни одна из величин не выводится из PID, hostname или текущего соединения (§14).

| Величина | Что идентифицирует | Кто создаёт | Источник истины | Меняется при | Не меняется при |
| --- | --- | --- | --- | --- | --- |
| `installation_id` | инсталляцию хаба | административная инициализация | `MF`; копия в PG сверяется при старте | никогда; новая инсталляция = новый ID | restart, restore |
| `restore_generation` | эпоху данных хаба | процедура restore, случайное значение (§18.1 п. 1) | `MF`; копия в PG; воркер хранит последнее согласованное | только restore по §18.1 | restart хаба (AT-C-17), reconnect |
| `machine_id` | установку воркера | хаб при регистрации (F-01) | PG + локальный credential воркера | явная локальная перерегистрация (§4.3) | restart, reboot, reconnect |
| `journal_id` | экземпляр журнала `CJ` или `SJ` | воркер или сопровождение при создании журнала, случайный | заголовок журнала | пересоздание локального состояния | restart, reboot |
| `connection_id` | текущее подключение воркера (пара потоков) | **Предложение**: воркер на каждую попытку подключения; оба потока несут один ID, потому что §8.6 п. 2 требует его в первом сообщении каждого потока | хаб (память, диагностика) | каждое новое подключение канала управления | исполнение, поколения, переоткрытие одного канала данных |
| `boot_id` | загрузку ОС машины | ядро Linux | ОС | каждая загрузка | |
| `conversation_id` | разговор | хаб | PG; после удаления бессрочный tombstone (§14.1) | никогда | |
| `execution_id`, `execution_generation` | исполнение и его место в разговоре | хаб в PG-tx старта или resume | PG; копия в записи принадлежности на машине | новое исполнение | reconnect, restart хаба или службы |
| `input_id`, `input_seq` | пользовательский ввод и его место в FIFO | хаб при commit | PG | никогда | |
| `idempotency_key` | изменяющую операцию клиента | клиент до первой отправки | PG, уникален в области владельца | никогда; повтор той же операции идёт с тем же ключом | |
| `command_id`, `dispatch_attempt` | команду хаб→воркер и попытку её выдачи | хаб в PG-tx операции; попытка растёт при повторной выдаче после отзыва | PG; квитанции в `CJ`/`SJ` | никогда; попытка только растёт | |
| `request_id` | запрос разрешения или вопрос | сопровождение, детерминированно из `execution_id` и нативного ID запроса | `SJ`, затем PG | никогда, в т.ч. при replay | |
| `block_id`, `revision` | элемент ответа и его версию | сопровождение | `SJ`, затем PG | ревизия только растёт | |
| ключ события `(journal_id, journal_seq)` | факт с машины | запись в журнал | журнал машины; уникален в PG | никогда, в т.ч. при replay (§8.4) | |
| `scope_seq` | порядок фактов в области подписки браузера | хаб в PG-tx факта | PG | только растёт | |
| `attachment_id`, `blob_id`, `checksum` | вложение и неизменяемое содержимое | хаб | PG (метаданные), `BLOB` (содержимое) | никогда | |
| `native_conversation_id` | разговор во внешнем CLI | CLI | адаптер, затем `SJ` и PG | новый нативный разговор | resume |

**Предложение** по `execution_generation`: целое число, монотонное в пределах разговора; команды адресуются парой `execution_id` + `execution_generation`; воркер отклоняет поколение ниже максимального известного ему для разговора. Число нужно для простого сравнения «старое/новое» на машине, UUID для адресации. После restore счётчик поднимается выше максимума, сообщённого воркерами (recovery.md, R7).

## Источники истины

| Факт | Источник истины | Кто отражает |
| --- | --- | --- |
| Ввод принят хабом, порядок FIFO, паузы очереди, решения пользователя, tombstone | PG | браузер, воркер (через команды) |
| Команда записана на машине, начиналась ли передача агенту | квитанции `CJ`/`SJ` | PG (последний полученный статус) |
| Жив ли процесс, чья группа ресурсов, кто владеет рабочим каталогом | воркер: запись принадлежности и `CJ` | PG (последнее наблюдение и его давность) |
| Агент принял ввод или применил решение | доказательство адаптера (зависит от этапа 0) | `SJ` → PG |
| Фаза агента, фоновые работы | факты адаптера | `SJ` → PG → браузер |
| Поколение восстановления | `MF` | PG, воркер |
| Содержимое вложения | `BLOB` после durable-публикации; готовность по PG | |
| Доступность машины | хаб по прикладному heartbeat на монотонных часах хаба | браузер |
| Черновик | `LS` устройства | |

## Квитанции и их смысл

| Квитанция | Кто выдаёт | Что гарантирует | Отметка в UI |
| --- | --- | --- | --- |
| `draft_saved` | браузер | запись в `LS` | черновик / «Сохраняется» |
| `api_committed` (успешный ответ изменяющей операции) | хаб | завершённый `PG-tx`: объект, команда и событие для подписчиков (§7.1) | «В очереди», «решение сохранено хабом» |
| `command_stored` | воркер | команда записана в `CJ` с fsync, дедупликация по `command_id` | «На машине» |
| `transmission_started` | сопровождение | намерение передачи записано в `SJ` с fsync до первого байта во внешний процесс | «Передаётся агенту» |
| `agent_accepted` | адаптер через сопровождение | положительное доказательство приёма | «Принято агентом», «агент применил решение» |
| `event_range_ack(journal_id, up_to_seq)` | хаб | записи журнала до `up_to_seq` закоммичены в PG | нет |
| `blob_published` | драйвер blob storage | содержимое долговременно доступно по неизменяемому ID | нет |
| `attachment_ready` | хаб, `PG-tx` | метаданные опубликованы, ссылки разрешены | «файл загружен» |
| `file_ready_for_agent` | воркер | файл проверен и durable-опубликован в каталоге исполнения | «файл готов агенту» |
| `local_cleanup_done` | воркер | локальные копии и журнал разговора удалены, минимальные квитанции оставлены | «локальная очистка завершена» |

Квитанцией **не являются** (§6.2, §8.4, §13.1): успешная запись в gRPC stream, HTTP/2 flow-control ACK, транспортный статус RPC, TCP ACK, закрытый дескриптор, заполненный буфер, запись байтов в stdin CLI.

Отметки времени (§14): `received_at` и `committed_at` по часам хаба; `stored_at`, `transmitted_at`, `agent_confirmed_at` по часам машины. Интервалы между хостами не вычисляются простым вычитанием.

## Ошибки (§6.3)

Каждая ошибка, причина отказа или паузы несёт `code` (машинный), `message`, `scope`, `retry` и `correlation_id`.

| `scope` | Область |
| --- | --- |
| `browser` | браузер, локальное хранилище |
| `auth` | авторизация, credential машины |
| `hub_db` | хаб и PostgreSQL |
| `delivery` | очередь, доставка, квитанции |
| `worker_disk` | воркер, журнал, диск |
| `cli_start` | запуск CLI, версия, локальный вход |
| `adapter_protocol` | протокол адаптера, совместимость формата |
| `agent_service` | внешний сервис агента: лимит, отказ API |

| `retry` | Смысл |
| --- | --- |
| `safe_same_key` | можно повторить тот же запрос с тем же ключом |
| `explicit_new_operation` | только новая операция по явному действию владельца, с предупреждением о возможном повторном действии |
| `after_condition` | повтор имеет смысл после устранения названной причины |
| `never` | повтор не изменит результат |

Частичный ответ при ошибке остаётся и помечается незавершённым; отрицательный результат инструмента не делает исполнение или разговор аварийным.

## Контракт адаптера (абстрактный)

Адаптер живёт в сопровождении и скрывает конкретный CLI (§10.1). Для автоматов важны только эти исходы:

| Операция | Исходы |
| --- | --- |
| `transmit(input или decision)` | `accepted(proof)`, `rejected(reason)` (однозначно, без неопределённости исполнения), `undetermined`. Адаптер обязан вернуть исход в пределах собственного deadline; по его истечении исход `undetermined` |
| `reconcile(command)` | `accepted_proven(proof)`, `not_accepted_proven` (только если источник истории гарантирует полноту, §7.2), `unknown` |
| `interrupt()` | `acknowledged`, `undetermined`; затем факт конца хода или выхода процесса |
| наблюдение | `phase(...)`, `run_finished`, `request_opened`/`request_closed`, `background_work(count или unknown)`, блоки ответа, `limit_reached`, фатальные ошибки |

**Зависит от этапа 0** (по каждому CLI):

| Вопрос | Где влияет |
| --- | --- |
| Какой наблюдаемый факт доказывает приём ввода и применение решения | delivery.md §2, §5 |
| Гарантирует ли нативная история полноту (возможен ли `not_accepted_proven`) и читается ли она без живого процесса | delivery.md §2, recovery.md R3, R4, R7 |
| Сохраняет ли прерывание процесс CLI, есть ли отдельное подтверждение прерывания | delivery.md §4, execution.md §1 |
| Какой сигнал означает конец хода и готовность к следующему вводу | delivery.md §3, execution.md §2 |
| Наблюдаемы ли фоновые работы | execution.md §4 (освобождение каталога) |
| Истекает ли запрос разрешения на стороне CLI, отклоняет ли CLI повторное решение по тому же запросу | delivery.md §5 |
| Безопасна ли приостановка чтения stdout CLI | execution.md §6 |

## Открытые вопросы и неоднозначности ТЗ

По убыванию влияния. Для каждого записано принятое здесь предложение; изменение решения затрагивает указанные документы.

1. **Доказательство приёма и полнота истории каждого CLI (этап 0).** Без положительного доказательства ввод никогда не станет «Принято агентом», а без гарантии полноты истории невозможен `not_accepted_proven`, и после любого сбоя на границе передачи останется только «Приём не подтверждён». Это определяет достижимость §6.2, классификацию restore (§18.1 п. 4) и AT-A-06/07, AT-G-11/12. Предложение: до результатов этапа 0 модель допускает оба исхода; адаптер без полной истории никогда не возвращает `not_accepted_proven`.
2. **Прерывание хода и сигнал готовности (этап 0).** Если прерывание завершает процесс CLI, каждое «Стоп» превращается в `stopped` и требует resume для следующего ввода; если CLI не сообщает явный конец хода и готовность, очередь не может выдавать следующий ввод автоматически (§7.3: выдача только после достоверной готовности). Предложение: готовность только по явному факту адаптера, наблюдённому после последней передачи; без него очередь стоит с удержанием `run_in_progress`.
3. **Наблюдаемость фоновых работ (этап 0) и освобождение каталога.** §5.1 разрешает освободить владение только при доказанном отсутствии активной и фоновой работы. Если адаптер этого не доказывает, владение держится до остановки исполнения, и два живых разговора в одном каталоге не могут работать по очереди без явного override (AT-F-11). Предложение: так и делать; UI называет конфликтующий разговор и предлагает остановить его или разрешить совместную работу.
4. **Остановка группы после смерти сопровождения: автоматически или по действию владельца.** §9.5 говорит «подтвердить остановку старой управляемой группы» и одновременно «воркер предоставляет действия ... принудительной остановки». Предложение: воркер сам завершает только подтверждённо принадлежащую группу (cgroup), потому что CLI без сопровождения не может получить ввод или решение; всё, что нельзя проверить, остаётся неопределённым до сверки или административного решения. Альтернатива: только по кнопке; тогда `owner_lost` будет висеть до действия владельца.
5. **Restore: живые исполнения и разговоры, которых нет в бэкапе, и квитанции удаления для разговоров, живых в бэкапе.** §18.1 и §14.1 запрещают выдумывать процессы и автоматически восстанавливать tombstone, но не говорят, что с ними делать. Предложение: известный разговор получает наблюдённое исполнение с поколением из записи принадлежности и паузой restore; неизвестный разговор не создаётся, исполнение попадает в отчёт с действиями диагностики и адресной остановки; разговор с квитанцией удаления блокируется с пометкой «удалён после точки восстановления» до решения владельца. Ничего не останавливается и не удаляется автоматически.
6. **Порядок шагов 3 и 4 удаления (§14.1).** Шаги пронумерованы последовательно, но п. 5 и AT-F-20 требуют отдельных статусов центральной и локальной очистки. Предложение: после подтверждённой остановки исполнения (шаг 2) центральная и локальная очистка идут независимо; при недоступной машине центральная часть может завершиться раньше, итоговый статус ждёт обе.
7. **Поколения исполнений после restore.** Восстановленный счётчик может повторно выдать номер поколения, уже выданный после бэкапа. Предложение: новые исполнения разговора запрещены, пока его машина не сверена в новом поколении; счётчик поднимается выше максимума, который сообщил воркер.
8. **Коллизия идентичности машины.** ТЗ требует видимый отказ, но клон с тем же credential, подключившийся при недоступном оригинале, неотличим по одному credential. Предложение: не вытеснять живой сеанс (повторный handshake отклоняется, пока heartbeat свежее 30 с), а смену `journal_id` журнала `CJ` считать сбросом локального состояния: ни одного вывода «не передано» по этой машине, диагностика владельцу.
9. **Политика разрешений при отключённом хабе.** §9.3 допускает «безопасный отказ по явно заданной политике», но не задаёт значение по умолчанию. Предложение: по умолчанию `wait` (ждать связи бессрочно); `deny_after(timeout)` только явной настройкой; разрешения по таймеру нет никогда.
10. **«Новые запуски» при заполнении журнала на 80 % (§9.3).** Неясно, относится ли это только к новым исполнениям или и к выдаче новых вводов. Предложение: к обоим; текущий ход продолжается.
11. **Место явного повтора неподтверждённого ввода в очереди.** Предложение: в конец FIFO, потому что это новая операция, а порядок задаёт серверная нумерация (§7.3). Альтернатива: в голову очереди с отдельным подтверждением.
12. **Отмена удаления разговора.** ТЗ не описывает. Предложение: удаление необратимо с момента записи tombstone.
13. **Повреждённый хвост журнала сопровождения.** Нельзя отличить оборванную запись намерения (передачи не было) от порчи носителя. Предложение: консервативно, команды без читаемого результата в повреждённой области считаются `acceptance_unconfirmed`.
14. **Пауза после завершения исполнения при пустой очереди.** §7.3 говорит «приостановить, сохранить ожидающие вводы». Предложение: ставить паузу всегда, чтобы причина оставалась видимой; UI предлагает составное действие «возобновить сессию и очередь».
