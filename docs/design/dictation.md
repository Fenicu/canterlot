# Диктовка: служба распознавания речи canterlot-speech

Служба `canterlot-speech` распознаёт речь для диктовки в поле ввода PWA. Хаб принимает звук от PWA по WebSocket `/api/v1/dictation` и пересылает его службе по unix-сокету; служба возвращает текст. Этот документ задаёт протокол хаб–служба (§1), живой алгоритм (§2), жизненный цикл движка (§3), ограничения (§4), конфигурацию (§5) и правила приватности (§6). Протокол PWA–хаб описан в §9, словарь замен терминов — в §10.

```
PWA ──WSS /api/v1/dictation──► canterlot-hub ──unix-сокет, кадры §1──► canterlot-speech serve
                                                                         └─ дочерний процесс движка
                                                                            (transcribe.cpp, Parakeet + Silero VAD)
```

## 1. Протокол хаб–служба

### 1.1 Транспорт и кадры

Unix-сокет потока, путь из `socket` конфигурации службы (по умолчанию `/run/canterlot-speech/speech.sock`). Права на сокет задаёт `UMask=0117` юнита (сокет `0660`, группа `canterlot`); служба права не меняет. Одно соединение — одна диктовка или один запрос `health`.

Каждый кадр в обе стороны:

| Байты | Поле |
| --- | --- |
| 0 | вид: `0x01` — JSON, `0x02` — звук |
| 1..5 | длина полезной нагрузки, u32 big-endian |
| 5.. | полезная нагрузка |

- JSON-кадр: один объект UTF-8 с полем `type`. Неизвестные поля игнорируются, неизвестный `type` — ошибка `bad_request`.
- Звуковой кадр (только хаб → служба): PCM s16le, 16 кГц, моно. Длина не ноль, чётная, не больше 8192 байт (256 мс). Нарушение — ошибка `bad_audio`.
- Предел JSON-кадра: хаб → служба 4096 байт, служба → хаб 262 144 байт. Больше, или неизвестный вид кадра — ошибка `bad_request` (служба) или разрыв соединения (хаб).

После ошибки служба закрывает соединение. Закрытие соединения хабом в любой момент равносильно `cancel`.

### 1.2 Сообщения хаба

Первый кадр обязан прийти за 5 с и быть JSON `start` или `health`.

| Сообщение | Когда | Смысл |
| --- | --- | --- |
| `{"type":"start","protocol":1,"sample_rate":16000,"format":"s16le","client":"hub/1.34.0"}` | первым | начать диктовку; `protocol` обязателен и равен 1, `client` — до 64 символов, идёт только в лог |
| звуковые кадры | после `start` | звук по мере записи, в темпе реального времени |
| `{"type":"finish"}` | после `start` | звука больше не будет: дораспознать и прислать `final` |
| `{"type":"cancel"}` | после `start` | отменить: служба закрывает соединение без ответа |
| `{"type":"health"}` | первым | состояние службы |

Звук после `finish`, повторный `start`, `start` с другим `sample_rate`/`format` — ошибки (`bad_request`, `bad_audio`).

### 1.3 Сообщения службы

| Сообщение | Смысл |
| --- | --- |
| `{"type":"state","state":"loading","mode":null}` | движок загружается или занят предыдущей диктовкой; звук уже копится |
| `{"type":"state","state":"listening","mode":"gpu"\|"cpu"}` | движок готов; `cpu` — медленный режим без промежуточного хвоста |
| `{"type":"text","committed":"…","tentative":"…","seq":N}` | полный текст: окончательная часть и промежуточный хвост, который ещё может измениться. `seq` растёт с 1, допустимы пропуски (служба шлёт только последнее состояние, если хаб читает медленно) |
| `{"type":"final","text":"…","reason":"finish"\|"too_long"}` | итог; затем служба закрывает соединение. `too_long` — звук достиг `limits.max_audio`, служба сама завершила диктовку тем, что услышала |
| `{"type":"error","code":"…"}` | ошибка; затем служба закрывает соединение |
| `{"type":"health","ok":true,"engine":"cold"\|"warm","mode":null\|"gpu"\|"cpu","model":"…","busy":false}` | ответ на `health`; `ok` — false, если последняя загрузка движка не удалась (до следующей удачной), `mode` известен только у тёплого движка, `model` — имя файла модели без `.gguf`, `busy` — идёт диктовка |

`state` приходит сразу после `start`: `listening`, если движок тёплый и свободен, иначе `loading` и позже `listening`. Если движок загрузился на CPU (§3.3), `listening` несёт `mode: "cpu"`.

Коды ошибок:

| Код | Причина |
| --- | --- |
| `bad_request` | нарушение порядка или формата сообщений, нет первого кадра за 5 с |
| `bad_audio` | неверный формат, размер или чётность звукового кадра; звук опережает реальное время больше чем на `limits.max_lead` |
| `busy` | уже идёт диктовка и одна ждёт очереди, или очередь не освободилась за `limits.queue_wait` |
| `idle` | нет звуковых кадров дольше `limits.idle` (до `finish`) |
| `lifetime` | диктовка длится дольше `limits.lifetime` от `start` |
| `start_timeout` | движок не готов за `limits.start_deadline` от `start` |
| `engine_unavailable` | движок не загрузился (нет модели, sha256 не сходится, нет GPU при `device = "gpu"`) |
| `engine_failed` | сбой распознавания или падение движка; движок перезапускается при следующей диктовке |
| `shutting_down` | служба останавливается |

### 1.4 Пример

```
хаб → {"type":"start","protocol":1,"sample_rate":16000,"format":"s16le","client":"hub/1.34.0"}
служба → {"type":"state","state":"loading","mode":null}
хаб → [звук 3200 байт] × N
служба → {"type":"state","state":"listening","mode":"gpu"}
служба → {"type":"text","committed":"","tentative":"Привет","seq":1}
служба → {"type":"text","committed":"Привет, это проверка.","tentative":"","seq":2}
хаб → {"type":"finish"}
служба → {"type":"final","text":"Привет, это проверка.","reason":"finish"}
(служба закрывает соединение)
```

## 2. Живой алгоритм

Parakeet v3 не потоковая модель, поэтому живой текст строится окнами. Все границы — абсолютные номера отсчётов от начала диктовки (16 000 в секунду).

1. **VAD.** Silero VAD (`VadSession::stream_feed`, кадр 512 отсчётов = 32 мс) оценивает звук по мере поступления. Кадр с вероятностью ≥ `vad_threshold` (0,5) — речь, < `vad_neg_threshold` (0,35) — тишина, между ними состояние не меняется.
2. **Сегменты.** Открытый сегмент начинается с начала речи минус `preroll` (200 мс); до первой речи его начало сдвигается вслед за звуком. Сегмент режется:
   - на паузе: тишина длиной `pause` (500 мс) после речи; разрез посередине паузы;
   - принудительно: сегмент достиг `max_segment` (20 с) — разрез посередине кадра с наименьшей вероятностью речи за последние `forced_window` (5 с).
   Разрез в отсчёте `c` фиксирует `[начало, c)`; `[c, сейчас)` остаётся следующим открытым сегментом, кадры VAD после `c` разбираются заново. Звук не теряется.
3. **Окончательный текст.** Зафиксированный сегмент распознаётся один раз, его текст дописывается к `committed` через один пробел.
4. **Промежуточный хвост.** Каждые `tentative_interval` (500 мс) нового звука при открытом сегменте с речью распознаётся `[начало, сейчас)`; результат заменяет `tentative`. Хвост сегментов, ждущих окончательного распознавания, показывается перед хвостом открытого, поэтому текст при разрезе не мигает.
5. **Очередь движка.** Распознаёт одно задание за раз. Окончательные задания идут первыми, по порядку сегментов. Промежуточное задание не ставится в очередь: такт, пришедший во время распознавания, только помечает, что хвост нужен, и он считается по свежему звуку, когда движок освободится; постановка окончательного задания снимает эту пометку. У задания есть `(segment_id, generation)`: промежуточный результат для уже зафиксированного сегмента или старшего поколения отбрасывается.
6. **Перекрытие.** Сегмент после принудительного разреза распознаётся с `overlap` (300 мс) звука до разреза; слова, середина которых попадает в перекрытие (по отметкам времени слов Parakeet), отбрасываются. Разрез на паузе перекрытия не получает.
7. **Завершение.** По `finish` служба сбрасывает VAD (`stream_flush`), разбирает оставшиеся кадры, фиксирует открытый сегмент до последнего отсчёта и после всех окончательных заданий шлёт `final` с `committed`.
8. Пока движок загружается, звук копится (до `max_audio`) и разбирается, когда движок готов.

## 3. Движок

### 3.1 Процессы

`canterlot-speech serve` — надзиратель: слушает сокет, ведёт диктовки и живой алгоритм, но нативный код не загружает. Распознаёт дочерний процесс движка — тот же бинарник со скрытой подкомандой `engine`. Он получает конфигурацию тем же файлом, читает задания из stdin и отвечает в stdout кадрами §1.1 (JSON и PCM). Окружение дочернего процесса очищено: передаются только `CUDA_VISIBLE_DEVICES`, `LD_LIBRARY_PATH` и `CUDA_CACHE_DISABLE=1`; переменные `TRANSCRIBE_*` (в том числе `TRANSCRIBE_DUMP_DIR`, который пишет тензоры на диск) не доходят.

Движок один, модель одна, диктовка одна: вторая диктовка ждёт до `limits.queue_wait` (в ожидании получает `state: loading` и копит звук), третья сразу получает `busy`.

### 3.2 Жизненный цикл

| Состояние | Событие | Действие | В |
| --- | --- | --- | --- |
| `cold` | `start` | запуск дочернего процесса, сверка отпечатков моделей (§5), загрузка | `loading` |
| `loading` | модель загружена | `state: listening` | `warm` |
| `loading` | загрузка не удалась | `engine_unavailable`, процесс завершается | `cold` |
| `warm` | конец диктовки | таймер `idle_unload` | `warm` |
| `warm` | `idle_unload` без диктовок | закрыть stdin движка; не вышел за 5 с — SIGKILL. VRAM и контекст CUDA освобождаются целиком | `cold` |
| `warm` | `cancel`, ошибка или разрыв во время распознавания | отмена нативного прогона (`CancelToken`); не вернулся за `limits.cancel_grace` (2 с) — SIGKILL | `warm` или `cold` |
| `warm` | сбой распознавания, падение движка | `engine_failed`, процесс убивается | `cold` |

Следующая диктовка после `cold` снова пробует GPU.

Движок и `probe` завершаются через `_exit` после сброса stdout и stderr: обработчики atexit и статические деструкторы C++ не запускаются. Иначе деструктор контекста ggml-cuda вызывается после остановки рантайма CUDA и роняет процесс (`CUDA error: driver shutting down`, abort, код 134). VRAM освобождает ядро при выходе процесса. Надзиратель пишет чистый выход (код 0) как `engine_unloaded` уровня INFO, любой другой — `engine_exited` уровня WARN с кодом.

### 3.3 Устройство и запасной режим на CPU

- `device = "auto"`: модель грузится на CUDA, затем прогоняется 1 с тишины (выделение памяти). Если CUDA не инициализировалась или памяти не хватило, движок грузится на CPU (`threads` потоков) в режиме `cpu`: без промежуточного хвоста, только окончательный текст по паузам. Повторной попытки GPU в той же диктовке нет.
- `device = "gpu"`: только CUDA, отказ — `engine_unavailable`.
- `device = "cpu"`: только CPU, режим `cpu`.
- VAD всегда считается на CPU в одном потоке: модель маленькая и не делит GPU с Parakeet.
- Сборка `--features cuda` динамически зависит от `libcuda.so.1`, `libcudart.so.12`, `libcublas.so.12`, `libcublasLt.so.12`. Без них бинарник не запускается вовсе (ошибка запуска юнита), запасной режим CPU покрывает только сбои инициализации и выделения памяти GPU.
- transcribe.cpp (`transcribe-cpp =0.4.2`) собирается статически, ggml-cuda только для sm_70 (`CMAKE_CUDA_ARCHITECTURES=70` через `TRANSCRIBE_CMAKE_ARGS`), CPU-часть без подстройки под сборочную машину (`GGML_NATIVE=OFF`, AVX2/FMA/F16C). Манифест компоновки transcribe-cpp-sys 0.4.2 в статической сборке не называет библиотеки CUDA, их добавляет `build.rs` крейта. Режим `dynamic-backends` (бэкенды отдельными модулями, CUDA подгружается только при наличии) не выбран: он требует класть `libtranscribe.so` и модули рядом с бинарником и менять раскладку выпуска; один статический бинарник проще выкатывать.

## 4. Ограничения службы

Служба соблюдает их сама, независимо от хаба:

| Ключ `[limits]` | По умолчанию | Смысл |
| --- | --- | --- |
| `max_audio` | 10m | звук одной диктовки; дальше `final` с `reason: "too_long"` |
| `lifetime` | 11m | жизнь диктовки от `start`; дальше `lifetime` |
| `start_deadline` | 30s | от `start` до `listening` (включая очередь и холодную загрузку) |
| `idle` | 15s | без звуковых кадров до `finish` |
| `max_lead` | 5s | звук не может опережать время с `start` больше чем на столько |
| `queue_wait` | 5s | ожидание занятого движка |
| `cancel_grace` | 2s | ожидание возврата нативного прогона после отмены |
| `write_timeout` | 5s | запись кадра хабу; дольше — диктовка отменяется |
| `finish_timeout` | 60s | от `finish` до `final`; дольше — `engine_failed` |

Кадр звука ≤ 8192 байт, не пустой, чётной длины; JSON от хаба ≤ 4096 байт. Очереди ограничены: звук хранится не дальше начала открытого сегмента (максимум `max_audio`), исходящие обновления текста сливаются в последнее, движку уходит не больше одного задания VAD и одного задания распознавания.

## 5. Конфигурация `speech.toml`

Полный пример с умолчаниями — в [configuration.md](../configuration.md#служба-распознавания-речи-speechtoml). Неизвестные ключи — ошибка запуска. Пути моделей относительные к каталогу файла конфигурации или абсолютные; `sha256` обязателен и сверяется при запуске `serve` (несовпадение — отказ запуска). Движок при каждой загрузке сравнивает отпечаток файла (устройство, inode, размер, время изменения) с проверенным при запуске и пересчитывает sha256 только изменённого файла: полный пересчёт модели 740 МБ без SHA-NI занимает около 4 с холодной загрузки.

## 6. Приватность и наблюдаемость

- Звук и текст живут только в памяти: на диск, в логи, `Debug`, ошибки и метрики не попадают. Ошибки transcribe.cpp (`Error::Aborted` несёт частичный текст) превращаются в код, их `Display` не пишется.
- Дочерний процесс ставит `PR_SET_DUMPABLE=0`. Сообщения transcribe.cpp идут через его обработчик логов, только уровни warn и error, обрезанные до 300 символов, с префиксом `transcribe:`. Надзиратель читает stderr движка и пропускает в журнал только строки с префиксами `transcribe:`, `ggml`, `GGML`, `CUDA`, `cuda`; остальные отбрасываются и считаются (`kind="engine_stderr_dropped"`).
- Временных файлов нет; `CUDA_CACHE_DISABLE=1` выключает кэш JIT CUDA (сборка содержит готовый код sm_70, JIT для V100 не нужен).
- Логи — строки `kind=…` уровня INFO: `speech_started`, `engine_spawned`, `engine_loaded` (режим, время загрузки и проверки sha256), `engine_unloaded`, `engine_killed` (причина), `dictation_started`, `dictation_finished` (длительность звука, число кадров, сегментов, заданий, p50/p90 времени распознавания, режим, исход). Ожидаемая недоступность службы (`canterlot-speech health` не достучался до сокета) — `speech_unavailable` уровня INFO. Сбои движка — WARN (`engine_load_failed`, `engine_failed`, `engine_exited`).

## 7. Команды

| Команда | Назначение |
| --- | --- |
| `canterlot-speech serve --config /etc/canterlot/speech.toml` | служба |
| `canterlot-speech health --socket PATH` | печатает `{"ok":…,"engine":…,"mode":…,"model":…}`; код выхода 0 при `ok`, иначе 1 |
| `canterlot-speech probe --config FILE --wav FILE [--realtime] [--json] [--text]` | живой алгоритм в одном процессе на WAV (16 кГц моно или с пересэмплированием): время холодной загрузки, каждое обновление (время звука последнего слова и время выдачи), длительности распознавания, задержка итога после конца звука, пик RSS и занятую память устройства через `nvidia-smi --query-gpu=memory.used` (до загрузки, пик и прирост: в LXC `nvidia-smi` не сопоставляет PID процессов). Текст печатается только с `--text` |

## 9. Протокол PWA–хаб

WebSocket `GET /api/v1/dictation`. Вход и проверка источника — как у основного сокета
(`GET /api/v1/ws`): cookie сеанса устройства владельца и разрешённый `Origin`; без живого
сеанса апгрейд отклоняется тем же ответом. Подпротокол не требуется.

Одно соединение — одна диктовка. Одновременно у владельца идёт не больше одной: слот
хранит сеанс устройства и поколение. `start` с того же устройства заменяет прежнюю
диктовку (та получает `replaced`), `start` с другого устройства получает `busy`, пока
прежняя продолжается.

Все числа длительности — от `start`.

### 9.1 Клиент → хаб

1. Первым за 5 с — текст `{"type":"start","sample_rate":16000,"format":"s16le","client":"pwa/<версия>"}`.
   `sample_rate` обязан быть `16000`, `format` — `"s16le"`, иначе `bad_audio`. `client` —
   до 64 символов, идёт только в журнал.
2. Звук — двоичные сообщения: PCM s16le, 16 кГц, моно. Непустой, чётной длины, не больше
   8192 байт; иначе `bad_audio`. Звук, опережающий реальное время больше чем на 5 с
   (32 000 байт в секунду), — тоже `bad_audio`.
3. Текст `{"type":"finish"}` — звука больше не будет, хаб ждёт `final`; или
   `{"type":"cancel"}` — хаб отменяет диктовку и закрывает соединение с кодом 1000 без
   дальнейших сообщений.

Текстовое сообщение — не больше 4096 байт. Неизвестный тип, второй `start`, звук до
`start` или после `finish`, не-JSON текст — `bad_request`.

### 9.2 Хаб → клиент

Только текстовые сообщения:

| Сообщение | Смысл |
| --- | --- |
| `{"type":"state","state":"loading","mode":null}` | движок загружается или занят |
| `{"type":"state","state":"listening","mode":"gpu"\|"cpu"}` | можно диктовать |
| `{"type":"text","committed":"…","tentative":"…","seq":N}` | полный текст со словарём замен: окончательная часть и хвост. `seq` растёт с 1, пропуски допустимы: если клиент читает медленно, хаб шлёт только последнее обновление |
| `{"type":"final","text":"…","reason":"finish"\|"too_long"}` | итог, затем закрытие 1000. `too_long` — служба сама завершила диктовку на 10 минутах звука: это нормальный конец, звук больше не читается |
| `{"type":"error","code":"…"}` | ошибка, затем закрытие 1000 |

Остановка хаба: хаб отменяет диктовку и закрывает сокет кодом 1001 без сообщения об
ошибке — клиент считает это потерей связи. Текстовое сообщение хаба — до 1 МиБ: служба
отдаёт JSON до 262 144 байт, а словарь замен может его расширить; если расширенный
`text` или `final` не влезает, диктовка кончается ошибкой `engine_failed`.

### 9.3 Коды ошибок клиенту

| Код | Когда |
| --- | --- |
| `speech_unavailable` | диктовка выключена в конфигурации; сокета службы нет, отказ соединения или срок 2 с; служба ответила `engine_unavailable` или `shutting_down` |
| `busy` | у другого устройства владельца уже идёт диктовка; служба ответила `busy` |
| `replaced` | этот же сеанс устройства начал новую диктовку |
| `bad_request` | нарушение порядка или формата сообщений, включая отсутствие первого за 5 с |
| `bad_audio` | неверный размер, чётность или формат звука; звук опережает время больше чем на 5 с |
| `idle` | звука нет 15 с до `finish` |
| `start_timeout` | за 30 с от `start` не пришло `listening` (очередь и холодная загрузка включены) |
| `lifetime` | диктовка идёт дольше 11 минут |
| `engine_failed` | служба ответила `engine_failed` или `bad_request` (это ошибка хаба, в журнале WARN); `final` не пришёл за 60 с после `finish`; соединение со службой закрылось неожиданно; запись службе стояла дольше 5 с |

`idle`, `lifetime`, `start_timeout` и `bad_audio` от службы хаб передаёт как есть: те же
пределы он соблюдает и сам.

### 9.4 Состояние службы и словарь

`GET /api/v1/dictation/status` отвечает
`{"available":bool,"reason":null|"disabled"|"no_service"|"unhealthy","mode":null|"gpu"|"cpu","engine":null|"cold"|"warm"}`.
`available` — диктовка включена, `health` службы доступен и его `ok`; `mode` и `engine`
берутся из ответа службы, когда он доступен. Показание кэшируется на 10 с, срок запроса —
2 с, одновременные вызовы делят один запрос. Сбой базы и прочие ошибки чтения списка
замен дают клиенту `engine_failed`: других кодов у диктовки нет.

## 10. Словарь замен

Владелец пишет пары «как слышится» → «что подставить»: «мейн» → `main`,
«сессион спаун» → `session_spawn`. Хранится на владельца в `dictation_terms`
(`owner_id`, `position`, `pattern`, `replacement`, `created_at`).

- `GET /api/v1/dictation/terms` — `{"terms":[{"pattern":"…","replacement":"…"}]}` в
  сохранённом порядке.
- `PUT /api/v1/dictation/terms` с тем же телом заменяет список целиком одной транзакцией
  и идемпотентен (нужен `Idempotency-Key`). Ответ — сохранённый список.
- Проверка отклоняет весь запрос стандартным конвертом ошибки:
  `too_many_terms` (больше 200 пар), `term_empty` (шаблон или замена пусты после обрезки),
  `term_too_long` (больше 100 скалярных значений Unicode после обрезки),
  `duplicate_term` (два шаблона равны после нормализации: NFC, нижний регистр, ё как е,
  пробельные серии в один пробел). Сохраняются значения без пробелов по краям.

Список снимается в момент `start`: правки посреди диктовки действуют со следующей.

Применение — чистая функция над текстом службы:

- текст приводится к NFC; проход слева направо, на каждой позиции шаблоны пробуются от
  самого длинного к короткому;
- сравнение без учёта регистра (простое посимвольное приведение), ё и Ё равны е;
  пробельная серия в шаблоне совпадает с любой пробельной серией текста;
- если первый (последний) символ шаблона — словесный (Unicode-буква или цифра, `_`), то
  перед (после) совпадения не может стоять словесный символ;
- замена вставляется как есть и заново не просматривается (один проход); текст вне
  совпадений сохраняется.

Для каждого обновления службы `committed' = apply(committed)`. Пустой `tentative` даёт
пустой хвост; пустой `committed` — `tentative' = apply(tentative)`. Иначе
`joined' = apply(committed + " " + tentative)`: если он начинается с `committed' + " "`,
хвост — остаток, иначе `tentative' = apply(tentative)`. Итог: `final' = apply(final)`.

Звук, текст и пары словаря живут только в памяти и в журнал не попадают: хаб пишет
`kind="dictation_started"` (версия клиента) и `kind="dictation_finished"` (исход, звук в
миллисекундах, число кадров, длительность, режим). Недоступная служба — `speech_unavailable`
уровня INFO, настоящие сбои протокола — WARN.
