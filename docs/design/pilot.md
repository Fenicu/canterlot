# Пилот: PWA, лимиты, «кранч» и сессии

Документ фиксирует состав пилота и поведение PWA, согласованные с владельцем 26.10.2026. Пилот — момент, когда владелец переносит ежедневную работу с HAPI на canterlot на одной машине. Это меньше первого эксплуатационного релиза (ТЗ §2.1): пилоту не нужна вся надёжность этапа 4, но в нём есть всё, без чего пришлось бы возвращаться в HAPI.

Документ дополняет `README.md`, `delivery.md`, `execution.md`, `streams.md` и `recovery.md`. Имена событий, состояний и причин в новом коде берутся отсюда; расхождения с остальными документами исправляются в документах, если имя уже записано в базу как вид события.

## 1. Состав пилота

Входит:

1. PWA для телефона и десктопа: список сессий, чат с потоковым ответом, блоки инструментов, ленты субагентов.
2. Оба адаптера: Claude Code и Codex (этап 2). OpenCode в состав не входит: он включается после пилота, когда пройдёт смоук (решение владельца 31.10). Код уже в `main`, но без таблицы `[opencode]` харнесс скрыт и пилот его не видит.
3. Новая сессия запускается в режиме «Без подтверждений» (`bypass`), и в Claude Code, и в Codex, и в OpenCode (решение владельца 31.10); уже созданные сессии сохраняют свой режим. Режим «Как в настройках CLI» (`owner`, решение OD-3 этапа 0) ничего не передаёт при запуске: Claude Code берёт `defaultMode` из `~/.claude/settings.json` (у владельца `dontAsk`: работает только список allow, остальное отклоняется молча и карточка не появляется), Codex наследует `approval_policy` и `sandbox_mode` (у владельца `never` и `danger-full-access`). Настоящий режим известен только адаптеру и в протокол не входит, поэтому PWA показывает статичное пояснение. Сессия с пустым режимом запускается как `owner`. Интерактивные вопросы агента (`AskUserQuestion`, Codex `requestUserInput`) обязательны.
4. Очередь, отмена непереданного ввода, прерывание, остановка, продолжение остановленного разговора (F-10).
5. Вложения любых файлов, включая «Поделиться» из Android.
6. Модель и агент у каждого ответа, включая субагентов; расход на ответ.
7. Лимиты подписок всегда на виду; режим «кранч».
8. Отложенные сообщения.
9. Смена модели, режима разрешений и усилия посреди сессии.
10. Пресеты инструкций: выбор при создании сессии и смена посреди работы (§4).
11. Состояние машины: связь, CPU, память, диск, нагрузка.
12. Экспорт ответа в markdown и картинкой.
13. История расхода лимитов.

После пилота: туду-лист агента (§12.2), межсессионные инструменты для моделей (§12) и инструменты оркестратора (§12.1), push-уведомления, терминал, просмотр рабочих файлов, собственный вход вместо Authelia, cgroup v2 и восстановление R3/R4 (план 1.2c), OpenCode после смоука (план 2d), другие харнессы (Antigravity, pi), прогноз расхода лимитов и лимиты других провайдеров (§7.1), переезд разработки canterlot в canterlot.

## 2. Размещение

- Хаб и PostgreSQL — в отдельном LXC Proxmox. Воркер — на рабочей VM владельца, systemd user service.
- PWA и API — один HTTPS-origin за Caddy на web-сервере; Caddy проверяет вход через Authelia и проксирует на хаб в LXC.
- Хаб доверяет заголовку пользователя только от адреса Caddy; прямой доступ к HTTP-порту хаба из других сетей закрыт. CSRF-защита изменяющих запросов и проверка Origin на WSS остаются обязательными (§15).
- Воркер ходит к хабу по gRPC с TLS от внутреннего УЦ; входящих портов на машине воркера нет.
- Восстановление из снимка: база хаба окажется «в прошлом» относительно журналов воркера. Сигнал уже есть — расхождение курсоров (`state_divergence`). Реакция проектируется на этапе 4 (R7); до тех пор воркер останавливается с явной причиной.
- Обновления: по образцу системы обновления meeting-pipeline. Обновление воркера не убивает идущие исполнения: процессы сопровождения переживают перезапуск управляющей службы (R2).

## 3. Сессии и их список

Сессия интерфейса — это разговор (conversation) хаба с его исполнениями.

Атрибуты, которые задаёт владелец: название (по умолчанию автозаголовок по первому сообщению), цвет-метка, закрепление, группы (свободные, сессия может быть в нескольких), архив. Группы и закрепление — данные хаба, синхронные между устройствами.

Остановленную сессию можно удалить из меню сессии. Удаление необратимо, подтверждается явно и убирает данные хаба и файлы вложений; журналы и копии вложений на машине и нативная история CLI остаются ([recovery.md](recovery.md), R6).

Список показывает: цвет, название, агент и модель, машину, состояние активности (§9) с кратким доказательством («выполняет `cargo test` · 4 мин», «ждёт ответа», «пауза: лимит»), непрочитанное. Сверху — плавающая полоса вкладок групп («Все», «Закреплённые», группы с счётчиками) и строка лимитов. Поиск по названиям входит в пилот (§12.1); полнотекстовый — после.

## 4. Создание сессии и пресеты инструкций

Поля: машина, рабочий каталог (любой абсолютный путь при `allowed_workdir_roots = ["/"]`, экран показывает три последних, §13), агент (Claude Code / Codex / OpenCode, последний только на машине с таблицей `[opencode]`), модель, усилие, пресет инструкций (по умолчанию «Без инструкций»), «кранч» и текст продолжения. Каталог вводится любым путём под разрешёнными корнями; хаб запоминает проверенные каталоги (до 20 на машину) и показывает на экране три последних, существование каталога на машине он не проверяет.

Пресет инструкций — именованный текст инструкций агента, который хранится в хабе (не у воркера) и редактируется в PWA и через инструменты MCP canterlot (решение владельца 29.10). Встроенные пресеты «Без инструкций» (по умолчанию) и «Как у владельца» нельзя изменить или удалить. «Без инструкций»: агент запускается без личных и глобальных инструкций владельца — у Claude Code без `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` и `.claude/rules` в каталогах выше корня репозитория (например, `/home/fenicu/CLAUDE.md`), без `~/.claude/CLAUDE.md`, `~/.claude/rules` и автопамяти; у Codex без глобального `AGENTS.md` владельца, без его памяти и без `developer_instructions` из его конфигурации. Инструкции самого репозитория (`CLAUDE.md`, `AGENTS.md` в корне и подкаталогах) действуют; вход, MCP-серверы, плагины и настройки владельца остаются (решение владельца 29.10: исполнители не должны видеть инструкций оркестратора и его русского языка). Пользовательский пресет — «Без инструкций» плюс его текст (до 64 КиБ). Стартовый пресет «Исполнитель (английский)» (общение, рассуждения и отчёты на английском; язык коммитов, интерфейса и документации задаёт задача) создаётся один раз для владельца как обычный пресет, его можно менять и удалять; по умолчанию новые сессии создаются с «Без инструкций». «Как у владельца» — конфигурация агента владельца без изменений, canterlot добавляет только свой MCP-сервер и служебные флаги; сессии, созданные до пресетов, переведены на него миграцией. Сессия выбирает пресет при создании и может сменить его посреди работы (§5.4): смена действует со следующего хода, агент перезапускается между ходами с сохранением истории; если перезапуск не удался, возвращается прежняя конфигурация, а ввод отклоняется. Пока в Claude Code идёт фоновая работа, смена ждёт её конца: сообщение уходит сразу со старыми инструкциями, владелец видит предупреждение в ленте, а перезапуск происходит, как только список задач опустел. Явная остановка работает сразу. Сессия держит копию той версии пресета, которую применила: правка пресета идущие сессии не меняет, новую версию применяют явно; удалённый пресет пропадает из списков, а сессии с ним продолжают работать со своей копией. Агент через MCP canterlot видит пресеты (`canterlot_presets_list`), сохраняет (`canterlot_preset_save`: создаёт или меняет) и применяет к своей сессии (`canterlot_preset_apply`); такие пресеты и правки помечены в PWA как сделанные агентом. Агент действует только на свою сессию, canterlot не добавляет своего подтверждения: действует разрешение самого CLI. Подтверждение инструмента MCP от Codex (форма elicitation без полей с `_meta.codex_approval_kind`) показывается владельцу карточкой разрешения, согласие действует на один вызов. В PWA пресеты — экран «Инструкции» (список, создание, правка, удаление), выбор на экране новой сессии и в настройках сессии. После пилота агент-оркестратор создаёт сессии для других агентов с выбранным пресетом (часть делегирования, §12).

Механизм (по коду; живые проверки 29.10 и то, что ещё не подтверждено, — §15, вопросы 3 и 8). Claude Code (минимум 2.1.311): `--settings` с `claudeMdExcludes` — абсолютные пути, вычисленные при каждом запуске: `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.claude/CLAUDE.md`, `.claude/AGENTS.md` и `.claude/rules/**` во всех каталогах строго выше корня репозитория (ближайший каталог от рабочего вверх с записью `.git`; без git — сам рабочий каталог), и по логическому пути рабочего каталога, и по пути с раскрытыми символическими ссылками (CLI идёт от физического cwd и сверяет исключения с реальными путями), плюс `CLAUDE.md` и `rules/**` пользовательского каталога (`~/.claude` и `CLAUDE_CONFIG_DIR`, если задан, оба в тех же двух видах) — и `autoMemoryEnabled: false`; если корнем оказался сам `$HOME`, исключаются и личные `~/CLAUDE.md`, `~/CLAUDE.local.md`, `~/AGENTS.md`. Текст пресета — `--append-system-prompt-file` из `instructions.md` каталога исполнения (`0600`); всегда `--system-prompt-snapshot off`, чтобы после перезапуска с `--resume` действовал новый текст. `--bare` не подходит (отключает вход по OAuth), `--setting-sources ""` отбросил бы все настройки владельца. Codex: глобальный `AGENTS.md` не отключается ни ключом конфига, ни параметром app-server, поэтому для всех пресетов, кроме «Как у владельца», canterlot запускает Codex со своим `CODEX_HOME` (по умолчанию `<data_dir>/codex-home` воркера, каталог во временных путях и внутри дома владельца отвергается): при каждом запуске под блокировкой создаются символические ссылки на содержимое `~/.codex` владельца (вход, конфиг, сессии, навыки) без `AGENTS.md`, `AGENTS.override.md`, файлов SQLite, блокировок и каталогов демона, настоящие файлы в `CODEX_HOME` canterlot не заменяются (исполнение получает диагностику `codex_home_conflict`), а файлы владельца не открываются; рядом лежит собственный `AGENTS.md` canterlot (инструкции его MCP-сервера). `CODEX_SQLITE_HOME` из окружения убирается, у Codex свой индекс тредов, память отключена `--disable memories`. Текст пресета передаётся через `developerInstructions` в `thread/start` и `thread/resume`: у «Без инструкций» это пустая строка (по замыслу перекрывает `developer_instructions` из конфигурации владельца), при смене пресета первой строкой идёт примечание canterlot о смене. `AGENTS.md` репозитория действует (Codex не ищет его выше корня проекта). «Как у владельца» запускает Codex с настоящим `CODEX_HOME` владельца и с его `developer_instructions`, к которым добавляются инструкции MCP-сервера canterlot. OpenCode: «Как у владельца» — настоящий `XDG_CONFIG_HOME` без `OPENCODE_CONFIG_DIR`; «Без инструкций» и пресет — `OPENCODE_CONFIG_DIR=<каталог исполнения>/opencode-config`, где лежат ссылки на всё содержимое каталога владельца, кроме его `AGENTS.md` (так читаются и `opencode.json`, и `opencode.jsonc`, и плагины), и `OPENCODE_DISABLE_CLAUDE_CODE=1`; текст пресета — `AGENTS.md` того же каталога (`0600`). Смена между «Без инструкций» и пресетами не перезапускает OpenCode: он следит за файлом и присылает модели `<system-update>` на следующем шаге, фоновые задачи продолжают работать. Перезапуск с той же сессией и остановка фоновых задач остаются только у перехода на «Как у владельца» и обратно, потому что меняется окружение запуска. Разрыв с описанием «Без инструкций» принят (решение 4 спеки OpenCode): `~/AGENTS.md` и `AGENTS.md` выше корня репозитория читаются, если рабочий каталог лежит под домом; отдельно их выключает только внутренняя переменная `OPENCODE_TEST_HOME`, а файла `~/AGENTS.md` у владельца нет. Хуки плагинов владельца (например, SessionStart) добавляют свой текст и в «Без инструкций»: canterlot их не фильтрует, это часть конфигурации владельца.

MCP-серверы владельца и делегированные сессии (D24, решение владельца 01.11). Сессия, созданная другой сессией (`session_spawn`: задан родитель или глубина больше нуля, потомок удалённого родителя остаётся такой), не грузит MCP-серверы владельца ни в одном адаптере, у неё один сервер canterlot: сервер `nanokvm` управляет настоящим железом, а делегат в `bypass` не должен до него дотянуться. Хаб ставит флаг `isolate_mcp` в `StartExecution` при каждом запуске и возобновлении (поле 12, только с возможностью `session_tools_v1`: воркеру без неё команда не уходит), воркер несёт его в `StartCli` (поле 14) и `StartSpec`. Флаг не зависит от пресета инструкций и не имеет пути из аргументов инструментов, снять его агент не может. Сессии владельца не меняются. Адаптер, который не умеет изоляции, не запускает делегированную сессию (`mcp_isolation_unsupported`). Claude Code: `--strict-mcp-config` оставляет только `mcp.json` исполнения, то есть серверы пользователя, проекта и плагинов не стартуют; коннекторы аккаунта выключает `ENABLE_CLAUDEAI_MCP_SERVERS=false`; плагины, навыки и настройки пресета остаются. Codex: общий дом ссылается на `config.toml` владельца, поэтому его серверы грузятся в любом режиме; делегированной сессии достаётся отдельный дом (`<home_dir>-isolated`, у «Как у владельца» `<home_dir>-isolated-owner` со ссылкой на `AGENTS.md` владельца) с копией `config.toml` без `mcp_servers` (это единственный файл владельца, который воркер читает; не разобрался - запуск прерывается), запуск идёт с `--disable apps` (коннекторы аккаунта) и `--disable plugins` (плагины приносят свои серверы, вместе с ними пропадают и навыки плагинов), а действующий `config/read` сверяется до `thread/start`: любой другой включённый сервер либо включённые приложения и плагины дают `mcp_isolation_failed`. OpenCode: каталог конфигурации исполнения берёт у владельца всё, кроме `mcp`: `opencode.json` и `opencode.jsonc` копируются без этого ключа, `XDG_CONFIG_HOME` указывает на пустой каталог исполнения, `OPENCODE_DISABLE_PROJECT_CONFIG=1` выключает конфигурацию репозитория, а список `GET /api/mcp` сверяется с единственным canterlot (иначе `mcp_isolation_failed`); это относится и к «Как у владельца», где остаются только инструкции владельца. Серверы репозитория (`.mcp.json`, `opencode.json` проекта) в делегированной сессии тоже не грузятся.

Инвариант для рабочих проектов: canterlot ничего не создаёт и не меняет в репозитории и ничего не пушит. Вложения, файлы инструкций исполнений, `CODEX_HOME` canterlot, каталоги исполнений и будущие worktree для делегирования живут в каталоге данных воркера; тексты пресетов хранит хаб.

## 5. Чат

### 5.1. Лента

- Сообщение пользователя — тонированный пузырь с отметками «сохранено хабом» и «принято агентом» (§6.2, F-03).
- Ответ агента — карточка: шапка «агент · время · модель» и кнопка «инфо»; внутри текст, блоки инструментов и вызовы субагентов в порядке появления.
- Блок инструмента свёрнут в строку: имя, краткий аргумент, статус-таблетка, длительность. Раскрытый показывает хвост вывода во вдавленной области и «Показать полностью · N строк» (полное содержимое загружается отдельно, §12.2).
- Вызов субагента — отдельная строка с живым статусом («Субагент · Explore · haiku — читает поток»). Касание открывает ленту субагента (§6).
- Потоковый текст: дельты объединяются до 25 мс, видимая область обновляется не чаще кадра; markdown и подсветка не перерабатывают историю на каждый токен (§8.3).
- Автопрокрутка, только пока пользователь у нижней границы; чтение старого не сбивается новым токеном (§12.2).
- Под лентой — отдельно очередь («в очереди») и отложенные сообщения («отправится в 23:30»), не внутри общего индикатора.

### 5.2. Поле ввода

- На сенсорном вводе Enter — новая строка, отправка только кнопкой; поле с `enterkeyhint="enter"`. На десктопе Enter отправляет, Shift+Enter — перенос. Переключается в настройках.
- IME и вставка большого текста не отправляют сообщение.
- Экранная клавиатура не перекрывает поле: `interactive-widget=resizes-content` в Chrome Android.
- Кнопки: вложение, «Прервать» (пока идёт ход), отправка. Долгое нажатие на отправку — «Отправить позже» (выбор времени).
- Черновик хранится на устройстве по сессии (§12.2, §12.3).

### 5.3. Отложенные сообщения

Отложенное сообщение — ввод хаба со временем выдачи. До наступления времени оно видно в списке под лентой, его можно изменить или отменить. В момент наступления оно ставится в обычную очередь разговора. Планировщик тот же, что будит сессии в «кранче» (§8).

Время выдачи задаётся только точно: быстрые варианты «Через 15 минут» и «Через час» показывают итоговое время («Через час · 11:42»), остальное — выбор даты и времени. Расплывчатых вариантов вроде «вечером» или «завтра утром» нет (решение владельца 29.10).

### 5.4. Смена настроек посреди сессии

Модель, режим разрешений и усилие меняются командой в очереди; применяются со следующего хода и видны в шапке. Механизм: Claude Code — управляющие запросы stream-json (`set_model`, `set_permission_mode`), Codex — переопределения в `turn/start`, OpenCode — `POST .../model` и `PATCH` правил сессии перед вводом, на корневую сессию и живых потомков. Точный набор проверяется на этапе 2; недоступная агенту настройка не показывается или объясняет причину. Пресет инструкций (§4) меняется там же, но применяется иначе: Claude Code и Codex перезапускаются между ходами с сохранением истории, поэтому лист настроек предупреждает о перезапуске и остановке фоновых задач сессии; OpenCode перечитывает файл инструкций без перезапуска, кроме перехода на «Как у владельца» и обратно.

### 5.5. Вопросы и разрешения

- Вопрос агента — карточка: текст, 2–4 варианта с описаниями (одиночный или множественный выбор), «свой ответ», если агент его допускает (§11).
- Разрешение (если всё-таки пришло, например в сессии не в bypass) — компактная карточка «Разрешить / Отклонить» с точными аргументами.
- Первое зафиксированное решение единственное; другие устройства видят итог. Отдельно показываются «решение сохранено» и «агент применил решение».
- Варианты вопроса показываются так, как их прислал агент (обычно по-английски), без перевода; по-русски только обвязка карточки (кнопки, «Свой ответ», подписи). Агенту уходит ровно присланное значение (решение владельца 29.10).
- Пропала связь воркера с хабом при открытом вопросе или разрешении — агент ждёт связи, пока она не вернётся или владелец не остановит сессию; ничего не разрешается и не отклоняется само (решение владельца 29.10).
- Действие, которое CLI разрешил сам по своим правилам, помечается в строке инструмента: «Разрешено правилами CLI»; кнопок отзыва нет (решение владельца 29.10).

### 5.6. «Инфо» об ответе и экспорт

Нижний лист «инфо» показывает по частям ответа: агента (основной или субагент), модель, токены (вход, выход, кэш), длительность, расход лимита «≈ 0,4 % недели» (§7). Действия: «Копировать как markdown», «Копировать картинкой» — ответ отрисовывается в изображение в браузере; на телефоне отдаётся в «Поделиться», на десктопе — в буфер обмена.

### 5.7. Картинки, на которые смотрел агент

Если агент открыл изображение (Claude Code: `Read` картинки; Codex: просмотр изображения), блок инструмента показывает саму картинку, а не только путь: миниатюру прямо в строке инструмента, по касанию — полноэкранный просмотр с масштабированием. То же для картинок, которые агент получил как вложение.

- Источник байтов: то, что агент действительно получил (содержимое результата инструмента, если адаптер его отдаёт; у OpenCode это `data:` URI в `session.tool.success.content`, в том числе у инструментов MCP, декодируется при подготовке картинки, вне цикла сопровождения), иначе — чтение файла по пути из вызова инструмента воркером сразу в момент события (позднее изменение файла не подменяет увиденное).
- Путь: воркер публикует картинку на хаб отдельным потоком канала данных (как вложения, в обратную сторону: надёжная публикация на хабе → только потом запись `block_media` в журнал сопровождения со ссылкой); пока картинка не опубликована, блок показывает заглушку «картинка загружается», при сбое — «картинка недоступна» с причиной.
- Ограничения: только изображения (png, jpeg, webp, gif), до 20 МиБ на картинку; крупнее — показывается путь и размер без миниатюры. Миниатюра строится в браузере.
- Хранение — пока жива сессия, как у вложений. В логи и метрики байты и пути не попадают.
- Точный формат результата чтения картинки у обоих CLI проверяется на этапе 2; синтетический адаптер получает шаг «посмотреть картинку» для тестов до этого.

## 6. Субагенты и модели

Работа субагента показывается не хуже основного чата: та же лента, тот же отрисовщик, тот же живой поток. Шапка ленты субагента — путь в дереве («оркестратор → субагент»).

Данные:

- блок ответа получает поля `agent` (основной или имя субагента), `model` и ссылку на вызов, породивший субагента (`parent_block_id` уже есть);
- итог хода (`run_finished`) получает расход по моделям;
- Claude Code: модель в каждом сообщении ассистента, сообщения субагента помечены `parent_tool_use_id`, итог хода содержит разбивку по моделям;
- Codex: модель известна на старте треда и хода; что app-server отдаёт про субагентов, проверяется на этапе 2;
- OpenCode: субагент это дочерняя сессия. Дорожка — блок вызова `subagent`: связь приходит в `session.tool.progress {metadata.sessionID}` до первого ввода потомка, после разрыва её даёт `metadata` результата вызова. Имя агента из `session.created` и `session.step.started`, модель из `session.step.started`. Расход потомка идёт в `run_finished` под его именем, контекст разговора считает только основной агент. Блоки потомка, целиком выпавшие в разрыв потока, не восстанавливаются: проекция читается только у корневой сессии, итог потомка виден в результате вызова.

На десктопе правая панель показывает дерево делегирования сессии (кто кого запустил, с состояниями) и выбранную ленту субагента.

## 7. Лимиты и расход

Источники (тот же механизм, что `agent-limits` владельца):

- Claude Code сам присылает `rate_limit_event` с загрузкой пятичасового и недельного окон и временем сброса — воркер берёт значения из потоков живых сессий бесплатно;
- Codex отдаёт лимиты через `account/rateLimits/read` app-server без запроса к модели;
- когда живых сессий нет, воркер опрашивает редко (Claude — дешёвым запросом, не чаще раза в 30 минут; Codex — каждые 5 минут);
- OpenCode опроса не имеет, API квот в нём нет. Источник только отказ: `provider.quota` и `provider.free-limit` дают `limit_reached` со сбросом из `retryAfterMs` (решение владельца 31.10). Окна в отказе нет: ожидание длиннее пяти часов считается недельным окном, иначе пятичасовым. Без `retryAfterMs` времени сброса нет, и карточка его не обещает.

Хаб хранит снимки лимитов по провайдеру и времени: строка лимитов в чате и списке, график по дням (экран истории лимитов) с разбивкой по сессиям и моделям.

Расход на ответ: токены точные (из итога хода); доля лимита — оценка «≈» как разница загрузки до и после хода. Лимит общий для всех сессий и устройств подписки, проценты целые, поэтому при параллельной работе разделить расход нельзя — это показывается честно, без ложной точности.

Модели знают остаток:

- инструмент `canterlot_limits` в MCP-сервере canterlot (воркер уже поднимает MCP-сервер для Claude Code);
- короткая системная пометка во входящем сообщении только при пересечении порогов 80 / 90 / 95 % недели.

### 7.1. Прогноз и другие провайдеры (после пилота, по решению владельца 28.10)

- **Прогноз темпа.** По истории снимков хаба для пятичасового окна и недели: ожидаемая загрузка на текущий момент, запас или дефицит относительно равномерного расхода и «кончится через …» либо «хватит до сброса». Показывается в строке лимитов и на экране истории; тот же прогноз берёт `route_task` (§12.1). Считается в хабе, без внешних инструментов.
- **Лимиты провайдеров без своего адаптера** (Antigravity, Cursor и другие): воркер может читать их через установленный на машине `codexbar usage --format json --provider <имя>` — только чтение лимитов, без запросов к моделям, с тем же хранением снимков и прогнозом. Для Claude Code и Codex так же работает опрос без живых сессий (README, раздел о лимитах), а показания живых сессий его дополняют.
- **Лимиты OpenCode Go.** Пока только отказ, §7. `codexbar usage --provider opencodego` и месячное окно отложены решением владельца 31.10: `codexbar` читает учётные данные владельца, а `LimitWindow` месячного окна не знает.

## 8. «Кранч» и паузы по лимитам

«Кранч» включается на сессию. Правила (решения владельца):

- **Пятичасовое окно.** Заранее не останавливаться. Если CLI вернул ошибку лимита со временем сброса (факт адаптера), разговор получает паузу `quota_exhausted` с временем пробуждения. После сброса окна (проверяется по лимитам, а не только по часам) харнесс снимает паузу и отправляет в тот же разговор агента текст продолжения.
- **Недельное окно, 95 %.** Хаб перестаёт начинать новые ходы у сессий этого провайдера: не выдаёт сообщения из очереди и не шлёт автопродолжение; пауза `weekly_reserve`. Идущий ход не прерывается. Остальные 5 % — резерв владельца: в любой сессии есть действие «Продолжить, тратя резерв» (ручное продолжение этой сессии). Автоматика в резерв не заходит. После сброса недели паузы `weekly_reserve` снимаются автоматически.
- Лимиты Claude и Codex независимы.
- После сброса сразу будятся все сессии в «кранче», которые остановил лимит (а не по очереди). Сессии, которые к этому моменту просто стояли без работы, текста продолжения не получают; если в очереди уже есть сообщение владельца, продолжением становится оно.
- Текст продолжения: по умолчанию «Лимиты восстановлены, продолжай с того места, где остановился.», меняется на сессию.
- Без «кранча» сессия при упоре в лимит останавливается с явной причиной и временем сброса.

Паузы `quota_exhausted` и `weekly_reserve` — причины удержания очереди хаба (`delivery.md` §3); пробуждение — плановая команда того же планировщика, что у отложенных сообщений. Всё проверяется синтетическим адаптером со сценарием «упёрлись в лимит со временем сброса» (§10.6) до подключения настоящих агентов.

## 9. Состояние активности сессии

Одно вычисляемое хабом состояние с доказательствами — для списка, шапки чата (F-11) и будущих межсессионных инструментов:

| Состояние | Условие | Доказательства |
| --- | --- | --- |
| `idle` | хода нет, очередь пуста, нет открытых вопросов, фоновая работа агента завершена | время последнего хода |
| `working` | ход идёт, события поступают | фаза (`generating`, `running_tool` + имя инструмента), длительность |
| `waiting_for_user` | открыт вопрос или запрос разрешения | текст вопроса кратко |
| `stalled` | ход идёт, событий нет дольше порога | последнее событие, фаза, жив ли процесс, CPU |
| `quota_paused` | пауза по лимиту | провайдер, окно, время пробуждения |
| `failed` | процесс умер, владелец потерян, ошибка, исчерпан контекст | причина (`owner_lost`, `context_exhausted`, …) |
| `stopped` | исполнение остановлено | исход |

Порог `stalled`: в фазе генерации 5 минут, в фазе инструмента 30 минут; оба настраиваются. `stalled` — подозрение с доказательствами, а не действие: сессия не прерывается автоматически.

Заполнение контекста (токены контекста, события сжатия) показывается в «инфо»; исчерпание — явное `failed: context_exhausted`, а не тишина.

Застрявшая сессия (OpenCode). Один и тот же `provider.invalid-request` дважды подряд значит, что история не меняется и следующий ввод получит тот же отказ. Причина такого отказа у провайдера не установлена, поэтому статус это `failed: session_stuck`, а не `context_exhausted`: контекст не исчерпан. Исполнение живо, очередь стоит на паузе `session_stuck`, карточка предлагает «Сжать контекст» и предупреждает, что сжатие тратит токены. Само оно не запускается (решение владельца 31.10). Удача снимает паузу, отказ оставляет карточку и разрешает повторить.

## 10. Вложения

- Любые файлы до 100 МиБ, до 10 на ввод; лимиты объявляются браузеру, хабу и воркеру одинаково (§13).
- Путь: загрузка на хаб с ID и checksum → надёжная публикация в хранилище хаба → метаданные в PostgreSQL (§13.1) → передача воркеру потоком по каналу данных (не блокирует управление) → надёжная публикация в каталоге вложений исполнения в каталоге данных воркера → ввод выдаётся агенту только после готовности всех вложений.
- Агенту передаётся путь к файлу и описание; изображение вдобавок — нативным блоком (Claude Code: base64-блок `image`, Codex: `localImage` по пути, OpenCode: `files` с `file://`, если модель принимает картинки и файл не больше 20 МиБ). У OpenCode ввод зависит от модели, поэтому каталог несёт `images` и `context_window` на модель, а форма объясняет, что модели без картинок вложение придёт путём.
- Android: установленное PWA — цель «Поделиться» (Web Share Target): файл из галереи или любого приложения попадает в выбранную сессию как вложение черновика.
- Хранение: пока жива сессия; при удалении сессии — вместе с ней.

## 11. Состояние машины

Экран машины: связь (последний heartbeat, `available` / `degraded` / `unavailable`), CPU, память, диск, нагрузка, сессии на машине. Воркер отдаёт метрики каждые 30 секунд по управляющему каналу; порог предупреждения по диску — 85 %. Содержимое чатов в метрики не попадает (§17).

## 12. Межсессионная работа (после пилота, закладывается сейчас)

Цель: сильная модель (Opus, GPT) делегирует работу сессии другого харнесса и получает надёжный сигнал о её завершении.

Инструменты MCP-сервера canterlot:

- `sessions_list`, `session_inspect` — состояние (§9) с доказательствами, последние сообщения и блоки, ресурсы процессов;
- `session_send` — сообщение в очередь другой сессии с пометкой «от сессии X, модель Y» и дедупликацией;
- `session_spawn` — новая сессия выбранного харнесса и модели, по желанию в изолированном worktree вне репозитория, с брифом и подпиской на завершение; после приёма результата worktree и процессы убираются;
- право создавать сессии (решение владельца 29.10): оркестратор сам создаёт сессию только в пределах белого списка владельца — харнессы и модели; всё, что вне списка, `session_spawn` превращает в запрос на одобрение, который владелец видит в PWA карточкой как разрешение агенту, и сессия появляется только после его «Разрешить»; белый список владелец правит в PWA, агент его не меняет;
- подписка по умолчанию: `session_send` и `session_spawn` автоматически подписывают отправителя на переход получателя в `idle` / `waiting_for_user` / `stalled` / `failed`, отказаться можно только явным параметром — оркестратор не может «забыть» поставить ожидание;
- подписка на смену состояния — основной способ ожидания: подписку хранит хаб, при переходе в `idle` / `waiting_for_user` / `stalled` / `failed` событие ложится в очередь подписавшейся сессии как durable-команда; переживает перезапуск оркестратора; блокирующий `session_wait` с таймаутом — вспомогательный;
- итог при завершении: состояние, финальный ответ (усечённый), коммиты за ход (HEAD до и после), изменённые файлы, расход, длительность;
- защита от зацикливания: лимит частоты и глубины цепочки сообщений.
- серверы MCP владельца (D24): делегированная сессия не наследует их ни в одном адаптере, у неё только canterlot; признак `isolate_mcp` ставит хаб при каждом запуске, механизм по адаптерам описан в §4.

В пилот входят только основания: состояние активности (§9) и подписки хаба в контракте событий.

### 12.1. Инструменты оркестратора (после пилота, по решениям владельца 27.10 и 29.10)

Агент-оркестратор (сессия, которая ведёт план и делегирует задачи) получает в MCP-сервере canterlot ещё семь инструментов. Все семь выросли из реальных потерь времени при разработке самого canterlot.

1. **Аренда тяжёлых ресурсов.** `resource_lease(kind, scope)` / `resource_release`: ограниченное число слотов на машину для тяжёлых операций (полная сборка и прогон тестов, общая тестовая база), остальные встают в очередь с видимой позицией. Аренда привязана к сессии и снимается при её завершении или падении. Цель — убрать как класс флаки «под нагрузкой» и переполнение диска от параллельных сборок.
2. **Будильники.** `wake_me(at | on_event)`: запланированное durable-сообщение в собственную очередь по времени или по событию (сброс окна лимита провайдера, переход другой сессии в состояние). Тот же планировщик, что у отложенных сообщений и «кранча» (§5.3, §8); переживает перезапуск оркестратора.
3. **Маршрутизация по квотам.** `route_task(level)` возвращает, кому отдать задачу уровня `medium` / `high` / `xhigh` сейчас, по правилам владельца (вторичная подписка выжимается первой, основная — фолбэк) и текущим лимитам из §7, с объяснением выбора.
4. **Доска плана.** Задачи плана — объекты хаба: номер, название, состояние, исполнитель (сессия и модель), коммиты, ссылка на отчёт, находки ревью. Оркестратор обновляет их инструментом `plan_task_update`, владелец смотрит доску в PWA (экран «План»), статус не нужно собирать вручную.
5. **Сторож машины.** Активные предупреждения оркестратору (а не только экран владельцу) по метрикам §11: диск выше порога с указанием растущих каталогов в каталогах данных и рабочих каталогах, утёкшие процессы исполнений, память. Доставляются как события в очередь подписавшейся сессии.
6. **Поиск по истории.** Полнотекстовый поиск по своим сессиям, делегированным сессиям и их итогам (§12, «итог при завершении»), с фильтрами по сессии, времени и харнессу; результат — фрагменты со ссылкой на место в ленте. Индексируются тексты сообщений и блоков на хабе; в логи и метрики они по-прежнему не попадают.
7. **Автопинок без модели.** Хаб сам подталкивает исполнителя, чтобы дорогой оркестратор (Opus, GPT) не тратил запрос со всем своим контекстом на одно «продолжай». Правило задаётся на сессию инструментом `nudge_set` оркестратора или владельцем в PWA. Условие: сессия в `idle` после хода без маркера готовности дольше N минут, либо `stalled`; маркер — строка в финальном ответе (например, `STATUS: DONE`) или появление файла отчёта. Действие: durable-сообщение в очередь исполнителя с текстом из пресета инструкций (§4). Предел: K толчков подряд без признаков работы (новый ход с изменениями, коммит, рост файла отчёта), после чего хаб один раз будит оркестратора событием `nudge_exhausted` через подписку (§12). Маркер готовности, вопрос агента (`waiting_for_user`) и `failed` автопинок не трогает: это сигналы для оркестратора. По желанию к правилу подключается дешёвый сортировщик — пресет с дешёвой моделью (Haiku, локальная), который видит только последнее сообщение исполнителя и отвечает «работает / спрашивает / застрял / закончил»; без него действуют одни детерминированные правила. Переиспользует планировщик отложенных сообщений (§5.3) и состояния активности (§9).

### 12.2. Туду-лист агента (после пилота, по решению владельца 28.10)

Список задач агента виден в сессии живой панелью: пункты, состояние (ожидает / в работе / готово / отменено), прогресс; панель обновляется по мере работы и есть в ленте субагента. Владелец список не редактирует — это зеркало плана агента.

Источник — собственный список харнесса. Адаптер переводит его в общий факт `todo_updated`: полный список, не дельты.

- **Claude Code.** Источник — `tool_use_result.newTodos` в кадре `user`: он есть только после успешного `TodoWrite` и одинаков для основного агента и субагента, чьи вызовы приходят без потоковых кадров. Живой прогон CLI 2.1.311 показал, что моделям новее `claude-*-4-*` список не положен вообще: ни `TodoWrite`, ни `TaskCreate`/`TaskUpdate` нет в `system/init`. Поэтому воркер запускает CLI с `CLAUDE_CODE_ENABLE_TODO_TOOLS=true` и `CLAUDE_CODE_ENABLE_TASKS=false`: второе оставляет `TodoWrite` с полным списком вместо инкрементальных `Task*`. `TodoWrite` отложенный, модель сначала загружает его через `ToolSearch`.
- **Codex.** Источник — уведомление `turn/plan/updated` (инструмент `update_plan`), форма по схеме app-server 0.164.0; детский поток пишет в дорожку своего вызова. Живая проверка — в чек-листе смоука Codex.
- **OpenCode.** Инструмента нет без `experimental.todo`, поэтому слой конфигурации canterlot включает его всегда (решение владельца 31.10). Своего события нет: источник — `session.tool.success.metadata.todos` вызова `todowrite`. Есть статус `cancelled`, он проходит через proto, хаб и PWA: пункт виден словом и цветом, а прогресс его не считает.
- **Дорожка.** Основной агент и каждый субагент ведут отдельный список; ключ дорожки — блок вызова субагента (`lane_block_id`), как у маршрута его ленты. Список, которому нельзя назначить дорожку, отбрасывается с диагностикой `todo_lane_unknown`, а не попадает к основному агенту.
- **Ревизия.** На воркере это номер записи в журнале сопровождения: он растёт и переживает перезапуск сопровождения. Хаб отсекает устаревшее по паре (поколение, ревизия) и выдаёт клиенту свою ревизию дорожки, которая растёт с каждым принятым обновлением.
- **Размер.** Запись не больше 256 КиБ: до 256 пунктов, пункт до 4 КиБ с многоточием на обрезе, отброшенные считаются в `omitted`, и панель называет их число. Текст — данные уровня сообщения: в логи, `Debug` и диагностику не попадает.
- **Совместимость.** Новая запись журнала едет только при согласованной возможности `todo_v1`; без неё список отбрасывается с одной диагностикой `todo_dropped`, ход продолжается.
- **Панель.** Над очередью и в ленте субагента: компактная дорожка этапов, счёт, состояние словами и текущий пункт одной строкой, по касанию полный список. На телефоне свёрнута, на столе раскрыта; список прокручивается внутри и не выше 40 % экрана. Пустой список прячет панель; выполненный остаётся строкой «Все пункты выполнены» до следующего обновления. Активная точка движется только в идущем ходе; при `prefers-reduced-motion` состояния статичны.

Харнессам без своего списка (Gemini/Antigravity, pi и другие) MCP-сервер canterlot даст инструменты `todo_write` / `todo_read` с той же моделью данных, так что список будет выглядеть одинаково у всех агентов. Пока их нет: модель (`TodoStatus`, пункт `{text, status}`, дорожка, полный список с ревизией) от харнесса не зависит и места для них хватает.

Порядок после пилота: туду-лист агента (§12.2), межсессионные инструменты §12 → будильники, автопинок и маршрутизация (переиспользуют планировщик и лимиты) → аренда ресурсов и сторож машины → доска плана → поиск.

### 12.3. Как модели узнают, как работать с canterlot (решение владельца 29.10)

Подсказки даёт сам canterlot через свой MCP-сервер, а не набор навыков (skills): навыки у каждого харнесса свои или их нет, а MCP понимают все, и подсказка меняется вместе с кодом инструмента.

- Инструкции сервера: короткий блок (10–15 строк), который MCP-сервер отдаёт при подключении: что такое canterlot и главные правила (например, «не опрашивай чужую сессию — ты подписан, итог придёт сообщением»).
- Описания инструментов: что делает, когда вызывать, когда не надо.
- Ответы инструментов несут подсказку в нужный момент (`session_spawn` отвечает «сессия создана, ты подписан на завершение, итог придёт в твою очередь»).
- Пометки во входящих сообщениях: «от сессии X, модель Y», итог делегированной задачи, пересечение порогов лимита (§7).
- Политика владельца (порядок трат подписок, уровни усилия, кто кому делает ревью) не пересказывается моделям, а исполняется самим canterlot: `route_task` (§12.1) возвращает исполнителя с объяснением. Поведение модели (персона, стиль, язык) остаётся в пресетах инструкций (§4).
- Codex не передаёт модели `instructions` MCP-сервера (§15, вопрос 7): для моделей Codex тот же текст лежит в `AGENTS.md` каталога `CODEX_HOME` canterlot (все пресеты, кроме «Как у владельца»), а в пресете «Как у владельца» добавляется через `developerInstructions` в `thread/start`.
- OpenCode передаёт `instructions` MCP-сервера в системный промпт, отдельный файл не нужен; инструменты там называются с именем сервера (`canterlot_canterlot_limits`), поэтому у него свой текст.
- Навыки — только дополнение для длинных сценариев одного харнесса (например, «вести план с помощниками» в пресете оркестратора Claude Code), если инструментов с подсказками окажется мало.

В пилоте подсказка нужна только инструменту `canterlot_limits` (его описание); остальное — вместе с инструментами §12.

## 13. Визуальный стиль

Утверждён по макетам v2 (рабочие файлы вне репозитория).

- Мягкие формы: карточки, пузыри и блоки инструментов со скруглением около 20 px; кнопки, чипы, вкладки, поле ввода — «таблетки»; кнопка отправки и действие создания — круглые. Заголовок и поле ввода плавают с отступом от краёв. Почти без жёстких разделителей: слои отделяются оттенком поверхности и воздухом.
- Палитра тёмной темы (по умолчанию) — по теме Telegram владельца: фон `#183135`; поверхности `#1d383b`, `#1d4044`; выделение `#1f5457`; акцент `#00f4ee`; ссылки `#56fffc`; текст `#e5f3f4`; второстепенный текст `#77989a`. Светлая тема — в той же бирюзовой гамме с контрастом WCAG AA.
- Все значения — дизайн-токены (цвета, отступы, радиусы, шрифты, тени, длительности и кривые анимации); тема — набор значений токенов.
- Интерфейс только на русском. «canterlot» — просто название, без тематических отсылок. Без эмодзи и символов-галочек (✓, ✔, ✗ и подобных) нигде в интерфейсе (решение владельца 28.10): статусы — словами, цветом, формой и дорожкой этапов.
- Анимации плавные и короткие: появление текста, раскрытие блоков, смена состояний; уважение `prefers-reduced-motion`.
- Интерфейс динамичный, без перебора (пожелание владельца 28.10). Компонент «дорожка этапов» в духе трекера доставки: точки на линии, пройденные этапы залиты акцентом, по линии бежит заливка к активному этапу, активный пульсирует или крутится, ошибка — точка цвета ошибки с причиной. Применяется там, где у системы есть настоящие этапы: доставка сообщения (сохранено → на машине → передаётся → принято → агент работает), вложение (загрузка с кольцом прогресса → сохранено на хабе → на машине → готово агенту), запуск сессии (создаётся → сопровождение → CLI поднят → готов), остановка и прерывание (запрошено → отправлено агенту → процессы завершаются → остановлено), «кранч» (кольцо обратного отсчёта до сброса → проверка лимита → продолжение); после пилота — туду-лист агента и доска плана. Правила: анимируется только активный этап, пройденные статичны; движение отражает только реальные события хаба, никакого фейкового прогресса; длительности и кривые — токены; при `prefers-reduced-motion` — статичные состояния.
- Плавное появление текста ответа, как в Telegram (пожелание владельца 28.10): пришедший рывками текст складывается в буфер и проявляется ровным адаптивным темпом по словам — каждое слово возникает из прозрачности с лёгким размытием (около 180 мс). Отставание показа от пришедшего текста ограничено (не больше 0,6 с при обычной скорости, при отставании темп ускоряется); итоговый текст не меняется, анимируется только проявляющийся хвост, показанное и markdown не перерисовываются.
- Настройка «Скорость анимаций» (на устройстве): выкл · быстрее · обычно · медленнее — общий множитель 0 · 0,5 · 1 · 1,5 над всеми токенами длительностей (текст, дорожки этапов, раскрытие блоков, листы, переходы); «выкл» равносилен reduced-motion (текст сразу, дорожки статичны); системный reduced-motion главнее настройки.

8. Пресеты инструкций (план 2c): ещё не подтверждено вживую. Claude Code: действует ли `--system-prompt-snapshot off` на сессию, начатую с записью по умолчанию; кеш промпта при `off`; исчезают ли `CLAUDE.md` и автопамять из возобновлённого контекста после смены с «Как у владельца» на «Без инструкций»; завершает ли EOF stdin простаивающий CLI при фоновых задачах Bash (иначе нормой остаётся SIGTERM); подхватывается ли `AGENTS.md` репозитория без `CLAUDE.md`, если предковый `CLAUDE.md` исключён (приемлемо в любом случае: это файл самого репозитория). Codex: заменяет ли `thread/resume` с другими `developerInstructions` прежние или оставляет их в истории (от этого зависит примечание о смене); возобновление треда по идентификатору между `CODEX_HOME` владельца и canterlot и запасной путь по файлу треда (поле нестабильно); принимается ли пустой `developerInstructions`; работают ли два app-server на одном `CODEX_HOME` canterlot без зависания `account/read`; показывает ли `codex resume` владельца треды, созданные под `CODEX_HOME` canterlot; запрашивает ли Codex в режиме `ask` подтверждение для инструментов пресетов. Известно и не фильтруется: хуки плагинов владельца (например, SessionStart) добавляют свой текст и в «Без инструкций»; навыки остаются в списке.
9. OpenCode (план 2d): остаётся только то, что нельзя снять без настоящей модели. Настоящий ход на маршруте Go, настоящее тело `GoUsageLimitError` и `Retry-After`, запись кэша, первопричина отказа `invalid parameters`. Всё перечислено в чек-листе смоука; §5.3 и §5.4 отчёта этапа 0 закрыты живыми тестами L2 на заглушке провайдера.
