# Пилот: PWA, лимиты, «кранч» и сессии

Документ фиксирует состав пилота и поведение PWA, согласованные с владельцем 26.10.2026. Пилот — момент, когда владелец переносит ежедневную работу с HAPI на canterlot на одной машине. Это меньше первого эксплуатационного релиза (ТЗ §2.1): пилоту не нужна вся надёжность этапа 4, но в нём есть всё, без чего пришлось бы возвращаться в HAPI.

Документ дополняет `README.md`, `delivery.md`, `execution.md`, `streams.md` и `recovery.md`. Имена событий, состояний и причин в новом коде берутся отсюда; расхождения с остальными документами исправляются в документах, если имя уже записано в базу как вид события.

## 1. Состав пилота

Входит:

1. PWA для телефона и десктопа: список сессий, чат с потоковым ответом, блоки инструментов, ленты субагентов.
2. Оба адаптера: Claude Code и Codex (этап 2).
3. Режим разрешений наследуется из конфигурации владельца (решение OD-3 этапа 0); у владельца это bypass. Интерактивные вопросы агента (`AskUserQuestion`, Codex `requestUserInput`) обязательны.
4. Очередь, отмена непереданного ввода, прерывание, остановка, продолжение остановленного разговора (F-10).
5. Вложения любых файлов, включая «Поделиться» из Android.
6. Модель и агент у каждого ответа, включая субагентов; расход на ответ.
7. Лимиты подписок всегда на виду; режим «кранч».
8. Отложенные сообщения.
9. Смена модели, режима разрешений и усилия посреди сессии.
10. Профили инструкций при создании сессии.
11. Состояние машины: связь, CPU, память, диск, нагрузка.
12. Экспорт ответа в markdown и картинкой.
13. История расхода лимитов.

После пилота: туду-лист агента (§12.2), межсессионные инструменты для моделей (§12) и инструменты оркестратора (§12.1), push-уведомления, терминал, просмотр рабочих файлов, собственный вход вместо Authelia, cgroup v2 и восстановление R3/R4 (план 1.2c), другие харнессы (Antigravity, pi, opencode), переезд разработки canterlot в canterlot.

## 2. Размещение

- Хаб и PostgreSQL — в отдельном LXC Proxmox. Воркер — на рабочей VM владельца, systemd user service.
- PWA и API — один HTTPS-origin за Caddy на web-сервере; Caddy проверяет вход через Authelia и проксирует на хаб в LXC.
- Хаб доверяет заголовку пользователя только от адреса Caddy; прямой доступ к HTTP-порту хаба из других сетей закрыт. CSRF-защита изменяющих запросов и проверка Origin на WSS остаются обязательными (§15).
- Воркер ходит к хабу по gRPC с TLS от внутреннего УЦ; входящих портов на машине воркера нет.
- Восстановление из снимка: база хаба окажется «в прошлом» относительно журналов воркера. Сигнал уже есть — расхождение курсоров (`state_divergence`). Реакция проектируется на этапе 4 (R7); до тех пор воркер останавливается с явной причиной.
- Обновления: по образцу системы обновления meeting-pipeline. Обновление воркера не убивает идущие исполнения: процессы сопровождения переживают перезапуск управляющей службы (R2).

## 3. Сессии и их список

Сессия интерфейса — это разговор (conversation) хаба с его исполнениями.

Атрибуты, которые задаёт владелец: название (по умолчанию автозаголовок по первому сообщению), цвет-метка, закрепление, группы (свободные, сессия может быть в нескольких), архив. Группы и закрепление — данные хаба, синхронные между устройствами.

Список показывает: цвет, название, агент и модель, машину, состояние активности (§9) с кратким доказательством («выполняет `cargo test` · 4 мин», «ждёт ответа», «пауза: лимит»), непрочитанное. Сверху — плавающая полоса вкладок групп («Все», «Закреплённые», группы с счётчиками) и строка лимитов. Поиск по названиям входит в пилот (§12.1); полнотекстовый — после.

## 4. Создание сессии и профили инструкций

Поля: машина, рабочий каталог (только под разрешёнными корнями, §13), агент (Claude Code / Codex), модель, усилие, профиль инструкций, «кранч» и текст продолжения.

Профиль инструкций — именованный набор глобальных инструкций и настроек агента, хранящийся у воркера вне рабочих каталогов. Профиль «Как у владельца» (по умолчанию) — конфигурация владельца без изменений. Другие профили заменяют глобальные инструкции (`CLAUDE.md` пользователя, `AGENTS.md` Codex), например «исполнитель без персоны». Инструкции самого репозитория продолжают действовать.

Механизм подмены проверяется на этапе 2: для Claude Code — источники настроек (`--setting-sources`) либо отдельный каталог конфигурации (`CLAUDE_CONFIG_DIR`, с вопросом, как не терять авторизацию); для Codex — `CODEX_HOME` и переопределения `-c`.

Инвариант для рабочих проектов: canterlot ничего не создаёт и не меняет в репозитории и ничего не пушит. Вложения, профили, каталоги исполнений и будущие worktree для делегирования живут в каталоге данных воркера.

## 5. Чат

### 5.1. Лента

- Сообщение пользователя — тонированный пузырь с отметками «сохранено хабом» и «принято агентом» (§6.2, F-03).
- Ответ агента — карточка: шапка «агент · время · модель» и кнопка «инфо»; внутри текст, блоки инструментов и вызовы субагентов в порядке появления.
- Блок инструмента свёрнут в строку: имя, краткий аргумент, статус-таблетка, длительность. Раскрытый показывает хвост вывода во вдавленной области и «Показать полностью · N строк» (полное содержимое загружается отдельно, §12.2).
- Вызов субагента — отдельная строка с живым статусом («Субагент · Explore · haiku — читает поток»). Касание открывает ленту субагента (§6).
- Потоковый текст: дельты объединяются до 25 мс, видимая область обновляется не чаще кадра; markdown и подсветка не перерабатывают историю на каждый токен (§8.3).
- Автопрокрутка, только пока пользователь у нижней границы; чтение старого не сбивается новым токеном (§12.2).
- Под лентой — отдельно очередь («в очереди») и отложенные сообщения («отправится в 23:30»), не внутри общего индикатора.

### 5.2. Поле ввода

- На сенсорном вводе Enter — новая строка, отправка только кнопкой; поле с `enterkeyhint="enter"`. На десктопе Enter отправляет, Shift+Enter — перенос. Переключается в настройках.
- IME и вставка большого текста не отправляют сообщение.
- Экранная клавиатура не перекрывает поле: `interactive-widget=resizes-content` в Chrome Android.
- Кнопки: вложение, «Прервать» (пока идёт ход), отправка. Долгое нажатие на отправку — «Отправить позже» (выбор времени).
- Черновик хранится на устройстве по сессии (§12.2, §12.3).

### 5.3. Отложенные сообщения

Отложенное сообщение — ввод хаба со временем выдачи. До наступления времени оно видно в списке под лентой, его можно изменить или отменить. В момент наступления оно ставится в обычную очередь разговора. Планировщик тот же, что будит сессии в «кранче» (§8).

### 5.4. Смена настроек посреди сессии

Модель, режим разрешений и усилие меняются командой в очереди; применяются со следующего хода и видны в шапке. Механизм: Claude Code — управляющие запросы stream-json (`set_model`, `set_permission_mode`), Codex — переопределения в `turn/start`. Точный набор проверяется на этапе 2; недоступная агенту настройка не показывается или объясняет причину.

### 5.5. Вопросы и разрешения

- Вопрос агента — карточка: текст, 2–4 варианта с описаниями (одиночный или множественный выбор), «свой ответ», если агент его допускает (§11).
- Разрешение (если всё-таки пришло, например в сессии не в bypass) — компактная карточка «Разрешить / Отклонить» с точными аргументами.
- Первое зафиксированное решение единственное; другие устройства видят итог. Отдельно показываются «решение сохранено» и «агент применил решение».

### 5.6. «Инфо» об ответе и экспорт

Нижний лист «инфо» показывает по частям ответа: агента (основной или субагент), модель, токены (вход, выход, кэш), длительность, расход лимита «≈ 0,4 % недели» (§7). Действия: «Копировать как markdown», «Копировать картинкой» — ответ отрисовывается в изображение в браузере; на телефоне отдаётся в «Поделиться», на десктопе — в буфер обмена.

### 5.7. Картинки, на которые смотрел агент

Если агент открыл изображение (Claude Code: `Read` картинки; Codex: просмотр изображения), блок инструмента показывает саму картинку, а не только путь: миниатюру прямо в строке инструмента, по касанию — полноэкранный просмотр с масштабированием. То же для картинок, которые агент получил как вложение.

- Источник байтов: то, что агент действительно получил (содержимое результата инструмента, если адаптер его отдаёт), иначе — чтение файла по пути из вызова инструмента воркером сразу в момент события (позднее изменение файла не подменяет увиденное).
- Путь: воркер публикует картинку на хаб отдельным потоком канала данных (как вложения, в обратную сторону: надёжная публикация на хабе → только потом запись `block_media` в журнал сопровождения со ссылкой); пока картинка не опубликована, блок показывает заглушку «картинка загружается», при сбое — «картинка недоступна» с причиной.
- Ограничения: только изображения (png, jpeg, webp, gif), до 20 МиБ на картинку; крупнее — показывается путь и размер без миниатюры. Миниатюра строится в браузере.
- Хранение — пока жива сессия, как у вложений. В логи и метрики байты и пути не попадают.
- Точный формат результата чтения картинки у обоих CLI проверяется на этапе 2; синтетический адаптер получает шаг «посмотреть картинку» для тестов до этого.

## 6. Субагенты и модели

Работа субагента показывается не хуже основного чата: та же лента, тот же отрисовщик, тот же живой поток. Шапка ленты субагента — путь в дереве («оркестратор → субагент»).

Данные:

- блок ответа получает поля `agent` (основной или имя субагента), `model` и ссылку на вызов, породивший субагента (`parent_block_id` уже есть);
- итог хода (`run_finished`) получает расход по моделям;
- Claude Code: модель в каждом сообщении ассистента, сообщения субагента помечены `parent_tool_use_id`, итог хода содержит разбивку по моделям;
- Codex: модель известна на старте треда и хода; что app-server отдаёт про субагентов, проверяется на этапе 2.

На десктопе правая панель показывает дерево делегирования сессии (кто кого запустил, с состояниями) и выбранную ленту субагента.

## 7. Лимиты и расход

Источники (тот же механизм, что `agent-limits` владельца):

- Claude Code сам присылает `rate_limit_event` с загрузкой пятичасового и недельного окон и временем сброса — воркер берёт значения из потоков живых сессий бесплатно;
- Codex отдаёт лимиты через `account/rateLimits/read` app-server без запроса к модели;
- когда живых сессий нет, воркер опрашивает редко (Claude — дешёвым запросом, не чаще раза в 30 минут; Codex — каждые 5 минут).

Хаб хранит снимки лимитов по провайдеру и времени: строка лимитов в чате и списке, график по дням (экран истории лимитов) с разбивкой по сессиям и моделям.

Расход на ответ: токены точные (из итога хода); доля лимита — оценка «≈» как разница загрузки до и после хода. Лимит общий для всех сессий и устройств подписки, проценты целые, поэтому при параллельной работе разделить расход нельзя — это показывается честно, без ложной точности.

Модели знают остаток:

- инструмент `canterlot_limits` в MCP-сервере canterlot (воркер уже поднимает MCP-сервер для Claude Code);
- короткая системная пометка во входящем сообщении только при пересечении порогов 80 / 90 / 95 % недели.

## 8. «Кранч» и паузы по лимитам

«Кранч» включается на сессию. Правила (решения владельца):

- **Пятичасовое окно.** Заранее не останавливаться. Если CLI вернул ошибку лимита со временем сброса (факт адаптера), разговор получает паузу `quota_exhausted` с временем пробуждения. После сброса окна (проверяется по лимитам, а не только по часам) харнесс снимает паузу и отправляет в тот же разговор агента текст продолжения.
- **Недельное окно, 95 %.** Хаб перестаёт начинать новые ходы у сессий этого провайдера: не выдаёт сообщения из очереди и не шлёт автопродолжение; пауза `weekly_reserve`. Идущий ход не прерывается. Остальные 5 % — резерв владельца: в любой сессии есть действие «Продолжить, тратя резерв» (ручное продолжение этой сессии). Автоматика в резерв не заходит. После сброса недели паузы `weekly_reserve` снимаются автоматически.
- Лимиты Claude и Codex независимы.
- После сброса сразу будятся все сессии в «кранче», которые остановил лимит (а не по очереди). Сессии, которые к этому моменту просто стояли без работы, текста продолжения не получают; если в очереди уже есть сообщение владельца, продолжением становится оно.
- Текст продолжения: по умолчанию «Лимиты восстановлены, продолжай с того места, где остановился.», меняется на сессию.
- Без «кранча» сессия при упоре в лимит останавливается с явной причиной и временем сброса.

Паузы `quota_exhausted` и `weekly_reserve` — причины удержания очереди хаба (`delivery.md` §3); пробуждение — плановая команда того же планировщика, что у отложенных сообщений. Всё проверяется синтетическим адаптером со сценарием «упёрлись в лимит со временем сброса» (§10.6) до подключения настоящих агентов.

## 9. Состояние активности сессии

Одно вычисляемое хабом состояние с доказательствами — для списка, шапки чата (F-11) и будущих межсессионных инструментов:

| Состояние | Условие | Доказательства |
| --- | --- | --- |
| `idle` | хода нет, очередь пуста, нет открытых вопросов, фоновая работа агента завершена | время последнего хода |
| `working` | ход идёт, события поступают | фаза (`generating`, `running_tool` + имя инструмента), длительность |
| `waiting_for_user` | открыт вопрос или запрос разрешения | текст вопроса кратко |
| `stalled` | ход идёт, событий нет дольше порога | последнее событие, фаза, жив ли процесс, CPU |
| `quota_paused` | пауза по лимиту | провайдер, окно, время пробуждения |
| `failed` | процесс умер, владелец потерян, ошибка, исчерпан контекст | причина (`owner_lost`, `context_exhausted`, …) |
| `stopped` | исполнение остановлено | исход |

Порог `stalled`: в фазе генерации 5 минут, в фазе инструмента 30 минут; оба настраиваются. `stalled` — подозрение с доказательствами, а не действие: сессия не прерывается автоматически.

Заполнение контекста (токены контекста, события сжатия) показывается в «инфо»; исчерпание — явное `failed: context_exhausted`, а не тишина.

## 10. Вложения

- Любые файлы до 100 МиБ, до 10 на ввод; лимиты объявляются браузеру, хабу и воркеру одинаково (§13).
- Путь: загрузка на хаб с ID и checksum → надёжная публикация в хранилище хаба → метаданные в PostgreSQL (§13.1) → передача воркеру потоком по каналу данных (не блокирует управление) → надёжная публикация в каталоге вложений исполнения в каталоге данных воркера → ввод выдаётся агенту только после готовности всех вложений.
- Агенту передаётся путь к файлу и описание; изображение вдобавок — нативным блоком (Claude Code: base64-блок `image`, Codex: `localImage` по пути).
- Android: установленное PWA — цель «Поделиться» (Web Share Target): файл из галереи или любого приложения попадает в выбранную сессию как вложение черновика.
- Хранение: пока жива сессия; при удалении сессии — вместе с ней.

## 11. Состояние машины

Экран машины: связь (последний heartbeat, `available` / `degraded` / `unavailable`), CPU, память, диск, нагрузка, сессии на машине. Воркер отдаёт метрики каждые 30 секунд по управляющему каналу; порог предупреждения по диску — 85 %. Содержимое чатов в метрики не попадает (§17).

## 12. Межсессионная работа (после пилота, закладывается сейчас)

Цель: сильная модель (Opus, GPT) делегирует работу сессии другого харнесса и получает надёжный сигнал о её завершении.

Инструменты MCP-сервера canterlot:

- `sessions_list`, `session_inspect` — состояние (§9) с доказательствами, последние сообщения и блоки, ресурсы процессов;
- `session_send` — сообщение в очередь другой сессии с пометкой «от сессии X, модель Y» и дедупликацией;
- `session_spawn` — новая сессия выбранного харнесса и модели, по желанию в изолированном worktree вне репозитория, с брифом и подпиской на завершение; после приёма результата worktree и процессы убираются;
- подписка на смену состояния — основной способ ожидания: подписку хранит хаб, при переходе в `idle` / `waiting_for_user` / `stalled` / `failed` событие ложится в очередь подписавшейся сессии как durable-команда; переживает перезапуск оркестратора; блокирующий `session_wait` с таймаутом — вспомогательный;
- итог при завершении: состояние, финальный ответ (усечённый), коммиты за ход (HEAD до и после), изменённые файлы, расход, длительность;
- защита от зацикливания: лимит частоты и глубины цепочки сообщений.

В пилот входят только основания: состояние активности (§9) и подписки хаба в контракте событий.

### 12.1. Инструменты оркестратора (после пилота, по решению владельца 27.10)

Агент-оркестратор (сессия, которая ведёт план и делегирует задачи) получает в MCP-сервере canterlot ещё шесть инструментов. Все шесть выросли из реальных потерь времени при разработке самого canterlot.

1. **Аренда тяжёлых ресурсов.** `resource_lease(kind, scope)` / `resource_release`: ограниченное число слотов на машину для тяжёлых операций (полная сборка и прогон тестов, общая тестовая база), остальные встают в очередь с видимой позицией. Аренда привязана к сессии и снимается при её завершении или падении. Цель — убрать как класс флаки «под нагрузкой» и переполнение диска от параллельных сборок.
2. **Будильники.** `wake_me(at | on_event)`: запланированное durable-сообщение в собственную очередь по времени или по событию (сброс окна лимита провайдера, переход другой сессии в состояние). Тот же планировщик, что у отложенных сообщений и «кранча» (§5.3, §8); переживает перезапуск оркестратора.
3. **Маршрутизация по квотам.** `route_task(level)` возвращает, кому отдать задачу уровня `medium` / `high` / `xhigh` сейчас, по правилам владельца (вторичная подписка выжимается первой, основная — фолбэк) и текущим лимитам из §7, с объяснением выбора.
4. **Доска плана.** Задачи плана — объекты хаба: номер, название, состояние, исполнитель (сессия и модель), коммиты, ссылка на отчёт, находки ревью. Оркестратор обновляет их инструментом `plan_task_update`, владелец смотрит доску в PWA (экран «План»), статус не нужно собирать вручную.
5. **Сторож машины.** Активные предупреждения оркестратору (а не только экран владельцу) по метрикам §11: диск выше порога с указанием растущих каталогов в каталогах данных и рабочих каталогах, утёкшие процессы исполнений, память. Доставляются как события в очередь подписавшейся сессии.
6. **Поиск по истории.** Полнотекстовый поиск по своим сессиям, делегированным сессиям и их итогам (§12, «итог при завершении»), с фильтрами по сессии, времени и харнессу; результат — фрагменты со ссылкой на место в ленте. Индексируются тексты сообщений и блоков на хабе; в логи и метрики они по-прежнему не попадают.

### 12.2. Туду-лист агента (после пилота, по решению владельца 28.10)

Список задач агента виден в сессии живой панелью: пункты, состояние (ожидает / в работе / готово), прогресс; панель обновляется по мере работы и есть в ленте субагента. Источник — собственный список харнесса: Claude Code `TodoWrite`, Codex — план хода (`update_plan`); адаптер переводит его в общий факт `todo_updated` (полный список с ревизией, не дельты). Харнессам без своего списка (Gemini/Antigravity, pi и другие) MCP-сервер canterlot даёт инструменты `todo_write` / `todo_read` с той же моделью данных, так что список выглядит одинаково у всех агентов. Владелец список не редактирует — это зеркало плана агента.

Порядок после пилота: туду-лист агента (§12.2), межсессионные инструменты §12 → будильники и маршрутизация (переиспользуют планировщик и лимиты) → аренда ресурсов и сторож машины → доска плана → поиск.

## 13. Визуальный стиль

Утверждён по макетам v2 (рабочие файлы вне репозитория).

- Мягкие формы: карточки, пузыри и блоки инструментов со скруглением около 20 px; кнопки, чипы, вкладки, поле ввода — «таблетки»; кнопка отправки и действие создания — круглые. Заголовок и поле ввода плавают с отступом от краёв. Почти без жёстких разделителей: слои отделяются оттенком поверхности и воздухом.
- Палитра тёмной темы (по умолчанию) — по теме Telegram владельца: фон `#183135`; поверхности `#1d383b`, `#1d4044`; выделение `#1f5457`; акцент `#00f4ee`; ссылки `#56fffc`; текст `#e5f3f4`; второстепенный текст `#77989a`. Светлая тема — в той же бирюзовой гамме с контрастом WCAG AA.
- Все значения — дизайн-токены (цвета, отступы, радиусы, шрифты, тени, длительности и кривые анимации); тема — набор значений токенов.
- Интерфейс только на русском. «canterlot» — просто название, без тематических отсылок. Без эмодзи в элементах интерфейса.
- Анимации плавные и короткие: появление текста, раскрытие блоков, смена состояний; уважение `prefers-reduced-motion`.
