# Раннеры как машины: носитель и `hub_dial`

Сторона воркера этапа B1 (`runners_v1`). Раннер, то есть второй хост для тяжёлых задач, — обычная машина хаба с воркером 1.44; отдельного конвейера задач нет. Соединение раннера с хабом идёт внутри SSH, который открывает не хаб и не раннер, а воркер VM, **носитель**. Входящих соединений в домашнюю сеть не бывает. Хабовая часть (роль `runner`, флаг носителя, доступность, отказы) описана отдельно; здесь только то, что делает воркер.

Имена: **носитель** (carrier) — воркер VM, помеченный в хабе `machine set-carrier`; **раннер** — машина с `role = 'runner'`, чей родитель носитель; **корень** (root) — каталог раннера, его присылает хаб.

## 1. `hub_dial`

`[worker].hub_dial = "unix:<абсолютный путь>"` (необязателен). Воркер строит `tonic::transport::Endpoint` из `hub_url`, как всегда, и подключает его через `connect_with_connector` с соединителем на `UnixStream`. Адрес в URI остаётся только для TLS: имя сервера в `ClientHello` и проверка SAN берутся из `hub_url`, куда бы ни вёл сокет. Все три соединения воркера (управляющее, данных и ленивое для вложений) идут через сокет. Неверный `hub_dial` (не `unix:`, относительный путь, `..`) — ошибка конфигурации при чтении файла и `InvalidConfig` при подключении.

Проверки: сертификат хаба на `localhost` принимается, когда `hub_url` называет `localhost`, а порт никто не слушает; тот же сокет с `hub_url`, называющим другое имя, не доходит до `Hello` (`tests/it/hub_dial.rs`).

## 2. Смертельный выход: `<data_dir>/fatal`

Воркер раннера живёт без службы и без человека рядом, поэтому перед выходом по неисправимой причине он пишет `<data_dir>/fatal` с одним словом (запись атомарна: временный файл и переименование). Обычный запуск файл удаляет сразу после того, как конфиг прочитан, токен найден, а хранилище открыто.

| Слово | Когда | Что делает носитель |
| --- | --- | --- |
| `unauthenticated` | хаб ответил `Unauthenticated` или отказал без повтора (`Rejected{retryable:false}`) | новый токен, `reset_local_state = false` |
| `restore_generation` | поколение восстановления изменилось, не совпало с сохранённым или курсоры журналов разошлись | новый токен, `reset_local_state = true`, каталог `state/` сносится |
| `config` | конфигурация не читается или негодна | переписывает `worker.toml`, токен не запрашивает |

Любое другое слово лечится как `unauthenticated`. Сбой чтения диска или прав токена не смертелен: воркер сам повторяет чтение, а на исходе повторов выходит без слова, и носитель просто запускает его снова. Если сам файл конфигурации не разобрался, каталог данных берётся из сырого TOML (`data_dir`), чтобы слово всё равно легло на место.

## 3. Носитель

Модуль `carrier`: [`run(settings, control, assigned, shutdown)`]. Он действует только для раннеров, названных и в `[[runners.ssh]]`, и в `RunnersAssigned` хаба (по имени машины); корень из хаба проходит `valid_root` (абсолютный, нормализованный, не длиннее 90 знаков, только `[A-Za-z0-9/._+@-]`, как у хаба), иначе раннер пропускается с предупреждением. Смена корня или записи конфига — это уход старого раннера и приход нового.

Обмен с хабом спрятан за трейтом `RunnerControl` (`request_token`, `report_observation`), список раннеров приходит каналом `watch`. Так носитель проверяется без хаба. Боевая реализация — `carrier::bridge::ControlBridge`, мост к потоку управления воркера:

- **Возможность.** Воркер объявляет `runners_v1` только с `[[runners.ssh]]`; мост принимает запросы лишь на соединении, где она согласована (иначе хаб закрыл бы поток отказом `capability_missing`). Вне такого соединения `request_token` отвечает «недоступно», наблюдения отбрасываются, а носитель спрашивает снова по своей паузе.
- **`RunnersAssigned`** (хаб шлёт при подключении и при каждом изменении списка детей) заменяет прежний список целиком: раннеры, которых в нём больше нет, останавливаются (воркер, затем проброс). Повторный равный список тоже будит носитель.
- **`RunnerTokenRequest`** уходит с `machine_id` и `reset_local_state`, ответ `RunnerToken` сопоставляется по `machine_id`. Токен проходит через мост одним сообщением: в очереди исходящих, журнале и `Debug` его нет (в `Debug` прото-сообщения только размер).
- **`RunnerTokenRefused`** (`not_carrier`, `not_parent`, `revoked`, `unknown_machine`) останавливает оба цикла этого раннера (проброс и присмотр) с предупреждением, где только идентификаторы; воркер раннера остаётся как есть. Раннер запускается заново со следующим `RunnersAssigned`, то есть не позже следующего подключения.
- **`RunnerObservation.observed_at`** — миллисекунды Unix по часам носителя.
- Очередь исходящих сообщений при новом соединении очищается: просьба прошлого соединения без ответа не повторяется.

На раннер приходятся две независимые задачи.

### 3.1 Проброс

Один присматриваемый `ssh` на раннер:

```
ssh -F <ssh_config, если задан> -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
    -N -o ExitOnForwardFailure=yes -R <корень>/hub.sock:<хост gRPC хаба>:<порт> <псевдоним>
```

Хост и порт берутся из собственного `hub_url` носителя (по умолчанию порт 443). Перед каждым пробросом отдельные вызовы `ssh <псевдоним> mkdir -p -- <корень>` и `ssh <псевдоним> rm -f -- <корень>/hub.sock` убирают старый сокет. Проброс считается поднятым, если процесс прожил `tunnel_settle` (2 с); дальше он следит за выходом процесса. При обрыве перезапуск идёт с экспоненциальной паузой от 1 до 60 с; проброс, державшийся 30 с и дольше, поднимается снова без накопленной паузы. Воркер раннера в это время сам переподключается с обычным backoff, а его задачи продолжают работать.

### 3.2 Присмотр

Раз в `liveness` (30 с) носитель делает круг по SSH. Всё идёт через `sh -s` со скриптом в stdin: корень вставляется буквально и проверен заранее, кавычек оболочки входа нет.

1. **Каталоги.** Идемпотентно создаются `bin`, `jobs/personal`, `jobs/work`, `repos/personal`, `repos/work`, `state` (права 0700: без них хранилище воркера отказывает).
2. **Зонд.** Один скрипт печатает `root`, `token`, `store`, `toml`, `fatal`, `alive` и хэш `ca.pem`. После подъёма проброса и при первом круге зонд полный: добавляются `sha256` и `--version` бинарника.
3. **Бинарник.** Если хэш бинарника на раннере или его версия не совпадают с собственным бинарником носителя (`std::env::current_exe`, версия из `--version`), носитель загружает его в `bin/canterlot-worker.new` через stdin (`cat > … && echo "<sha256>  …" | sha256sum -c - && chmod 755 … && mv -f`), переименовывает и перезапускает воркер раннера. Сверка хэша на раннере обязательна: оборванная отправка (истёк `upload_limit`, носитель перезапустился при выкатке) кончается для удалённого `cat` обычным концом файла, и без неё обрубок встал бы на место рабочего бинарника. При расхождении старый бинарник не тронут, код выхода не ноль. Признак «нужна полная сверка» сбрасывается только после успешных шагов бинарника и `ca.pem`, поэтому следующий круг присмотра (раз в `liveness`), а не переподключение туннеля, сверяет хэш заново. Выполняющиеся задачи не ждутся: их оболочки живут отдельными сеансами и после перезапуска воркер переподхватывает их. `ca.pem` копируется из `ca_cert` носителя тем же способом.
4. **Токен.** Он запрашивается, если файла `token` или `worker.toml` нет либо стоит слово из `fatal` (кроме `config`). `reset_local_state` — истина, когда каталога состояния ещё нет (`state/cj` отсутствует) или слово `restore_generation`; тогда воркер останавливается и `state/` сносится. Токен кладётся одной командой `ssh <псевдоним> 'umask 077; cat > <корень>/token.new && mv <корень>/token.new <корень>/token'` через stdin: значение не попадает ни на диск носителя, ни в журнал, ни в `Debug` (`SecretToken` печатается как `SecretToken(..)`, не клонируется). Если ответ хаба потерялся, носитель спросит снова, и хаб ротирует токен ещё раз.
5. **Конфиг.** Идентификаторы машины приходят в том же `RunnerToken` и записываются в `worker.toml` (см. §3.3). Дальше носитель читает лежащий `worker.toml`, берёт из него идентификаторы и сверяет остальное с тем, что сгенерировал бы сейчас; расхождение (другой `hub_url`, `max_running`, `lease_slots`) переписывается с перезапуском. Слово `config` переписывает файл так же и затем убирает `fatal`. Если идентификаторы из файла не прочесть, файл убирается, и со следующего круга запрос токена.
6. **Запуск.** Воркер, которого нет, запускается:
   ```
   cd <корень> && setsid sh -c '<пишет «pid время-старта» в state/worker.pid>; exec bin/canterlot-worker run --config worker.toml >> state/worker.log 2>&1 < /dev/null' &
   ```
   pid пишет сам процесс (после `exec` pid и время старта не меняются), а скрипт ждёт появления файла: следующий зонд не примет ещё не записанный pid за смерть. Живость — это `/proc/<pid>/stat` с тем же временем старта и состоянием не `Z`: чужой процесс с переиспользованным pid воркером не считается. Журнал `state/worker.log` при размере больше 5 МиБ сдвигается в `.1`. Ничего вне корня не ставится.
7. **Снятие.** Когда раннер уходит из конфигурации или назначения хаба, носитель убивает проброс и останавливает воркер раннера (`SIGTERM`, через 10 с `SIGKILL`; задачи на месте это не трогает). Выход самого носителя гасит только проброс: воркеры раннеров и их задачи остаются.

Защита от петли: запросы токена к одному раннеру идут не чаще чем раз в `token_retry_min` (30 с), пауза удваивается до `token_retry_max` (10 мин) и сбрасывается, когда воркер прожил два круга подряд без слова `fatal`. Недоступность хаба ждёт той же паузы, а отказ хаба (`not_carrier`, `not_parent`, `revoked`, `unknown_machine`) останавливает раннер до следующего списка (см. §3).

### 3.3 Сгенерированный `worker.toml`

Правок вручную нет: носитель перезаписывает файл при любом расхождении.

```toml
hub_url = "<hub_url носителя>"
hub_dial = "unix:<корень>/hub.sock"
ca_cert = "<корень>/ca.pem"
token_file = "<корень>/token"
machine_id = "…"            # из RunnerToken
installation_id = "…"
restore_generation = "…"
data_dir = "<корень>/state"

[execution]
allowed_workdir_roots = ["<корень>/jobs"]

[memory]
work_roots = ["<корень>/jobs/work"]

[jobs]
max_running = <из [[runners.ssh]]>

[machine]
lease_slots = <из [[runners.ssh]]>
```

Таблиц харнессов нет: на раннере не запускаются сессии, только задачи на месте.

### 3.4 Наблюдения достижимости

После каждой попытки SSH (подъём проброса, любой вызов круга присмотра) носитель отправляет `Observation { machine_id, reachable, consecutive_failures, observed_at }`: связь потеряна — `ssh` не запустился, вышел с 255 или не уложился в срок; удачной считается любая попытка, дошедшая до раннера, даже если команда ответила отказом. Раз в минуту (`observe_every`) носитель повторяет последний итог, даже когда попыток не было: хабу нужны свежие наблюдения, чтобы объявить раннер `offline` (три неудачи подряд, наблюдению меньше трёх минут).

## 4. Исходники и результаты задач (стадия B2)

Носитель, кроме присмотра за раннерами, выполняет три команды хаба. Модуль `carrier::stage` (`Stager`: `stage`, `cleanup`, а `collect` в `carrier::collect`) не знает про хаб: принимает запрос и отвечает `Ok` или `Failure { reason, message }` (короткая машинная причина и одна строка). Сообщения хаба превращаются в запросы мостом, а раннер по идентификатору машины находится по списку `RunnersAssigned` и записи `[[runners.ssh]]` (`Targets`).

Хаб повторяет эти команды после рестарта воркера (они идут через долговечную очередь), поэтому каждая безопасна при повторе.

**Команды и факты (`carrier::commands`, `CarrierCommands`).** Команды хаба `StageSource`, `CollectOutputs`, `CleanupSource` и `OwnerJobFinished` (`Command` 25–28) идут тем же долговечным путём, что остальные команды машины: воркер сохраняет их до исполнения, ставит в маршрут исполнений (`Executions::route`), а после рестарта и на каждом новом соединении доигрывает непогашенные. Ответ — факт журнала, который гасит команду вместе с записью (`RecordBody` 53–57):

| Команда | Факт при успехе | Факт при отказе |
| --- | --- | --- |
| `StageSource` | `SourceStaged` | `SourceStageFailed { reason }`, где `reason` — `<код>: <строка>` |
| `CollectOutputs` | `OutputsCollected { local_dir, files, truncated }` | `OutputsCollectFailed { reason }` |
| `CleanupSource` | `SourceCleaned` | нет факта: команда гасится, хаб повторит уборку сам (до 5 раз) |
| `OwnerJobFinished` | итог записан в `owner-jobs/`, команда гасится | запись на диск не удалась: команда остаётся и доиграется |

Хаб заканчивает задачу по `OutputsCollected`/`OutputsCollectFailed` (или сразу, если собирать нечего), а `CleanupSource` выдаёт после конца: итог, сообщение и ждущий вызов очистку не ждут, сбой очистки только повторяет её. Если `SourceStaged` приходит для уже законченной задачи (отмена застала подготовку на ходу), хаб заново выдаёт очистку: прежняя могла отработать до того, как появились checkout и ссылка.

Команды идут только на соединении с согласованной `runners_v1`. Пока она не согласована, команда остаётся непогашенной (а не отклоняется), факты 53–57 удерживаются в журнале на месте (как факты задач на месте без `jobs_inplace_v1`), и всё уходит на первом согласованном соединении. Долгие команды (`StageSource`, `CollectOutputs`, `CleanupSource`) выполняются отдельной задачей, чтобы не держать маршрут; повторная доставка той же команды, пока она идёт, второй раз не запускается. Если факт не записался, команда остаётся непогашенной и повторяется: работа идемпотентна. `OutputsCollected` не несёт списков отсутствующих и пропущенных путей: если они есть или предел сработал, рядом с результатами лежит `COLLECT-NOTES.txt` (`truncated`, `missing: <путь>`, `skipped (not a regular file): <путь>`).

Носитель включается только с `[[runners.ssh]]`: возможность `runners_v1` объявляется лишь тогда, поэтому и `job run` с командами носителя работает только на воркере, у которого есть хотя бы один такой раннер в конфиге.

**Проверка до того, как строится хоть одна строка оболочки.** Скрипты идут в `sh -s` через stdin ssh, проверенные значения вставляются буквально: `job_id` — UUID в каноническом виде; `rev` — ровно 40 шестнадцатеричных знаков; `domain` — `personal` или `work`; `repo_key` — `[A-Za-z0-9._-]+`, не `.` и не `..`; корень раннера проходит `valid_root` и должен совпасть с корнем, который носитель знает для этой машины; `workdir` при цели-раннере равен `<root>/jobs/<domain>/<job_id>`, при цели-носителе `<родитель repo>/.canterlot-jobs/<имя repo>/<job_id>`; `repo` абсолютный, без `..`, равен своему каноническому виду (ни ссылок в пути, ни лишних слэшей) и лежит внутри `[execution].allowed_workdir_roots`, иначе `bad_repo` до любого вызова git и ssh: хаб относит задачу к домену по тексту пути, и ссылка из личного каталога на рабочий репозиторий иначе перенесла бы его содержимое через границу доменов (та же проверка, что у рабочего каталога обычной задачи). Пути результатов — относительные, без `..`, из знаков `[A-Za-z0-9._/+@-]`, не начинаются с `-`, не больше 64 на команду. Отказ — `bad_rev`, `bad_job_id`, `bad_domain`, `bad_repo_key`, `bad_repo`, `bad_root`, `bad_workdir`, `bad_path`, `bad_machine_id`, `unknown_target`.

**`StageSource`.** Цель-раннер (корень не пуст):

1. По SSH: каталоги `<root>/repos/<domain>`, `<root>/jobs/<domain>`; если рабочая копия уже на этом sha, ответ сразу «готово»; иначе `git init --bare` для `<root>/repos/<domain>/<repo_key>.git`, если его нет.
2. `git -C <repo> push --no-verify <alias>:<bare> <rev>:refs/canterlot/<job_id>` с `GIT_SSH_COMMAND`, собранным из того же `ssh_config`, что и остальные вызовы носителя (`BatchMode=yes`). Прежде носитель проверяет, что коммит есть в репозитории: `unknown_rev`, `not_a_repo`.
3. По SSH: `git worktree prune`, остаток прерванного создания (рабочая копия не на том sha или пустой каталог) снимается `git worktree remove --force` и `rmdir`, затем `git worktree add --detach <workdir> refs/canterlot/<job_id>` и проверка `HEAD`. Каталог, который так не освободился, — `workdir_busy`.

Цель-носитель (корень пуст): `git -C <repo> worktree add --detach <workdir> <rev>` локально, каталог `.canterlot-jobs/<имя repo>` создаётся при нужде, остаток прерванного создания убирается так же. Домен рабочей копии совпадает с доменом репозитория по пути: она лежит рядом с ним. Повтор на готовой копии на нужном sha — успех, без обращения к репозиторию. Причины отказа: `ssh_unreachable`, `push_failed`, `push_timeout`, `worktree_failed`, `wrong_rev`, `mkdir_failed`, `git_missing`, `init_failed`, `script_failed`.

**`CollectOutputs`.** Каждый путь копируется из рабочей копии в `<data_dir>/job-outputs/<job_id>/` (каталог 0700). Только обычные файлы и каталоги:

- путь, в котором на любом шаге есть символьная ссылка, пропускается целиком (попадает в `skipped`), `find -type f` не заходит в ссылки и не показывает особые файлы, `rsync` идёт с `--no-links --no-specials --no-devices`; на самом носителе обход ведётся по `lstat`, а файл открывается с `O_NOFOLLOW`;
- общий предел `cap_bytes` измеряется до копирования (`find -printf '%s'` по SSH): файлы идут по порядку путей, пока сумма влезает, первый не поместившийся обрывает отбор, итог помечается `truncated`; `rsync` идёт ещё и с `--max-size=<cap_bytes>`, поэтому файл, выросший между измерением и копированием (задача с таймаутом, чей контейнер пережил её), не перетянет предел, а будет пропущен;
- отсутствующий путь не ошибка, он попадает в `missing`;
- имя с управляющими знаками или не-UTF-8 не копируется.

Ответ: `local_dir`, `files [{path, bytes}]` (размеры по факту на диске носителя), `truncated`, а также `missing` и `skipped` для пометки в итоге задачи. Нужен `rsync` на раннере и на носителе, иначе `rsync_missing`. Повтор перезаписывает файлы.

**`CleanupSource`.** Цель-раннер: `git -C <bare> worktree remove --force <workdir>`, `worktree prune`, `update-ref -d refs/canterlot/<job_id>`, затем `rmdir` для пустого остатка. Если в bare-репозитории не осталось ни одной `refs/canterlot/*` (рядом нет других задач того же репозитория), на раннере идёт `git gc --prune=now --quiet` (по возможности: сбой на ответ не влияет), чтобы исходники законченных задач не копились; пока живёт соседняя задача, сборка не запускается, иначе `--prune=now` мог бы съесть объекты чужой отправки, которая ещё не успела получить ссылку. Цель-носитель: репозиторий находится по рабочей копии (`rev-parse --git-common-dir`), без поля `repo` в команде. Никакого `rm -rf`. Рабочая копия, пережившая удаление, остаётся на месте, а команда отвечает `workdir_remains`: хаб логирует это и повторяет уборку, пока не исчерпает предел. Ссылки и рабочие копии других задач не трогаются; второй вызов безвреден.

**Уборка результатов.** Раз в час и при запуске воркер удаляет каталоги `job-outputs/<job_id>` старше `[jobs].output_retention` (по умолчанию 7 дней). Имена берутся из списка этого одного каталога, годятся только имена-UUID и только каталоги (не ссылки), `remove_dir_all` не разыменовывает ссылки внутри. То же срок жизни у записей итогов задач владельца (ниже).

### 4.1 `canterlot-worker job run`

```
canterlot-worker job run --title T [--machine NAME|auto] [--labels a,b] [--expected-minutes N]
    [--lease none|build|gate] [--timeout-minutes N] --source <repo>@<sha> [--output PATH]...
    [--wait] -- <команда оболочки>
```

Команда идёт к воркеру по сокету `jobs.sock` (рядом с сокетом аренды: `$XDG_RUNTIME_DIR/canterlot/jobs.sock`, иначе `<data_dir>/jobs.sock`; `CANTERLOT_JOBS_SOCKET` переопределяет; `CANTERLOT_LEASE_SOCKET` из окружения исполнения путь не подсказывает). Сокет 0600 в каталоге 0700, но доверие уже, чем у `lease run`: `lease run` только запускает локальную команду, а `job run` стартует работу на других машинах и выбирает домен по пути исходников. Поэтому сервер по `SO_PEERCRED` берёт pid собеседника и отвечает `refused: not_allowed` на любое сообщение, если этот процесс сам или его предок по цепочке родителей — супервизор либо CLI работающего исполнения (те же `(pid, время старта)`, что воркер держит для измерений исполнений; осиротевшие потомки переходят к сопровождению, которое держит subreaper). Метку окружения потомок снять может, предка в дереве — нет. Процесс с чужим uid или нечитаемым родством тоже получает отказ. Остаточный риск: исполнение работает под тем же uid, и агент, вышедший из дерева процессов (`systemd-run --user` без `--scope`), снова станет «терминалом владельца»; граница по uid здесь не проводится. Протокол — строки JSON `{"v":1,"op":...}`: `submit {spec}` → `accepted {job_id}` или `refused {code, message}`; `wait {job_id}` → `finished {…}`. Описание задачи (`spec`, он же `spec_json` в `OwnerJobSubmit`) называет поля как `job_run`: `title`, `machine`, `labels`, `expected_minutes`, `lease`, `timeout_minutes`, `source {repo, rev}`, `outputs`, `shell`; хаб отвергает незнакомые поля. Воркер сам отклоняет очевидно негодное описание (`bad_spec`), остальное решает хаб: мост шлёт `OwnerJobSubmit {request_id, spec_json}` по потоку управления и ждёт `OwnerJobAccepted` или `OwnerJobRefused` с тем же `request_id` (код отказа хаба, например `domain_mismatch`, `no_runner_can_satisfy`, доходит до команды как есть). Нет соединения с хабом или ответ не пришёл за 30 с — отказ `hub_unavailable`.

- Без `--wait` команда печатает идентификатор задачи в stdout и выходит с нулём.
- Итог приходит командой хаба `OwnerJobFinished` и записывается файлом `<data_dir>/owner-jobs/<job_id>.json` (0600, запись через переименование, повтор безвреден). `--wait` читает этот файл: итог, пришедший до запуска команды или во время рестарта воркера, всё равно доходит. Обрыв соединения команда переживает переподключением (до 5 минут) и тем же `wait`.
- С `--wait` в stdout идёт хвост журнала, а в stderr строки `canterlot job: <id> <state> (exit N)`, `canterlot job: outputs: <каталог>` и пометка о результатах. Код выхода: код команды; 124 по `timed_out`; 130 по `canceled`; 1 для `failed` и `lost` без кода; 2 при отказе принять задачу и при ошибках аргументов.
- `--source <repo>@<sha>` требует полный sha и коммит, который есть в репозитории; `repo` — корень репозитория (или `@HEAD` для текущего каталога). Только буквальное `HEAD` превращается в sha, и только при чистом дереве (`git status --porcelain` пуст, неотслеживаемые файлы тоже грязь), иначе отказ до хаба. `--source` обязателен: хаб ставит задачу владельца только на подготовленные исходники, рабочего каталога у неё нет (его создаёт носитель), поэтому флага `--workdir` нет. Без `--machine` место выбирает хаб (`auto`); название машины ограничивает выбор самой несущей и её раннерами.
- Несколько слов после `--` склеиваются в одну строку с кавычками на каждом слове, одно слово идёт как есть (текст оболочки).

### 4.2 Гейт на раннере

`scripts/gate.sh --runner auto|<машина>` — потребитель `job run --wait`: задача `--lease gate --labels kernel-6.12 --source <repo>@<полный sha> --output .gate-out`, команда `scripts/gate/runner-gate.sh <sha>`. Носитель готовит ровно этот коммит, `runner-gate.sh` гоняет в рабочей копии контейнерный гейт (образ и `in-container.sh` из самой копии, кэши под `<корень>/cache`, контейнер с именем и `docker kill` по TERM), носитель забирает `.gate-out`, а `gate.sh` на VM пишет аттестацию `.superpowers/gate/<sha>.ok` с `runner=` по собранным `result.txt` и `state.tsv`. Отмены у `job run` нет, новых API хаба гейт не добавляет: прерванное ожидание оставляет задачу работать, отменяют её в PWA. Подробности и проверки — `docs/development.md`, «Гейт на раннере».

## 6. Облачный провайдер (стадия C1, `canterlot-hub/src/cloud/`)

Самодостаточный модуль хаба: без таблиц и без связи с циклами. Окна, деньги, сверку и жизненный цикл строит поверх него следующий слой. Ни ключа конфигурации, ни команды, ни ручки он не добавляет.

**Трейт `CloudProvider`** (асинхронный, его же подменяют в тестах):

| Операция | Ответ |
| --- | --- |
| `configurator(id)` | `Configurator {id, location, cpu_frequency, prices {cpu, ram_gb, disk_gb}, limits}`: цены в копейках в месяц за единицу, пределы (`requirements` API) в МБ |
| `ensure_ssh_key(name, public_key)` | номер ключа; идемпотентно по имени; то же имя с другим телом — `Conflict`; ключи не удаляются никогда (у токена может не быть этого права) |
| `create_server(CreateServer)` | `Created {server_id}`, `Rejected {code, message}` (определённый 4xx, кроме 429), `Ambiguous {why}` (таймаут, обрыв, 5xx, нечитаемый успех, нет связи, 429 без успеха) |
| `get_server(id)` | `Found(ServerState {status, ipv4, …})` или `NotFound` |
| `delete_server(id)` | `Deleted {quarantined}`, `AlreadyGone` (404), `NeedsConfirmation` (хеш в ответе или 423: у токена нет `is_able_to_delete`), `Failed {retryable}` |
| `list_project_servers(project_id)` | все серверы проекта или `ListError`; частичный список успехом не бывает |
| `ensure_public_ipv4(server_id)` | `POST /servers/{id}/ips {"type":"ipv4"}` → `Assigned(ip)`, `Refused {status, code, required_balance}` (4xx, кроме 429), `NotProcessed` (429), `Ambiguous`; один вызов, без повторов (С2, §7.3a) |
| `list_floating_ips()` | все плавающие адреса аккаунта (`{id: строка, ip, bound}`, идентификаторы строки, как у API) или `ListError` |
| `delete_floating_ip(id)` | `DELETE /floating-ips/{id}`: `Deleted`, `AlreadyGone` (404), `Failed`; идентификатор в путь проходит только из знаков `A-Za-z0-9_-` |

`Ambiguous` значит «сервер мог появиться»: создание не повторяется, вызывающий ищет имя в списке проекта. `NeedsConfirmation` не повторяется никогда. `CreateServer` в `Debug` не показывает облачный скрипт (в нём закрытый хостовый ключ).

**`TimewebProvider`.** Базовый адрес `https://api.timeweb.cloud` (в тестах другой). Токен читается один раз из файла при создании клиента, не попадает в `Debug`, логи и тексты ошибок; всё, что пришло от сервера, очищается от значения токена. Тот же HTTP-клиент `reqwest`, что и в остальном хабе. Предел частоты на клиенте: 20 запросов в секунду на конечную точку, скользящее окно. Таймаут запроса 30 с. На 429 запрос повторяется (до 4 раз) с ожиданием `Retry-After`, а без него с паузой 1 с, 2 с, 4 с…, не больше 60 с; `Retry-After` больше этой границы не ждётся, попытка сдаётся (`Failed {retryable: true}`, у создания `Ambiguous`). Другие повторы запрещены: ни 5xx, ни обрыв не повторяются внутри клиента.

**Список проекта.** Ручка `GET /projects/{id}/resources/servers` в описании API не имеет пагинации, но отдаёт `meta.total`. Клиент всё равно идёт по страницам (`limit=100`, `offset`), складывает серверы по номеру и принимает результат, только если уникальных элементов ровно `meta.total`. Страница с ошибкой, страница без новых элементов при недоборе и расхождение с общим числом (список менялся во время обхода) дают ошибку целиком (`ListError::Page` или `Incomplete`), а не частичный список.

**Цены (`price.rs`), только целые копейки.**

- Месяц = `cpu × цена_cpu + ГБ_памяти × цена_памяти + ГБ_диска × цена_диска`; размеры API в МБ, доли ГБ округляются вверх. Проверка пресета из спеки: конфигуратор 133, 28 vCPU, 112 ГБ, 160 ГБ = 133 600 ₽.
- Час = `ceil(месяц / 720)`.
- Резерв = `час × (ceil(минуты / 60) + 1)`, где минуты — жёсткий предел плюс `drain_grace` плюс `teardown_margin`.
- Итог закончившегося окна = `час × ceil(минуты / 60)`, не меньше одного часа; минуты идут от вызова создания до подтверждённого удаления.
- Переполнение `i64` и отрицательные цены дают `PriceError`, а не обрезанное число.

Это рабочее правило тарификации: оно остаётся таким, пока живая проверка не подтвердит часовое округление и судьбу серверов в карантине.

**Цены конфигуратора.** Описание API для конфигуратора серверов поля цен не содержит (оно есть у конфигуратора баз данных: `prices {cpu, ram, disk, bandwidth}`); живая проверка 21.11 показала те же поля у конфигураторов серверов. Клиент читает `prices.cpu|ram|disk` в рублях за единицу в месяц и отказывает (`Malformed`), если их нет.

**Cloud-init (`cloud_init.rs`).** Генератор `#cloud-config` по `{host_key_ed25519_private, host_key_ed25519_public, runner_authorized_key, root_dir}`: ставит хостовый ключ (`ssh_keys`, `ssh_deletekeys`, остальные ключи сервера стираются, `HostKey` в drop-in), docker (`docker.io`), git и rsync; заводит пользователя `runner` в группе `docker` с `sudo` без пароля и ключом носителя; создаёт `root_dir` во владение `runner`; маркер `/var/lib/canterlot-runner/ready` пишется последней командой и только после проверки docker, git, rsync, пользователя и каталога. Токена canterlot и бинарников в нём нет. Входные данные проверяются (формат ключей, безопасный абсолютный путь), результат длиннее 65 535 байт — ошибка.

**Хостовый ключ (`host_key.rs`).** `HostKey::generate()` создаёт пару ed25519 в памяти (`ring`, семя из `getrandom`) и отдаёт закрытый ключ в формате OpenSSH, открытую строку `ssh-ed25519 …` и отпечаток `SHA256:…`. На диск ключ не пишется, в `Debug` закрытая часть скрыта.

**Поддельный Timeweb** (`tests/it/support/fake_timeweb.rs`) повторяет формы ответов из OpenAPI и держит ручки сбоев для следующего слоя: создание «принял и закрыл соединение», зависание, 5xx и произвольный отказ, 429 с `Retry-After`, страницы списка с отказом на заданном смещении, список без пагинации и с подменённым `total`, удаление с хешем, 423, 5xx и с `is_moved_in_quarantine: true`, серверы, видимые в списке только после заданного числа листингов (счёт по листингам, а не по часам), загрузка сервера (`installing` → `on` с адресом после заданного числа опросов), заголовок `Authorization` в текстах ошибок. Тесты клиента лежат в `tests/it/cloud_timeweb.rs`, остальные (цены, cloud-init, ключ, предел частоты) — модульные в `src/cloud/`.

## 7. Облачные окна в хабе (стадия C2, `canterlot-hub/src/cloud/{windows,service}.rs`)

Окно — жизнь одного облачного сервера: от намерения создать до подтверждённого конца оплаты. Таблицы `cloud_windows` и однострочная `cloud_budget` (миграция `0131`), конфигурация `[runners.cloud]` (`docs/configuration.md`), HTTP владельца (`docs/design/api.md`). Токен провайдера и закрытый хостовый ключ нигде, кроме памяти и тела запроса создания, не живут.

### 7.1 Состояния

`create_intent` → (`create_unknown`) → `identified` → `ready` → `draining` → `deleting` → `ended`; тупики без сервера или с исчезнувшим: `failed`, `gone`. Живое окно — одно из первых шести (кроме `ended`, `failed`, `gone`): `create_intent`, `create_unknown`, `identified`, `ready`, `draining`, `deleting`. Живое окно одно: замок строки `cloud_budget` в транзакции создания и частичный уникальный индекс `cloud_windows_one_live`. Окно в `deleting` остаётся живым, пока сервер не пропал из полного списка: оно считается в расходе по резерву и блокирует создание нового.

| Было | Условие | Стало |
| --- | --- | --- |
| `create_intent` без метки вызова | первая успешная сверка в этом запуске хаба; метка `create_called_at` и пределы ставятся до вызова | вызов `create_server` |
| вызов: `Created` | | `identified` (+`server_id`, строка раннера `cloud` готова) |
| вызов: `Rejected` с кодом из списка перебора (409 `no_free_node`, `location_not_available`, `preset_not_found`, 400 `configuration_requires_sales_request`) | сервера точно нет | вызов следующего профиля списка в том же окне, без новой транзакции; перед каждым вызовом в строке стоят конфигуратор и цена этого профиля |
| вызов: `Rejected` с другим кодом, либо отказали все профили | сервера точно нет | `failed`, итог 0, резерв снят, коды в `last_error` |
| вызов: `Ambiguous`, либо метка есть, а ответа нет (упал хаб, оборвали проход) | второго POST нет никогда, и на другом профиле тоже: сервер мог появиться | `create_unknown` |
| `create_unknown` | полная выборка показала имя | `identified` |
| `create_unknown` | полная выборка без имени и с `create_called_at` прошло `create_unknown_window` | `failed`, итог 0 |
| `identified` | сервер `On` с IPv4 | несущей уходит `AttachRunner`; окно ждёт воркер |
| `identified` | воркер раннера `cloud` на связи | `ready` |
| `identified` | `ready_timeout` от вызова, либо жёсткий предел | `deleting` |
| `ready` | простой `idle_minutes` без работы | `deleting` |
| `ready` | раннер отключён 10 минут при подключённой несущей | `deleting` |
| `ready` | `hard_cap_at` (от вызова создания) | `draining`: раннер перестаёт брать работу (`accepts_remote_work = false`) |
| `draining` | работы не осталось | `deleting` |
| `draining` | `drain_until` | идущие задачи отменяются штатной отменой |
| `draining` | `teardown_until` | `deleting`; отзыв раннера заканчивает неподтверждённое как `lost` |
| `identified`/`ready`/`draining` | дольше `teardown_until` (в `draining` ещё 10 минут), например после простоя хаба | `deleting` и пуш владельцу (`outage_extra_cost` на первом проходе после старта, иначе `window_overrun`) |
| `identified`/`ready`/`draining` | сервера нет в полном списке, прошло `create_unknown_window` от вызова | `gone`, раннер отозван, пуш `window_gone` |
| `deleting` | `delete_server` принят (в том числе в карантин), затем полный список без сервера | `ended` с `delete_confirmed_at` и итогом |
| `deleting` | сервер пропал из полного списка без принятого удаления (владелец удалил в панели) | `ended` |

«Удалить сейчас» (`POST /api/v1/cloud/windows/{id}/delete`) переводит `identified`/`ready`/`draining` в `deleting`, а `create_intent` без вызова отменяет (`failed`, итог 0). Для `create_unknown` ответ `not_yet`: сервера в известных ещё нет, решит сверка.

### 7.2 Создание и деньги

`windows::create_in_tx(conn, config, pricing, CreateRequest {trigger, proposal_id, hard_cap_minutes, consent_over_budget_kopecks})` — одна транзакция для всех входов (карточка, кнопка, автоматика): замок `cloud_budget`; отказ `LiveWindowExists`; резерв = `reservation_kopecks(час самого дорогого профиля списка, предел + drain_grace + teardown_margin)` (`Pricing.profiles` — все профили `[[runners.cloud.profile]]` с ценой часа; снимок списка хранится в окне, `cloud_windows.profiles`); бюджет месяца = `cloud_budget.monthly_budget_kopecks` (0 по умолчанию), расход месяца = итог закончившихся окон + резерв живых (`spent_in_month`); не помещается — отказ `OverBudget`, если только `consent_over_budget_kopecks` не равно резерву в точности; вставка `create_intent` с резервом, месяцем (`YYYY-MM` по Москве на момент создания) и хостовым ключом: в базе только открытая половина, закрытая лежит в памяти (`PENDING_KEYS`) до вызова создания и уходит только в cloud-init для провайдера. После перезапуска хаба окну, которому ещё не звонили, генерируется новый ключ. Цену часа вызывающая сторона берёт у провайдера до транзакции (`CloudService::pricing`), чтобы сетевой вызов не держал замок; `CloudService::create` делает это сама. Предложения-карточки, автоматический режим и редактирование бюджета строятся поверх этой функции (задача C2b).

Профили: служба пробует их по порядку снимка окна; определённый отказ из списка (`cloud::profile_fallback`: 409 `no_free_node`, `location_not_available`, `preset_not_found`, 400 `configuration_requires_sales_request`) переходит к следующему, любой другой отказ или отказ всех закрывает окно (`failed`, итог 0, коды в `last_error`), `Ambiguous` останавливает перебор. В строке окна `configurator_id` и `price_hourly_kopecks` ставятся перед каждым вызовом: после приёма это действительные значения принятого профиля.

Итог закончившегося окна = `final_cost_kopecks(действительная цена часа, минуты от create_called_at до delete_confirmed_at)`; у окна, у которого сервера не было, 0; у `gone` — до момента обнаружения.

### 7.3 Служба (`CloudService`)

Проход `tick(now)` каждые 10 с под `singleton::supervise("cloud_windows")`: один хаб за раз. «Сейчас» параметр, поэтому сроки проверяются в тестах без ожидания. Проход: сверка (первым делом при старте и каждые `reconcile_interval`), затем шаг каждого живого окна. Новые серверы создаются только после первой успешной сверки в этом запуске.

**Сверка** читает проект целиком (`list_project_servers`); любая ошибка или неполный список не меняют ничего. По полному списку:

- сервер с именем `canterlot-runner-<канонический uuid>` без живого окна (нет строки, закрытое окно) удаляется, владельцу пуш `stray_server_deleted` (или `stray_server_stuck` раз в 30 минут, если удалить не вышло); серверы с другими именами и других проектов не трогаются никогда;
- `create_unknown` и `create_intent` с меткой вызова идентифицируются по имени; окна, которым сервера нет в списке дольше `create_unknown_window`, закрываются.

**Удаление.** Раннер `cloud` отзывается (токен гаснет, незаконченные задачи `lost`), затем `delete_server`: `Deleted` (в том числе `quarantined`) и `AlreadyGone` ждут подтверждения полным списком; `NeedsConfirmation` оставляет окно в `deleting` с `last_error = needs_confirmation`, пуш `delete_needs_confirmation` сразу и с каждой повторной попыткой раз в 30 минут (токен не может удалить, сервер тарифицируется); `Failed` повторяется с паузой 30 с, 1 мин, 2 мин… до 10 мин, после трёх неудач пуш `delete_failing` раз в 30 минут. Открытое обязательство удаления не снимается и не вычищается.

### 7.3a Публичный IPv4 (проверено на живом Timeweb 22.11)

- У нового сервера адреса нет. Служба на первом проходе после `identified` ставит метку `ip_requested_at` и вызывает `add_ipv4` (`POST /servers/{id}/ips {"type":"ipv4"}`, ответ `server_ip {ip, type}`); адрес пишется в `cloud_windows.ipv4`. Определённый отказ (`Rejected`, `Conflict`, `NotFound`, `Auth`, 429) снимает метку, и следующий проход повторяет заказ; неопределённый (обрыв, 5xx) оставляет метку: второго заказа нет, а адрес появится в ответе `get_server`. Подключение (`AttachRunner`) уходит, когда сервер `On` и адрес известен.
- **Единая точка.** Адрес получает один метод провайдера, `ensure_public_ipv4(server_id) -> Ipv4Outcome {Assigned(ip), Refused{status, code, required_balance}, NotProcessed, Ambiguous}`; способ за ним (сейчас заказ нового адреса, позже, возможно, привязка заранее купленного плавающего через `POST /floating-ips/{id}/bind`) можно сменить, не трогая машину состояний окна. Привязку плавающего адреса сейчас не делаем.
- **Отказ провайдера.** Любой 4xx, кроме 429, — определённый отказ: адреса нет, повтор не поможет (например 400 `abuse_prepayment_required` с `details.required_balance`: правило против злоупотреблений на аккаунте). Окно сразу уходит на удаление по обычному пути (`delete_reason = ipv4_refused`, отзыв раннера, удаление сервера, подтверждение отсутствием в полном списке), метка заказа снимается (адреса нет, итог без него: только сервер от `create_called_at`), в `last_error` остаётся `error_code` ответа. Владельцу пуш `ipv4_refused` сразу: «Timeweb отказал в публичном IPv4 (<код>), сервер удалён» и `required_balance` в рублях, если он был, больше ничего из ответа. 429 — запрос не обработан, метка снимается и заказ повторяется. 5xx, таймаут, обрыв, нечитаемый ответ — неопределённый исход: сервер перечитывается тем же проходом, второго заказа для окна нет.
- **Блок провайдера.** Отказ `abuse_prepayment_required` пишет `cloud_budget.provider_block_code` и `provider_block_at`; пока блок стоит, `create_in_tx` отказывает `CreateRefusal::ProviderBlocked {code}`, а список окон (`GET /api/v1/cloud/windows`) показывает `provider_block_code` и `provider_block_at`. Снимает блок только владелец: функция `windows::clear_provider_block` оставлена задаче C2b (кнопка в PWA).
- Цена: `ipv4_hourly_kopecks` в окне (из `ipv4_monthly_rubles`), резерв = резерв сервера + резерв адреса (каждый `час × (ceil(минуты / 60) + 1)`).
- Конец окна: после принятого удаления сервера и подтверждения его отсутствия в полном списке (`server_gone_at`) служба ищет адрес окна в полном списке плавающих адресов (`list_floating_ips`). Привязан — ждёт; отвязан — `delete_floating_ip(id)` и повторный список; нет в списке — `ip_gone_at`, окно `ended`. Отказ удаления повторяется с паузой, после трёх неудач пуш `ip_delete_failing`. Окно, в котором заказ адреса остался без ответа и адрес неизвестен, кончается пушем `ipv4_unattributed` (чужие плавающие адреса не трогаются, итог считается с запасом до конца окна).
- Итог = `final_cost(цена сервера, от create_called_at до server_gone_at) + final_cost(цена адреса, от ip_requested_at до ip_gone_at)`.
- Сверка: отвязанный плавающий адрес, записанный на окне в `ended`/`failed`/`gone` и не записанный ни на одном живом, удаляется (пуш `stray_ip_deleted`, при отказе `stray_ip_stuck` раз в 30 минут). Привязанные и чужие адреса не трогаются никогда.
- Cloud-init: пакеты ставятся не модулем `packages` (без сети он падает и не повторяется), а `runcmd`-циклами, которые ждут сеть; маркер готовности по-прежнему последний.

### 7.4 Раннер `cloud` и несущая

Одна строка `machines` с именем `cloud`, ролью `runner`, родителем `carrier_machine_id`, корнем `/srv/canterlot-runner`, рангом и метками из конфигурации; создаётся при первом окне и переиспользуется (`cloud_budget.cloud_machine_id`). Несущей в `RunnersAssigned` она попадает, пока окно `identified`, `ready` или `draining`, независимо от токена. Подключение:

1. Сервер `On` с адресом: несущей уходит `AttachRunner {window_id, machine_id, host, host_key_public, root_dir, max_running, lease_slots}` (долговечная команда уровня машины, только на соединении с `runners_v1`, только несущей). Закрытого ключа, токена и бинарников в команде нет. Реализацию на стороне несущей делает C3: войти пользователем `runner` с проверкой `host_key_public`, дождаться маркера готовности, запросить токен, запустить воркер. До C3 несущая отвечает на команду отказом `unsupported_command` (хаб гасит её как отклонённую), и окно уйдёт по `ready_timeout`.
2. Запрос токена `RunnerTokenRequest` для строки `cloud`: пока окно `identified`, хаб ротирует токен с `reset_local_state = true, reactivate = true`; пока `ready`/`draining` — с флагом несущей и `reactivate = true`; вне окна отказ `revoked`. Статические раннеры ведут себя как прежде.
3. Окно становится `ready`, когда воркер `cloud` на связи; команда подключения считается выполненной.

Конец окна отзывает строку раннера (`machines::revoke`): токен гаснет, его незаконченные задачи становятся `lost`, из списка несущей он уходит. Закрытие строки `draining` (`accepts_remote_work = false`) использует ту же паузу, что и размещение: новых привязок нет.

### 7.5 Пуши владельцу (`cloud_alert`)

Через `owner_pushes` (вид `cloud_alert`, без разговора, ключ `dedupe_key` с номером попытки или получасового слота): `stray_server_deleted`, `stray_server_stuck`, `delete_needs_confirmation`, `delete_failing`, `window_overrun`, `outage_extra_cost` (с оценкой лишнего расхода), `window_gone`, `stray_ip_deleted`, `stray_ip_stuck`, `ip_delete_failing`, `ipv4_unattributed`, `ipv4_refused` (с `error_code` и `required_balance`). Без `[notify.gotify]` пуша нет, но запись в журнале (`cloud_alert`, код без значений) остаётся.

### 7.6 Тесты

`tests/it/cloud_windows.rs` (против поддельного Timeweb, с ручками сбоев из §6; сроки через `tick(now)`): полный цикл создание → `identified` → `ready` (имитация подключения несущей) → простой → удаление → `ended` с итогом; неопределённое создание (найдено позже → `identified`, нет в полных списках → `failed`, счётчик POST поддельного сервера равен 1); оборванный вызов; плохой или неполный список ничего не меняет; жёсткий предел (`draining` → отмена → граница сноса → `lost` → удаление, предел от вызова создания); исходы удаления (`NeedsConfirmation` с пушами и живым окном, три отказа `DELETE`, карантин подтверждается только отсутствием); сверка (лишний сервер, чужие имена и проекты, до любого создания, перезапуск хаба с окнами во всех состояниях); одно живое окно и две параллельные попытки создания; арифметика резерва из конфигурации; строка `cloud` (оживление при подключении, отзыв и `lost`, список несущей по сети в `runners_grpc.rs`); простой и отключение; секреты в журнале (захват). `tests/it/cloud_http.rs` — HTTP владельца. Конфигурация и включение при старте проверяются там же.
