# Конфигурация

Для запуска команд хаба подготовьте TOML-конфиг и отдельный файл с URL PostgreSQL.
URL не передаётся аргументом CLI и не читается из `DATABASE_URL` при запуске бинарника:

```bash
umask 077
mkdir -p ~/.config/canterlot ~/.local/state/canterlot-control
read -rsp 'URL PostgreSQL: ' canterlot_db_url
printf '\n'
printf '%s\n' "$canterlot_db_url" > ~/.config/canterlot/database-url
unset canterlot_db_url
```

Сохраните `~/.config/canterlot/hub.toml`:

```toml
database_url_file = "database-url"
grpc_listen = "127.0.0.1:7443"
tls_cert = "tls/cert.pem"
tls_key = "tls/key.pem"
manifest = "../../.local/state/canterlot-control/installation.toml"

[timers]
handshake = "10s"
degraded_after = "15s"
unavailable_after = "30s"
command_stored_receipt = "5s"
dispatch_sweep = "5s"
steer_outcome = "2m"
http2_keepalive_interval = "30s"
http2_keepalive_timeout = "10s"

```

Хаб принимает факты `pilot_v1`: модель и агент блока, инструмент и краткое описание, расход хода по моделям и агентам, заполнение контекста, лимиты и отчёт машины. `runs` хранит интервалы в машинном времени, приведённом к часам хаба; пересекающиеся и опоздавшие более чем на минуту ходы исключаются из оценки доли недельного лимита. История расхода группируется по разговору, модели, агенту и дню выбранного часового пояса; временные выборки используют полуинтервал `[from, to)`. Прирост недельного лимита хода засчитывается один раз, в строке с наибольшим расходом токенов; отрицательный прирост (сброс окна внутри хода) в оценку не входит.

В `[limits]` уже работают `snapshot_min_interval` (снимок при изменении значения/сброса или по истечении интервала между наблюдениями) и хранение времени наблюдения. Старые наблюдения остаются историей и не изменяют текущее значение; событие `limits_changed` пишется только при изменении значения или времени сброса. Без образца машинных часов наблюдение сохраняется только в историю с диагностикой. Снимки отправляются после commit подходящим сеансам `pilot_v1`, включая первое заполнение после отчёта машины.

Правила лимитов (`crunch.rs`, [контракт](design/api.md#лимиты-кранч-и-недельный-резерв)) работают внутри цикла планировщика и останавливаются вместе с ним. Упор в лимит без «кранча» ставит паузу `limit_reached` со временем сброса; с «кранчем» очередь удерживается до сброса (`reset_grace` после него, `unknown_reset_retry` при неизвестном времени), а пробуждение проверяется по новому показанию лимитов: точное показание доказывает сброс само, оценочному (`data_confidence=estimated`) нужны два отдельных отсчёта после срока, каждый из которых показывает сброс. Без подтверждения задание повторяется по `verify_backoff` и после commit просит одну доступную машину провайдера с `pilot_v1` опросить лимиты: не чаще `poll_min_interval`, после исчерпания шагов не чаще `poll_floor`. Недельное показание не ниже действующего порога расхода включает резерв: новые ходы провайдера удерживаются, идущий ход завершается. Умолчание порога — `100 - weekly_reserve_pct`; владелец меняет остаток `reserve_remaining_pct` и пороги окраски в настройках PWA (`/api/v1/limit-settings`), и смена пересчитывает резерв сразу, без перезапуска хаба. Выход из резерва требует нового окна или двух показаний ниже порога на `reserve_exit_hysteresis_permille`. После сброса продолжаются только сессии в «кранче», которые остановил лимит; текст продолжения берётся из сессии или `default_resume_text`. Резерв тратится только действием владельца `spend-reserve` для одной сессии до сброса недели.

`machine_info` заменяет каталог харнессов атомарно, проверяет лимиты вложений и сохраняет последнюю допустимую метрику. Проектор доступности получает отдельное PostgreSQL-соединение с singleton-блокировкой, при первом захвате в процессе сбрасывает сохранённую доступность и обновляет её каждые 5 секунд и по изменениям Registry. При повторных захватах проекция сразу использует живой Registry. При потере соединения служба освобождает блокировку и переподключается; второй процесс остаётся пассивным и принимает работу после освобождения блокировки. Shutdown завершает службу.

Обновление: сначала хаб, затем воркер. Откат хаба ниже уже использованной воркером capability не поддерживается.

HTTP сессий поддерживает создание по каталогу машины (режим разрешений по умолчанию `bypass`), старт в одной транзакции, закрепление, цвет, архив, удаление остановленной сессии (`DELETE /api/v1/conversations/{id}`), группы, поиск по заголовку с ICU, список с курсором и отметку прочитанного. Проверенный каталог запоминается (до 20 на машину, экран новой сессии показывает последние 3); чтение машин включает каталоги, ОС, метрики и предупреждения; история лимитов учитывает часовой пояс и расход по агентам. Поля и маршруты описаны в [контракте API](design/api.md#сессии-группы-и-чтение-данных-машин). Пресеты инструкций хранит хаб: `GET` и `POST /api/v1/presets`, `GET`, `PATCH` и `DELETE /api/v1/presets/{id}` (версии текста, правка с `base_revision`, мягкое удаление), событие `instruction_preset_changed` и поле `presets` в снимке списка; текст пресета отдаёт только детальное чтение и чтение агента. Ссылка на пресет (`clean` по умолчанию, `owner` или UUID) — поле `instruction_profile` создания сессии и настроек; сессия закрепляет применённую версию, а пресет, отличный от `owner`, получает только сеанс воркера с `instructions_v1`. Новых таблиц конфигурации не требуется: текст кранча берётся из `[limits]`, предупреждения из `[machines]`, HTTP использует существующий `[http]`.

Таблицы пилота в `hub.toml` необязательны; показаны значения по умолчанию. Таблица `[http]` отсутствует по умолчанию: без неё хаб обслуживает только gRPC. Пуши владельцу через [Gotify](https://gotify.net) включает необязательная таблица `[notify.gotify]`; без неё пушей нет. Пример (раскомментируйте):

```toml
# [notify.gotify]
# url = "https://gotify.example"           # Адрес сервера Gotify, http(s), без query.
# token_file = "/etc/canterlot/gotify-token" # Ключ приложения Gotify; читается один раз при старте.
# app_url = "https://canterlot.example"  # Адрес PWA для ссылки в пуше; по умолчанию первый из [http].allowed_origins.
# timezone = "Europe/Moscow"             # Пояс времени в тексте пуша (IANA), по умолчанию UTC.
# waiting = true                         # Сессия ждёт владельца (приоритет 8).
# turn_finished = true                   # Корневая сессия закончила ход (приоритет 5).
# failures = true                        # Корневая сессия упала или застряла (приоритет 7).
# max_per_minute = 20                    # Общий предел пушей в минуту.
```

Пуши о входе идут при любой таблице `[notify.gotify]`, отдельного выключателя у них нет; ведут на экран «Сеансы и вход» (`{app_url}/settings/sign-in`), приоритет 8, разговора у них нет, и отмена по разговору их не касается. `sign_in` — каждый новый сеанс: «Новый вход в canterlot», в тексте устройство, место, адрес и способ входа («Firefox 159 · Linux · Москва · 203.0.113.9 · по паролю»). `sign_in_failures` — сводка неудач («Неудачные попытки входа: 37 с 12 адресов за час»), когда за час их набралось не меньше пяти, не чаще раза в час; числа считаются при отправке. `sign_in_lock` — включилась общая блокировка входа по паролю, один пуш на блокировку. `session_country` — живой сеанс заговорил из новой страны (геолокация на хабе): «Сеанс «Ноутбук» используется из новой страны: Germany (Berlin, 198.18.0.7)», не больше одного пуша на сеанс и страну, страна входа пуша не даёт. Адреса и города уходят только в собственный Gotify владельца. Ссылка восстановления `auth recovery-link --push` уходит мимо очереди `owner_pushes`, напрямую, чтобы не лежать в базе открытым текстом.

Место по IP. Хаб ищет место сеанса сам, в файле `[auth.geoip].path` (по умолчанию `data/geoip/dbip-city-lite.mmdb` от каталога конфигурации): база DB-IP «IP to City Lite» в формате MMDB, около 121 МБ, обновляется ежемесячно. Файл отображается в память (`mmap`), а не читается целиком, поэтому процессы хаба делят одну копию страниц. Хаб проверяет mtime файла не чаще раза в минуту и при смене открывает его заново; без файла место сеанса `null`, частные, петлевые, link-local и CGNAT адреса дают «локальная сеть» и без него. Адрес никуда не отправляется. Обновление:

```bash
sudo -u canterlot canterlot-hub geoip update --config /etc/canterlot/hub.toml
```

Команда не открывает базу данных хаба: скачивает `https://download.db-ip.com/free/dbip-city-lite-YYYY-MM.mmdb.gz` за текущий месяц, а если его ещё нет (`404`) — за прошлый, распаковывает во временный файл рядом с целевым, проверяет открытием и одним поиском и атомарно переименовывает поверх целевого. При любой ошибке прежний файл остаётся, а команда завершается с кодом ошибки (`geoip_download_failed`, `geoip_not_gzip`, `geoip_invalid`, `geoip_not_published`, `geoip_dir_error`). Запрос несёт только имя файла: ни адресов, ни данных владельца. Запускать раз в месяц, например таймером systemd или шагом развёртывания, когда файла нет или он старше 35 дней. Лицензия базы — CC BY 4.0 (https://db-ip.com/db/download/ip-to-city-lite): экран, показывающий место, указывает источник — «IP-геолокация: DB-IP» со ссылкой на https://db-ip.com.

События. `waiting` — любая сессия, корневая или делегат, открыла запрос к владельцу: вопрос (AskUserQuestion, elicitation; понимаются формы `questions` и `ask_question.questions`, в том числе строкой), разрешение, одобрение плана (`ExitPlanMode`) или одобрение запуска вне списка; один пуш на запрос. `turn_finished` — корневая сессия (без родителя) осела в `idle` после хода; решение то же, что у подписок и доски плана, поэтому сессия, которую держит автопинок, или продолжающая работу пуша не даёт; итоги делегатов уходят их оркестратору и пушем не дублируются. `failures` — корневая сессия получила `failed`, `stalled`, `owner_lost` или `quota_paused`; один пуш на эпизод (отпечаток осевшего состояния). Итог старше 10 минут не шлётся: перезапуск хаба, переоценивающий давно осевшие сессии, телефон не будит. У сессии, которую держала фоновая задача, свежесть считается от последнего события: пока задача работает, пуша нет, а когда фон заканчивается, итог приходит.

Пуш: заголовок — название сессии (до 60 символов, без управляющих символов), текст — одна-две строки по-русски («Ждёт ответа: …», «Ждёт разрешения: …», «Ждёт одобрения плана», «Ход завершён» и начало ответа этого хода до 300 символов, без ответа — просто «Ход завершён», «Сессия упала: …», «Застряла: нет событий с …», «Пауза по лимиту до …»). Ответы на вопросы в пуш не попадают, только сам вопрос. Gotify получает `extras` с `client::display.contentType = "text/plain"` (без разметки) и `client::notification.click.url = <app_url>/c/<id сессии>`: нажатие открывает чат в PWA.

Доставка. Строка ставится в таблицу `owner_pushes` в той же транзакции, что и событие, и сетью ничего не ждёт; отправляет фоновая служба (одна на базу, advisory lock `canterlot:owner_push`) после commit: `POST {url}/message`, ключ только в заголовке `X-Gotify-Key`, срок запроса 10 секунд. Сеть, 408, 429 и 5xx повторяются: три попытки примерно за четыре минуты (паузы 1 и 3 минуты); другой ответ 4xx и последняя неудача бросают пуш с одной строкой WARN `owner_push_dropped` (вид, сессия, код ответа). Попытка и пауза записываются до запроса: потерянное подтверждение стоит одного отложенного повтора в пределах трёх попыток, а не повторной доставки. Пуш, не ушедший за 30 минут, тоже бросается. Готовность и возраст строки считает база: расхождение часов хаба и PostgreSQL доставку не сдвигает. Ключ дедупликации уникален: повторная оценка того же эпизода, повтор пакета журнала или повторно открытый запрос второго пуша не дают (если первый пуш запроса был отменён или брошен до отправки, повторное открытие всё же шлёт его); итог хода привязан к концу хода, поэтому дребезг состояния сессии (например, перезапуск воркера) второй «Ход завершён» не шлёт. Решённый к моменту отправки запрос и сессия в корзине пуш отменяют; корзина отменяет ожидающие пуши сессии, окончательное удаление удаляет их строки. Сигнала «владелец сейчас смотрит этот чат» у хаба нет, поэтому пуш уходит всегда. Журнал содержит только числа и идентификаторы; ключ не попадает ни в журнал, ни в `Debug`, ни в API. Ключ читается только при старте: после замены файла перезапустите хаб. Без таблицы при старте хаб отменяет ожидающие пуши и удаляет готовые строки старше недели. Ошибки старта: `config_invalid_notify_url`, `config_invalid_notify_app_url`, `config_notify_app_url_missing`, `notify_token_file_unreadable`, `notify_token_file_invalid` (пустой файл или пробелы внутри), `notify_timezone_invalid`.

Origin задаётся как `scheme://host[:port]`, без пути, query и fragment. `[auth].origin` обязан входить в `allowed_origins`, `[auth].rp_id` — быть хостом `origin` или его родительским доменом; иначе старт падает с `config_invalid_auth`. WebAuthn не принимает IP-адрес как `rp_id`: для ключей доступа origin должен иметь имя (`localhost` подходит). Устаревшие `user_header` и `logout_url` больше не проверяются, чтобы старое значение не останавливало развёртывание. `blob_dir` и `proxy_secret_file` разрешаются от каталога конфигурации, staging и blobs размещаются на одной файловой системе вне рабочих репозиториев. Все процессы хаба с общим томом координируют загрузку, публикацию и удаление через `flock` на постоянных `blob_dir/locks/<id>`; эти lock-файлы нельзя удалять во время работы хабов. `multi_process = true` включает `NOTIFY` и слушатель PostgreSQL с восстановлением соединения; при `false` шина остаётся внутри процесса.

`WorkerData.FetchAttachment` читает опубликованные blobs из того же `[attachments].blob_dir` чанками до 128 КиБ, начиная с запрошенного смещения. На машину допускается четыре потока; пятый получает `RESOURCE_EXHAUSTED`. Потоки не удерживают соединения PostgreSQL и завершаются с `UNAVAILABLE` при остановке хаба. Готовность файлов и причины ожидания поступают в `CJ` как `attachment_ready` / `attachment_failed`; обрыв передачи сам по себе не отклоняет ввод. Blobs связанных вложений хранятся до удаления сессии (`DELETE /api/v1/conversations/{id}`) и освобождаются после него.

Картинки, на которые смотрел агент (pilot.md §5.7), принимает `WorkerData.PutMedia`: первый кадр несёт заголовок (`media_id`, исполнение, блок, тип, размер, SHA-256), следующие - данные до 128 КиБ. Тело пишется в staging того же `[attachments].blob_dir`, проверяется по длине и SHA-256, публикуется (`fsync`, `rename`, `fsync` каталогов), сверяется сигнатура типа (png, jpeg, webp, gif), и только затем фиксируется строка `block_media`; ответ `MediaStored` уходит после commit. Повтор с тем же ID и checksum возвращает тот же ответ без копирования, другой checksum даёт `ALREADY_EXISTS`. Ссылка из блока и событие `block_media_attached` появляются только по записи `BlockMedia` журнала сопровождения, которую воркер пишет после `MediaStored`. История и снимок несут `media` на блоке, `GET /api/v1/media/{id}` отдаёт картинку владельцу (`inline`, `nosniff`, ETag = SHA-256). Сборщик вложений не трогает blobs с записью `block_media` и удаляет картинки без ссылки из блока через `gc_grace`.

`[machines]` задаёт пороги свободного места на файловой системе данных воркера и рабочих корней: ниже `disk_warn_free_gb` (30 ГБ) машина получает предупреждение в PWA, ниже `disk_critical_free_gb` (10 ГБ) — второй, критический уровень. Свободное место измеряется в десятичных гигабайтах (1 ГБ = 10^9 байт), как в условиях будильников. Возврат выше порога предупреждения плюс 5 ГБ молча закрывает эпизод. Событие диска называет до трёх крупнейших кэшей сборки из последнего отчёта сторожа машины (`watchdog_v1`). `mem_warn_gb` (3 ГБ): свободной памяти меньше этого три выборки метрик подряд открывают эпизод `mem_low`, возврат выше порога плюс 1 ГБ молча закрывает его. Порог намеренно ниже стража запуска `[orchestrator.guards]` (4 ГБ): страж перестаёт пускать новые сессии раньше, чем оркестратор слышит о нехватке; выравнивать их не нужно. Получатели событий машины (диск, память, пережившие сессии процессы) — подписчики незавершённых сессий на машине и оркестраторы на ней, которые работают, ждут владельца или простаивали меньше суток (`docs/design/pilot.md` §12.1, п. 5). `disk_warn_pct` оставлен только для чтения старых файлов и ни на что не влияет. `[sessions]` задаёт срок хранения корзины: `trash_retention` (24 часа) — сколько сессия, убранная владельцем вручную, остаётся восстановимой; по истечении уборка удаляет её прежним окончательным путём. `0` выключает автоматическую уборку, кнопка «Удалить навсегда» продолжает работать. `[session_tools]` задаёт пределы межсессионных инструментов модели: глубину вложенных запусков (`max_spawn_depth`, 3) и цепочки сообщений (`max_chain_depth`, 8), число сообщений на пару (`pair_sends`, 10 за `pair_window`, 10 минут) и на отправителя (`sender_sends`, 30 за `sender_window`) и число запусков на родителя (`parent_spawns`, 10 за `spawn_window`, час); превышение даёт модели ошибку инструмента. `max_working_children` (6) — сколько детей одного родителя могут работать одновременно (`working`, `stalled` и начало хода): запуск сверх предела не отказывает, а встаёт в очередь с причиной `children` и стартует, когда ребёнок уходит в `idle` или ждёт владельца. `spawn_stagger` (20 секунд) — пауза между запусками детей одного родителя: запуск раньше срока ждёт с причиной `stagger` и стартует ровно к нему, а не к общему тику повтора. `0` выключает каждый из двух пределов. `accepted_retention` (3 дня) — срок хранения принятой делегации: через него уборка удаляет её из архива обычным путём; `0` выключает автоматическое удаление. `machine_unavailable_after` (3 минуты) — сколько машина должна пробыть без живого воркера, чтобы подписчики её незавершённых сессий один раз услышали об этом, а после возврата — один раз о возврате с текущим состоянием цели. Отметки хранятся в базе, поэтому повторный обход и перезапуск хаба не дают второго события; короткий простой молчит. В PWA видна тихая строка «Машина недоступна N мин» в шапке чата. Владелец удерживает сессию закреплением, группой или сохранённой веткой с уникальными коммитами. Таблица необязательна: добавляйте её только при смене умолчаний. `idle_quiet` в `[activity]` (5 секунд) - сколько сессия должна простоять в `idle` без фоновой работы и без новых событий, чтобы считаться устоявшейся. `idle_background_max` в `[activity]` (15 минут) - сколько сессия может простоять в `idle` с работающей фоновой задачей, прежде чем её подписчики один раз за эпизод простоя получат отдельное предупреждение `idle_background`: фоновая задача не будит сессию, сама она ничего не делает. Это не итог: подписка не закрывается, план, пачки и будильники его не засчитывают, обычный итог придёт, когда фон кончится (`docs/design/pilot.md` §9, §12). Работают все инструменты `sessions.*`; `sessions.accept` и `POST /api/v1/conversations/{id}/accept` останавливают принятую сессию, убирают её рабочую копию и архивируют (ветка с коммитами остаётся). `session_interrupt` останавливает текущий ход прямым родителем, `session_stop` останавливает процесс, сохраняя рабочую копию и ветку; обе идемпотентны и не трогают корневые сессии владельца. `session_send` и `session_spawn` принимают `attachment_ids` — готовые вложения из разговора вызывающего, которые цель получает как вложения владельца без повторной загрузки. `canterlot_limits` показывает тех же провайдеров, что полоса и экран лимитов PWA (харнесс есть в каталоге хотя бы одной машины владельца; выключенный в `worker.toml` провайдер пропадает), с пятичасовым, недельным и месячным окнами, процентом, временем сброса и свежестью; окно с прошедшим сбросом или наблюдением старше `[limits].stale_after` помечено устаревшим и не получает прогноза; первая строка остаётся прежней строкой текущего провайдера. `share_file` отдаёт владельцу файл из процесса агента: путь читается с `O_NOFOLLOW`, проверяется по дескриптору, секретные имена (`.credentials.json`, `auth.json`, `.env`, `*.sqlite*`, `*.lock`) и каталоги `.ssh`, `.gnupg`, `.claude`, `.codex`, `~/.config/opencode`, в том числе за символическими ссылками родителей, запрещены, потолок 50 МиБ; файл появляется в ленте блока `share_file` с картинкой, видео или именем, размером и скачиванием. Какие пары харнесса и модели агент запускает сам, владелец задаёт в настройках (`/api/v1/spawn-whitelist`); запуск вне списка ждёт его решения в карточке. Изолированный запуск и приём результата требуют воркера с возможностью `session_tools_v1`. Поведение целиком описано в `docs/design/pilot.md` §12.

`[activity]` задаёт пороги подозрения на зависание и частоту проекции. Генерация без событий прогресса дольше получаса или инструмент без событий дольше получаса получают `stalled` только при доступной машине, свежих метриках её процесса и отсутствии живых потомков CLI; без телеметрии подозрение не выносится. Генерация с занятым CPU или потоковыми блоками считается работой: удалённая модель не тратит CPU, пока ждёт токены. Это состояние не прерывает исполнение. Проектор считает непрочитанные блоки и сводку очереди, публикует `derived_changed` при изменении и восстанавливает пропущенные уведомления периодическим обходом.

`[orchestrator]` — выключатели инструментов оркестратора без отката схемы. Пока работает `alarms.enabled` (по умолчанию `true`): при `false` `alarm_set` отвечает ошибкой, уже взведённые будильники доставляются как раньше. Будильники по времени и по устоявшемуся состоянию одной или нескольких сессий переживают перезапуск хаба; `all` ждёт все цели, `batch` собирает их итоги в одно сообщение, `only_on_timeout` работает сторожем. Сработавшие будильники одного получателя в пределах пяти секунд приходят одним сообщением. HTTP: `GET /api/v1/conversations/{id}/alarms` и `DELETE /api/v1/conversations/{id}/alarms/{alarm_id}`; в снимке разговора поле `alarms`, событие `alarm_changed`. `[orchestrator.routing]` задаёт свежесть показаний лимитов для выбора (`stale_limits`, 30 минут): старше — кандидат проходит с пометкой «limits unknown», если политика разрешает (`unknown_limits: "allow"`). Исключения: превышение порога при известном будущем сбросе остаётся превышением и после старения показания (расход внутри окна не падает), а показание с прошедшим сбросом считается неизвестным, как несвежее. `queue_horizon` (6 часов) — насколько далеко вперёд очередь ждёт освобождения лимита; если ближайший сброс дальше, запуск отвечает `no_executor_available`. У типа задачи политики `expected_minutes` (целое 5..1440, по умолчанию 60) задаёт ожидаемую длительность: если прогноз лимита пересечёт порог за это время и окно не успеет сброситься, кандидат пропускается с `projected_over_threshold`. У провайдера в политике `providers.<provider>` пороги задаются в процентах расхода: `max_weekly_percent`, `max_five_hour_percent`, `max_monthly_percent`; у Claude отдельный `max_weekly_fable_percent` ограничивает только кандидатов модели Fable, а без него действует недельный порог. Остальные модели Claude недельную квоту Fable не проверяют. `[orchestrator.spawn_queue]` задаёт очередь запусков: `ttl` (24 часа) — срок жизни элемента, после которого он истекает с заметкой родителю; `max_waiting` (20) — предел ожидающих на родителя (`spawn_queue_full`); `retry_delay` (60 секунд) — пауза повторной проверки занятости, лимита и стража. `[orchestrator.guards]` — пороги стража машины перед запуском: `min_free_disk_gb` (30), `min_free_disk_percent` (10), `max_load_per_core` (1.5), `min_mem_available_gb` (4), `metrics_max_age` (2 минуты). Нарушение ставит запуск в очередь с причиной `resources` и называет измерения и кандидатов на уборку; метрики старше `metrics_max_age` страж не включают, ответ помечается «machine metrics stale». `lease_warn_hold_minutes` (90) в самой таблице `[orchestrator]` — через сколько минут удержания аренды тяжёлой задачи (очередь `canterlot-worker lease run`, возможность `resource_lease_v1`) получатели событий машины (подписчики её незавершённых сессий и активные оркестраторы на ней) один раз слышат `lease_long_hold`; считается только свежее состояние очереди машины в сети.

`[scheduler]` ограничивает число ожидающих сообщений в разговоре, повторы при заполненной очереди и время ожидания без уведомлений. Маршруты `/api/v1/conversations/{id}/scheduled` (GET, POST) и `/api/v1/scheduled/{id}` (PATCH, DELETE) позволяют планировать ввод от секунды до 366 дней вперёд. Изменение и отмена доступны до отправки. В момент отправки одна транзакция создаёт обычный ввод с ключом `sched:<id>` и завершает задание; диспетчер учитывает все паузы и удержания. Повторный запуск хаба не дублирует ввод. Планировщик удаляет события старше семи дней, снимки лимитов старше `[limits].history_days` и отправленные либо отменённые задания старше 30 дней. Планировщик и проектор держат отдельные advisory lock, проверяют их в цикле и завершаются вместе с `serve`.

`[attachments]` задаёт каталог вложений хаба, число одновременно принимаемых тел загрузки, общий объём медиа одной машины, отсрочку и период сборщика. `max_media_bytes_per_machine` (по умолчанию `0` — предел выключен) ограничивает суммарный объём картинок и файлов `PutMedia` от одной машины; чтобы включить, задайте предел в байтах, например `10737418240` для 10 ГиБ. Их строки `block_media` и `block_files` держат blob до удаления разговора или уборки, загрузка сверх предела получает `INVALID_ARGUMENT` с кодом `media_quota_exceeded`. Файл от 0 байт до 100 МиБ (до 10 на ввод) создаётся `POST /api/v1/attachments`, загружается частями до 8 МиБ через `PATCH /api/v1/attachments/{id}/content` с `Upload-Offset` (текущее смещение даёт `HEAD`) и завершается `POST …/complete`: длина и SHA-256 проверяются вне транзакций, затем `fsync` файла, `rename` из `staging/` в `blobs/` и `fsync` каталогов, и только потом PostgreSQL помечает вложение готовым. Сбой между публикацией и commit оставляет orphan, повтор `complete` завершает публикацию без копирования. Ввод и отложенное сообщение ссылаются на готовые вложения через `attachment_ids`; машина должна сообщить `pilot_v1` и совпадающие лимиты. Выдача `GET …/content` показывает на месте (`inline`) только изображения из короткого списка с проверенной сигнатурой, остальное скачивается как `application/octet-stream` (`attachment`); имя файла в обоих случаях, всегда с `nosniff` и `sandbox`. Сборщик держит advisory lock `canterlot:attachment-gc`, завершается вместе с `serve` и через `gc_grace` удаляет брошенные загрузки, вложения без ссылок и файлы без записи.

Относительные пути хаба разрешаются от каталога конфига. Таймеры хаба и воркера задаются строками humantime (`"10s"`, `"250ms"`);
таблицу `timers` и отдельные её поля можно опустить, тогда действуют показанные значения.
Секреты задаются только путями к файлам; неизвестные поля конфига отклоняются.
Каталог манифеста должен существовать и находиться вне восстанавливаемого набора PostgreSQL/blobs.
Для рабочей инсталляции этот файл должен сохраняться независимо от восстановления данных.

Инициализируйте хаб и добавьте машину:

```bash
source ~/.cargo/env
cargo run -p canterlot-hub -- init --config ~/.config/canterlot/hub.toml
cargo run -p canterlot-hub -- machine add --config ~/.config/canterlot/hub.toml --name workstation
```

`init` применяет миграции и создаёт владельца, запись инсталляции и внешний манифест.
Повторный вызов запрещён, если уже есть запись инсталляции или файл манифеста.
`machine add` выводит ровно четыре строки: `machine_id=<uuid>`, `installation_id=<uuid>`, `restore_generation=<uuid>`, `token=<base64url>`.
Перенесите `machine_id`, `installation_id` и `restore_generation` в конфиг воркера, а значение `token` сохраните в файл, указанный в `token_file`.
Токен показывается один раз; сохраните его в файл воркера с правами `0600` или строже.
Хаб сохраняет только SHA-256 токена, повторно получить токен нельзя.

Относительные пути воркера считаются от рабочего каталога процесса. Неизвестные поля,
включая опечатки в `[timers]`, отклоняются; числовые таймеры без единицы измерения запрещены.
`data_dir` создаётся с правами `0700`, файлы журналов — `0600`.
Журнал воркера идёт в stderr, фильтр задаёт `RUST_LOG` (по умолчанию `info`).

Таблицы `[machine]` и `[attachments]` необязательны и отклоняют неизвестные поля. `fetch_parallelism` равен 1 или 2 и ограничивает загрузки всей машины; число попыток и интервалы положительны. `fetch_attempts` считает только ошибки содержимого (checksum и преждевременный `last`), между ними выдерживается `fetch_retry`. Обрывы, `RESOURCE_EXHAUSTED` и отсутствие соединения не расходуют попытки: повтор начинается через 250 мс с удвоением до `fetch_backoff_cap`, ожидание восстановления хаба не ограничено этим интервалом. Таблица `[[instruction_profiles]]` удалена планом 2c: такой раздел теперь ошибка разбора, пресеты инструкций хранит хаб.

Картинки, на которые смотрел агент, сопровождение читает сразу в момент события (байты из результата инструмента или файл по пути, только обычный файл до 20 МиБ с сигнатурой png, jpeg, webp или gif) и кладёт копию в `data_dir/executions/<execution_id>/media/<media_id>` (каталог `0700`, файл `0600`). Крупный или другой файл картинки не даёт: блок сохраняет путь и размер. Управляющая служба загружает копии по одной на исполнение через отдельное соединение HTTP/2, так что поток SJ и управляющий сеанс её не ждут; транспортные ошибки повторяются с backoff до `fetch_backoff_cap`, после перезапуска управляющей службы сопровождение повторяет запрос. Запись `BlockMedia` попадает в SJ только после ответа хаба о публикации, копия затем удаляется. Байты и пути не попадают в журналы.

Рабочие копии делегированных сессий лежат в `data_dir/worktrees/<id сессии>`: корень создаётся при старте воркера с правами `0700` и сообщается хабу в `MachineReport.worktree_root`; воркер сам готовит копию (`git worktree add -b canterlot/<последние 8 hex id> … <основа>`, хуки отключены) и убирает её по команде `RemoveWorktree`. Это полноценные чекауты, следите за местом на диске (предупреждение `disk_usage_high` по умолчанию с 85 %). В `.git` исходного репозитория появляются запись о копии и ветка `canterlot/…`; рабочее дерево, индекс и настройки репозитория не меняются, ничего не пушится. Ветка с коммитами остаётся после уборки. Без возможности `session_tools_v1` у воркера изолированный запуск не стартует.

Вложения воркера находятся только в `data_dir/executions/<execution_id>/attachments/`, вне рабочих каталогов. Временный файл `.tmp/<attachment_id>.part` возобновляется с его длины, в том числе после перезапуска управляющей службы. Публикация: проверка длины и SHA-256, `fsync` файла, `rename` в `<uuid>-<безопасный суффикс>`, `fsync` каталогов. Каталоги имеют права `0700`, файлы `0600`; агент получает абсолютный путь и метаданные через `Deliver.files`. Уже опубликованный файл проверяется повторно без загрузки.

Для каждого ввода actor запускает отдельную отменяемую задачу и передаёт ввод сопровождению только после готовности всех файлов. Отмена, отзыв и остановка исполнения удаляют его временные файлы сразу; завершение управляющей службы оставляет их для продолжения. Опубликованные копии удаляются после терминального состояния исполнения и полного подтверждения его SJ. `attachment_ready` / `attachment_failed` пишутся только для команды, полученной с согласованным `pilot_v1`; этот признак сохраняется в receipt и защищён временной durable-меткой до записи inbox. На один непрерывный сбой транспорта пишется одна причина `hub_unreachable`; окончательная ошибка файла заканчивается `command_rejected{reason:"attachment_unavailable"}` без передачи агенту.

После согласования `pilot_v1` воркер отправляет `MachineReport` на каждом подключении: каталог харнессов и моделей, канонические рабочие корни, домашний каталог пользователя воркера, версию, ОС и ограничения вложений. Метрики `[machine].metrics_interval` собираются из `/proc` и `statvfs` в блокирующем пуле: CPU, память, нагрузка, диски без повторов одного устройства, процессы исполнения и потомки CLI с проверкой времени старта. Заполненная управляющая очередь отбрасывает sample; heartbeat сохраняет приоритет. Незавершённый сбор дожидается завершения при остановке воркера. С возможностью `watchdog_v1` воркер раз в 5 минут (первый — через 90 секунд после подключения) и сразу, когда наименьшее свободное место пересекает `[machine].disk_warn_free_gb` вниз, отправляет `MachineWatch`: крупные кэши сборки под корнем рабочих копий и `[machine].hotspot_roots`, процессы, пережившие отпущенные исполнения этого воркера, и число сборок без `CANTERLOT_LEASE_HELD`. Размеры меряет отдельный поток с наименьшим приоритетом процессора (ввод-вывод планировщик выводит из него же): поиск до 20 секунд, полный перемер раз в час, первый проход через минуту после согласования. Корень `/` не обходится никогда. Уборка рабочих копий идёт раз в час: живая, но простаивающая дольше `idle_cache_hours` копия теряет `*/incremental`, `target/lint` и старые тестовые бинарники (логика `scripts/prune-target.sh`), копия без живого исполнения дольше `released_target_hours` — весь `target` и `node_modules/.cache`. Простой считается по времени записи `target/{*,lint/*}/{deps,.fingerprint,build,incremental}` и `target/nextest`. Копия занята, если не взялся исключительный замок на `.cargo-lock`, `.cargo-build-lock` или `.cargo-artifact-lock` профиля или какой-либо процесс держит под `target` рабочий каталог, исполняемый файл или дескриптор; тогда она не трогается. Под замками cargo убираемое переименовывается в `<data_dir>/worktrees/.gc/` и удаляется уже вне потока хранилища; остатки прерванной уборки удаляет следующий проход. Новые ключи `[machine]` необязательны: файл без них работает со значениями по умолчанию, а старый бинарник с ними не запустится, поэтому добавлять их стоит только после выката.

Очередь тяжёлых задач. Воркер держит локальный сокет аренды `<runtime>/canterlot/lease.sock` (каталог времени выполнения тот же, что у сокетов исполнений, обычно `$XDG_RUNTIME_DIR`; без него `<data_dir>/lease.sock`), каталог 0700, сокет 0600, рядом замок `lease.lock` (`flock`): второй воркер или тестовый воркер живой сокет не удаляет, а занятый сокет пробует снова раз в 5 с. Ёмкость `[machine].lease_slots` (по умолчанию 2, ключ необязателен): аренда `build` занимает слот, `gate` — все. Выданные аренды сохраняются в `<data_dir>/leases.json` (`lease_id`, `kind`, `weight`, `wrapper_pid`, `start_ticks`, `execution_id`, `since`), после рестарта воркер оставляет те, чья обёртка жива; нечитаемый `/proc/<pid>/stat` считается живой обёрткой, чтобы ошибка чтения не снимала аренды. Исполнениям воркер передаёт `CANTERLOT_LEASE_SOCKET` (путь сокета) и `CANTERLOT_WORKER_BIN` (свой бинарник: абсолютный argv[0], то есть ссылка `current/bin` прод-юнита, иначе `current_exe`) рядом с меткой `CANTERLOT_EXECUTION_GROUP`: адаптеры чистят окружение CLI, поэтому переменные ставит сопровождение. С согласованной возможностью `resource_lease_v1` воркер шлёт хабу `LeaseState` (`docs/design/streams.md`). Старый воркер не знает ключа `lease_slots` и с ним не запустится (`deny_unknown_fields`): ключ добавляют только после выкатки нового бинарника.

С feature `synthetic-adapter` доступны `synthetic`, `synthetic-exit-on-interrupt` (провайдер `claude`) и `synthetic-codex` (`codex`). Каталог содержит `synthetic-large` (усилие `low/medium/high`) и `synthetic-small` (`low/medium`), режимы `owner/ask/bypass/read_only`. Начальные параметры передаются через `StartCli`; изменения settings проверяются до durable intent и поступают в CLI с очередным вводом. Сценарии JSON описаны в `src/adapter/synthetic_cli.rs`: модели, субагенты, usage, limit-факты, исчерпание контекста, чтение локального вложения по индексу и просмотр картинки (`view_image`: блок `Read` с путём и картинка по пути или байтами). Текст и пути не попадают в диагностику.

`PollLimits` читает `data_dir/synthetic-limits/<provider>.json` с окнами `five_hour`/`weekly` и полями `used_permille`, `resets_at_ms`; без синтетической feature `PollLimits` читает CodexBar (для Codex запасной путь `account/rateLimits/read`), см. раздел о лимитах ниже. Последний `LimitsSnapshot` хранится в памяти (`LimitsCache`). Без `pilot_v1` новые факты не передаются, остальные журналы продолжают отправляться; диагностика `journal_withheld` указывает на несовместимость. Обновляйте сначала хаб, затем воркер; откат хаба ниже уже использованной возможности воркера не поддерживается.

Адаптер Claude Code собирается без дополнительных feature. Воркер показывает `claude_code` в каталоге только при наличии `[claude_code]` и успешной проверке `--version` при запуске. Сейчас минимум 2.1.311, проверена версия 2.1.311; более новая версия допускается с диагностикой `untested_cli_version`. При отсутствии CLI, ошибке проверки или старой версии харнесс отсутствует в каталоге, причина пишется один раз. Сопровождение повторяет проверку перед запуском исполнения. Субагент не шлёт потоковых кадров: его вызовы инструментов, текст и рассуждение приходят целыми кадрами `assistant` с `parent_tool_use_id` вызова `Agent` и становятся блоками его дорожки. Каталог содержит Opus 1M, Sonnet 1M и Fable 1M (`opus[1m]`, `sonnet[1m]`, `fable[1m]`) и Haiku, режимы `owner`, `ask`, `bypass`, `read_only`. Сессии, созданные с `opus`, `sonnet` или `fable` до сокращения каталога, продолжают работать: каталог ограничивает только новый выбор, а лист настроек показывает их текущую модель. Первая модель каталога считается выбором формы по умолчанию; почему у Haiku нет варианта 1M, описано в [docs/stage0/claude-code.md](stage0/claude-code.md). Модель, усилие и режим разрешений меняются между ходами (`settings_midsession_effort: true`). Модель уходит управляющим запросом `set_model`, усилие после неё запросом `apply_flag_settings` с ключом `effortLevel`: CLI кладёт его в слой флагов и шлёт со следующего запроса к API (`output_config.effort`; проверено на 2.1.316 и 2.1.319). После перезапуска и продолжения CLI получает действующее усилие флагом `--effort`. Отказ CLI или отсутствие ответа отклоняет ввод с `effort_change_failed`, хаб снимает смену с ожидания.

Старт Claude Code. CLI присылает `system/init` только после первого сообщения в stdin и после подключения серверов из `--mcp-config` (на загруженной машине до 10 с и больше), поэтому пока процесс не показался, передача ввода ждёт `ready_deadline` (30 с по умолчанию), а не `transmit_deadline`. То же действует для процесса после перезапуска со сменой инструкций. С первым `system/init` ожидание доказательства возвращается к `transmit_deadline`. Если init не пришёл за `ready_deadline`, пишется обязательная диагностика `cli_init_missing`, исполнение завершается как `failed(start_failed)`, а не `protocol_incompatible`: протокол не нарушен, процесс не поднялся. Ответ CLI раньше init не отвергается: адаптер дожидается init в пределах того же срока.

Инструкции агента приходят от хаба в `StartExecution` и смене настроек (`Instructions`: режим, текст, пресет и версия; текст не длиннее 64 КиБ и не входит в лимит меты). Неверные инструкции отклоняют запуск (`invalid_instructions`) или ввод. Смена инструкций применяется перезапуском CLI между ходами с тем же нативным ID (`CliRestarted` обновляет владельца); текст инструкций хранится только в хабе и каталоге исполнения и не попадает в журналы и события.

Пресет «Как у владельца» (`Owner`) сохраняет настройки, плагины, MCP-серверы и инструкции владельца. Делегированная сессия (создана через `session_spawn`) MCP-серверов владельца не получает ни в одном пресете и адаптере, кроме перечисленных в `[execution].delegate_mcp_servers` (ниже): хаб ставит `isolate_mcp`, Claude Code запускается с `--strict-mcp-config`, Codex в отдельном доме с конфигом без чужих `mcp_servers` и с `--disable apps --disable plugins`, OpenCode с копией конфигурации без чужих серверов в `mcp`, Antigravity получает только canterlot (подробно в `docs/design/pilot.md` §4). «Без инструкций» (`Clean`, по умолчанию) добавляет к `--settings` вычисленные при каждом запуске абсолютные пути файлов инструкций владельца строго выше корня репозитория рабочего каталога (`CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, `AGENTS.md`, `.claude/AGENTS.md`, `.claude/rules/**`) — по логическому пути и по пути с раскрытыми символическими ссылками (CLI идёт от физического cwd), файлы `CLAUDE.md` и `rules/**` пользовательского каталога (`~/.claude` и `CLAUDE_CONFIG_DIR`, если задан; оттуда же берётся `.credentials.json` для опроса лимитов) и `"autoMemoryEnabled": false`; файлы самого репозитория остаются. Пользовательский пресет (`Preset`) — то же плюс `--append-system-prompt-file <exec_dir>/instructions.md` (текст хаба, `0600`, каталог исполнения вне репозитория). Каждый пресет передаёт `--system-prompt-snapshot off`, чтобы перезапуск с `--resume` применял новый текст. Смена инструкций применяется перезапуском CLI между ходами с флагами действующих настроек: stdin закрывается (до 5 с), затем SIGTERM группе и до 2 с, затем SIGKILL; после него дочитывание stdout и ожидание выхода ограничены секундой каждое, остатки дерева гасит контейнер; ввод пишется только в новый процесс; неудача — запасной запуск с `--resume` со старыми настройками и отказ входа, а провал запасного запуска (или невозвращённый файл прежних инструкций) останавливает исполнение с исходом `start_failed`. Текст пресета не попадает в журналы, события и диагностику.

Адаптер Codex говорит с `codex app-server` по stdio JSON-RPC и собирается без дополнительных feature. Таблица `[codex]` задаёт путь к CLI (по умолчанию `codex` из `PATH`), интервал фонового опроса лимитов `rate_limits_poll_interval_s` (по умолчанию 300, меньше 60 поднимается до 60) и необязательный `home_dir` — корень собственного `CODEX_HOME` canterlot (по умолчанию `<data_dir>/codex-home`, временные каталоги запрещены); без живой сессии воркер раз в 60 с ставит Codex в очередь опроса и при необходимости вызывает `account/rateLimits/read` через короткий probe app-server. Минимум 0.164.0, проверены 0.164.0 и 0.167.0 (схемы app-server различаются только добавлениями, адаптер работает с обеими), более новая версия допускается с диагностикой `untested_cli_version`. Каталог показывает `codex` только при настроенной таблице и успешном зонде `model/list` на старте воркера; модели и усилия берутся из ответа CLI, умолчательная первой. В пресете «Как у владельца» (`Owner`) запуск добавляет лишь флаги `--enable default_mode_request_user_input` и `--disable incremental_tools` и свой MCP-сервер через `-c mcp_servers.canterlot.*`, конфигурация владельца не меняется. Второй флаг нужен всем пресетам: с инкрементальными инструментами смена модели в 0.164 переобъявляет пространство `functions` без неизменного `request_user_input`, и модель спрашивает через `request_user_input_async` без карточки. Тред помнит режим при создании, поэтому старый тред так и остаётся; вопрос без карточки в нём виден текстом и дополняется диагностикой `codex_async_question`. Остальные пресеты запускаются со своим `CODEX_HOME`: символические ссылки на записи дома владельца (вход, конфиг, сессии, навыки) без `AGENTS.md`, файлов SQLite, блокировок и каталогов демонов, плюс общий `AGENTS.md` canterlot; ссылка `sessions` есть всегда (каталог владельца создаётся до первого запуска, настоящий каталог в доме canterlot переносится к владельцу), иначе тред не возобновится при смене режима; `AGENTS.md` репозитория действует, память Codex отключена (`--disable memories`). Окружение наследуется за вычетом `OPENAI_API_KEY`, `CODEX_API_KEY`, `OPENAI_BASE_URL`, `CLAUDECODE`, `CLAUDE_CODE_*`, `CANTERLOT_*` и `RUST_LOG`; у не-владельца `CODEX_HOME` подменяется, а `CODEX_SQLITE_HOME` убирается. Рукопожатие: `initialize` с `experimentalApi`, затем `account/read` без обновления токена (без входа — `auth_required`), `config/read` и `model/list`; текст пресета едет в `developerInstructions` (`«Без инструкций»` — пусто, перекрывает конфиг владельца; при смене — однострочное примечание canterlot первым). Смена инструкций применяется перезапуском app-server между ходами и `thread/resume` с новыми инструкциями; неудача — запасной запуск со старыми домом и инструкциями, отказ входа `instructions_change_failed`, хаб снимает несостоявшуюся смену с ожидания. Возобновление — новым исполнением с `thread/resume` по нативному ID. Ввод идёт строго по одному ходу с доказательством эхом `clientId`, повтор сверяется с историей, настройки меняются оверрайдами `turn/start`, прерывание держит процесс и гасит терминалы прерванного хода. Субагенты: `thread/started` потомка в 0.164 нет, потомок принимается из элемента `subAgentActivity` (мультиагентность v2, имя из `agentPath`) или из завершения `collabAgentToolCall` с `spawnAgent` (v1, имя `subagent`, задача из `prompt`). В ленте это вызов `spawn_agent`, шаги потомка лежат под ним, а конец хода потомка становится результатом вызова (`error`, `interrupted` или без сводки), от него хаб ведёт состояние в панели делегирования. Потомок может пережить прерванный главный ход: его блоки принимаются, фазу сессии он не трогает. Кадры неизвестного треда ждут объявления потомка в ограниченном буфере, до конца главного хода; не нашедшие хозяина и пришедшие вне хода дают диагностику `unattributed_thread_frame`. Разрешения и вопросы идут через запросы сервера с доказательством `serverRequest/resolved`; вызов без запроса при чужой политике помечается `cli_policy`. Elicitation MCP открывает карточку разрешения только в режиме `url` (согласие — `content: null`); `form`, `openai/form`, `openaiForm` и `openai/userVerification` ждут содержимого или доказательства, которых PWA пока не собирает, и сразу отклоняются (`decline`) с диагностикой `unsupported_elicitation`. Ошибки хода разбираются по таблице: вход, модель, повтор, классы сервера, лимиты, контекст, прерывание. Обычные тесты используют поддельный app-server и записанные кадры, без настоящих запросов. Владелец сверяет схему после обновления CLI и запускает live smoke отдельно: Запросы сервера Codex решает владелец: команды, правки, вопросы, `url`-запросы MCP и подтверждения инструментов MCP (форма без полей с `_meta.codex_approval_kind`) приходят карточкой, разрешение действует на один вызов. Настоящие формы и `openai/userVerification` отклоняются сразу: PWA не собирает их поля. Запрос вне хода и открытый запрос субагента к концу хода получают отказ.

Адаптер OpenCode (`src/adapter/opencode`) говорит с `opencode serve --stdio --port 0` по HTTP и SSE на loopback, один сервер на исполнение. Харнесс спрятан за таблицей `[opencode]`: без неё каталог, реестр и оба других адаптера работают как раньше. Ключи таблицы: `executable` (по умолчанию `opencode` из `PATH`), `data_root` — корень данных canterlot (по умолчанию `<data_dir>/opencode`, внутри `data/`, `state/`, `cache/`, `tmp/`), `refuse_paths` — каталоги, где базу держать нельзя, `providers` — провайдеры в каталоге моделей сверх `opencode-go`, `provider_models` — фильтр моделей провайдера по шаблонам, `default_model` — модель, которая идёт первой в каталоге, и `owner_config` — каталог конфигурации владельца; каталог `opencode` в данных владельца запрещён всегда: управляемая служба на общей базе подхватывает чужие живые исполнения. Минимум 2.1.4, проверены 2.1.4, 2.2.5 и 2.2.6, более новая допускается с диагностикой `untested_cli_version`, ветка 1.x не поддерживается. Даже `opencode --version` заводит каталоги и журнал, поэтому проверка идёт с теми же каталогами XDG, что и сервер. Окружение собирается заново: от воркера берутся только `PATH`, `HOME`, `USER`, `LANG`, `TERM` и `XDG_CONFIG_HOME`; `TMPDIR` — каталог исполнения, пароль `OPENCODE_PASSWORD` случаен на запуск, `OPENCODE_CONFIG_CONTENT` несёт слой canterlot (`update`, `share`, `snapshots`, `experimental.todo` и MCP-сервер с `codemode: false`).

Адаптер Antigravity (`src/adapter/antigravity`) говорит с `agy acp` по stdio JSON-RPC и запускается на Google-аккаунте владельца: воркер не читает вход и настройки из `~/.gemini`, а сессии, MCP владельца и история разговоров живут в его каталоге. Таблица `[antigravity]` включает харнесс; ключи: `enabled` (по умолчанию `true`; `false` прячет харнесс) и `binary` — исходный `agy` (по умолчанию `~/.local/bin/agy`). Воркер проверяет `agy --version` (минимум 1.4.12, проверены 1.4.12 и 1.5.0; более новая допускается с диагностикой `untested_cli_version`), копирует бинарник в `<data_dir>/antigravity/bin/agy-<версия>` и запускает только копию: `<bin> acp --log-file <exec_dir>/agy.log --disable-telemetry [--dangerously-skip-permissions]`, cwd — рабочий каталог, `--gemini-dir` не передаётся. Проба лимитов — `<bin> -p /usage --output-format json`; `--disable-telemetry` у неё не передаётся, потому что 1.5.0 принимает этот флаг только в `acp`. Делегированная сессия перед запуском спрашивает у закреплённой копии `agy mcp list` (без хода) и стартует только при пустом глобальном списке MCP владельца; непустой список даёт диагностику `owner_mcp_not_isolated`, а неудачная проба — `mcp_list_failed`. Если системный `agy` обновился, воркер кладёт рядом новую копию и пишет диагностику `antigravity_cli_version_changed`; старые копии не перезаписываются. Окружение собирается заново из `PATH`, `HOME`, `USER`, `LANG`, `TERM`, `TMPDIR`, `SSH_AUTH_SOCK`, `CARGO_BUILD_JOBS` и `GEMINI_FORCE_FILE_STORAGE=true`. Каталог моделей берётся из `session/new` (`models.availableModels`) без хода; `configOptions.model` — семейство, а не id модели. Возобновление — через `session/list` и `session/resume`, `session/load` не используется. Режимы: `owner`, `ask`, `bypass`; `read_only` не поддерживается. Вопросы `ask_question` отвечаются обычным prompt внутри логического хода начиная с 1.5.0; на 1.4.12 карточка вопросов не показывается.

Запуск: версия, каталоги, сервер со своим stdin на всё время жизни (EOF завершает его вместе с shell, в том числе при смерти супервизора), строка готовности только с loopback, поток событий раньше всех запросов, `GET /api/info` с проверкой версии и PID, сессия `POST /api/session` со своим `ses_<hex>`, заголовком и правилами режима (возобновление: `GET`, `PATCH`, `POST .../model`), ожидание MCP (`failed` или срок — диагностика `mcp_unavailable`) и агентов. У непроверенной версии `GET /openapi.json` сверяется с манифестами проверенных версий, расхождение со всеми — диагностика `openapi_changed`. Мягкое закрытие: EOF stdin, `stop_grace`, SIGTERM, SIGKILL; принудительное сразу убивает группу. Разрыв потока, потерянный или неразобранный кадр и запуск после падения идут одним путём: подписка, затем чтение проекций. Сообщение истории, которое нельзя прочитать, обрывает хвост с диагностикой `history_unreadable`, а не сессию. Снимается сервер только если подписка и сверка не удались четыре раза подряд: исполнение получает `ProcessExited` вместо вечного ожидания. При возобновлении правила режима ставятся и старым потомкам, иначе субагент продолжил бы потомка по прежним правилам. Половина эмодзи от сервера (`\ud83d`) становится U+FFFD.

Ввод: `POST .../prompt` с `msg_<command hex>` и всегда `delivery: "queue"`, значение по умолчанию `steer` влило бы его в идущий ход. Ответ 200 с тем же `id` — доказательство `opencode_inbox_admitted`, 400, 404 и 409 — отказ с именем ошибки, остальное — `Undetermined`. Повторной отправки нет: после `Undetermined` адаптер читает `.../inbox` и `.../message/{id}`, а поздний факт из потока или проекции становится `InputAccepted`; повторная попытка команды сперва сверяется с историей. Вложения идут путём в тексте; картинка вдобавок идёт в `files` с `file://`, если модель её принимает (`capabilities.input` в `GET /api/model`) и файл не больше 20 МиБ: двоичный файл там молча исчезает, а картинка у модели без такого ввода становится текстом ошибки. Ответ на ввод возвращает вложения в base64 и читается с тем же потолком 64 МиБ, что другие ответы: сверх него адаптер считает исход неизвестным и сверяется с проекциями. Поэтому `images` харнесса всегда `true`, а точное значение и окно контекста идут в каталоге на модель: `ModelInfo.images`, `ModelInfo.context_window`. Картинка, на которую посмотрел агент, лежит `data:` URI в `session.tool.success.content`: такой файл `image/*` становится `MediaSource::Base64` блока вызова, размер виден до декодирования, а декодирует подготовка картинки, не цикл супервизора. Текст крупнее порога финала блока (64 КиБ) идёт ещё и дельтой: супервизор режет её по границам букв, иначе хаб собрал бы пустой блок. Каталог моделей воркер читает при старте коротким запуском сервера в тех же каталогах данных: в него попадают `opencode-go` и явно включённые провайдеры, выключенные и устаревшие модели отброшены, идентификатор `провайдер/модель`, выбор по умолчанию из `GET /api/model/default` первым, у модели без вариантов единственное усилие `default`, которое серверу не передаётся. Пустой каталог не скрывает харнесс, а отказ сервера скрывает. Смена модели и усилия идёт `POST .../model` перед вводом; вариант сверяется с `/api/model` заранее, потому что сервер принимает неизвестный с 204 и падает только на ходе. Настройки вступают в силу вместе с принятым вводом: при отказе правила режима возвращаются на сервер сразу, а модель и усилие следующим вводом. Поток `/api/event` разбирается отдельной задачей с потолком кадра 64 МиБ: куски могут резать кириллическую букву. Блоки текста и рассуждений получают стабильный UUIDv5 от сессии, сообщения, вида и номера, чужие сессии отбрасываются, неизвестный тип даёт одну диагностику, неизвестный `session.execution.*` останавливает исполнение. Инструменты: начало блока ждёт `session.tool.called`, имя берётся из `session.tool.input.started`, ключ вызова — пара сообщения и `id`, поэтому параллельные вызовы могут завершаться в любом порядке. Вне `bypass` блок удерживается до запроса разрешения (без пометки), начала работы или конца вызова без запроса (`approved_by: "cli_policy"`), удержание общее с Codex (`adapter/held_tool.rs`). Статус выхода `shell` виден в сводке (`exit 3`), отказ — `declined`, прерывание — `interrupted`. Режимы задаются правилами сессии: `bypass` разрешает всё, `ask` спрашивает обо всём, кроме вопросов, списка задач и читающих инструментов canterlot (`canterlot_limits`, `canterlot_presets_list`, `sessions_list`, `session_inspect`, `session_subscribe`, `session_unsubscribe`, `session_wait`), `read_only` запрещает всё, кроме чтения, поиска, вопросов, субагентов, списка задач и тех же читающих инструментов canterlot, `owner` оставляет правила конфигурации владельца. Смена режима идёт `PATCH` перед вводом, на корневую сессию и на каждого живого потомка: копию правил он получает при создании и смены родителя не видит; `owner` шлёт пустой список, потому что `null` сервер игнорирует. Выход из `read_only` (в том числе при возобновлении, по правилам, оставшимся в сессии) добавляет к первому вводу напоминание в `<system-reminder>`: сервер возвращает Code Mode пользовательским `<system-update>`, и модель перестаёт звать `shell` и `question` напрямую. Напоминание уходит только на сервер, лента, журнал и хаб хранят ввод как набран; при отказе или неизвестном исходе ввода оно ждёт следующего. Не применившиеся правила останавливают ввод и ставятся заново перед следующим. Запрос разрешения доходит карточкой `RequestOpened`, и ответ идёт на путь его сессии: `once` при согласии и `reject` с текстом при отказе, а `always` не отправляется, он записал бы правило на весь проект. Отказ без текста оборвал бы ход, поэтому текст есть всегда, в том числе у отказа без участия владельца (карточка больше журнала, запрос вне хода). Отказ снимает всю пачку запросов сессии, соседние карточки закрываются по `permission.replied` с причиной `cli_cancelled`, запрос прерванного инструмента — по концу инструмента. Доказательство решения — ответ сервера `opencode_reply_accepted`; 404 и 409 дают `request_not_pending`, обрыв — `Undetermined`, повторной отправки нет: запрос живёт только в памяти сервера, отметка об ответе ставится до запроса. Вопрос — форма инструмента `question`: `key` становится `id`, `custom` — `allow_custom`, `multiselect` — `multi_select`, ответ уходит по ключам формы значениями вариантов. Полноту проверяет адаптер: сервер принял бы неполный ответ и подставил модели `Unanswered`. Форма больше чем из четырёх вопросов, с полями, которых карточка не соберёт, или не от `question` (`sessionID: "global"` у форм MCP) отменяется `DELETE` с сообщением и диагностикой `opencode_form_refused`, иначе вызов ждал бы вечно. Прерывание — `POST .../interrupt`: `interrupted: true` даёт `Acknowledged`, `false` — `NotApplicable`, обрыв — `Undetermined`. При обрыве супервизор закрывает карточки, и всё, что сервер мог не снять, получает отказ с текстом, иначе вызов ждал бы вечно; при `NotApplicable` ход и карточки остаются как были, и запросы на сервере тоже остаются отвечаемыми. Конец периода корня отказывает всем запросам, которые ещё ждут (фонового потомка, формы): супервизор закрывает их карточки с концом хода. Прерывание в паузе перед `continue` после замка общей базы снимает отложенное продолжение и закрывает ход как прерванный (`Acknowledged`). Фоновые команды прерывание не снимает, а `DELETE /api/shell/{id}` разбудил бы модель, поэтому они продолжают работать, а после конца хода `GET /api/shell` показывает работающие команды сессии блоком-предупреждением. Завершение фоновой команды или субагента запускает период без ввода: адаптер шлёт `RunAdopted`, для супервизора это ход последней команды, поэтому карточки доходят до владельца, прерывание работает, а новый ввод ждёт конца; `RunFinished` с `adopted` добавляет расход и контекст к той же команде. Если ввод всё же обогнал конец такого периода, сервер сливает их, расход идёт новому вводу, а граница берётся из `session.inbox.delivered`. Конец хода — `session.execution.{succeeded,failed,interrupted}`, расход суммируется по шагам (`output` плюс `reasoning`, `input` уже без кэша), контекст — последний шаг, окно — `limit.context` из `GET /api/model`, из ответа которого берётся только оно: там же лежит `settings.apiKey`.

MCP canterlot подключается на исполнение через `OPENCODE_CONFIG_CONTENT`: `codemode: false` обязателен, иначе инструменты доступны только изнутри `execute`. Имена у модели идут с именем сервера: `canterlot_canterlot_limits`, `canterlot_share_file`, `canterlot_canterlot_presets_list`, `canterlot_canterlot_preset_save`, `canterlot_canterlot_preset_apply` и `canterlot_<имя>` для десяти межсессионных инструментов. Инструкции сервера и текст бюджета свои, `OPENCODE_SERVER_INSTRUCTIONS`, без упоминания других CLI. Пресеты и межсессионные инструменты идут через хаб как `AgentCall` и возвращаются результатом инструмента. `canterlot_limits` идёт в хаб (`limits.report`) так же, как у других адаптеров: ответ несёт все известные хабу провайдеры, включая OpenCode Go с месячным окном из CodexBar. Строку «no limit data yet in this session» адаптер подставляет, только если хаб старый и инструмента не знает. Старт ждёт `connected` в `GET /api/mcp` и ещё 250 мс: инструмент появляется после дебаунса 100 мс, а публичного сигнала нет, событие `mcp.tools.changed` в поток не идёт; L2 проверяет все четыре инструмента в первом запросе к провайдеру на 20 холодных стартах. `failed` даёт необязательную диагностику `mcp_unavailable`.

Сверка по проекциям (`reconcile.rs`). Replay у сервера нет: `/api/event` не умеет `Last-Event-ID`, `/log` на CLI пуст, поэтому один путь обслуживает разрыв потока, потерянный слишком большой кадр и запуск после падения. Подписка идёт раньше чтения: событие либо придёт живым, либо уже видно в проекции. Читаются `/api/session/active`, `.../inbox`, список потомков `GET /api/session?parentID=`, потому что потомок мог родиться в разрыве, `.../permission` и `.../form` своей сессии и каждого потомка, затем хвост `.../message` от новых к старым до второго `idle`; страница больше потолка ответа читается мельче. Сообщения проходят теми же обработчиками, что живые события, с теми же идентификаторами блоков (`ordinal` части — её номер среди частей того же вида), а закрытые блоки и посчитанные шаги пропускаются, поэтому поздний живой кадр ничего не задваивает. Пока идёт сверка, новый поток ждёт, чтобы конец хода не обогнал потерянное. Дельты открытого в разрыве блока отбрасываются: остаток текста приходит одной дельтой перед финалом, и хаб сходится с контрольной суммой. Запросы из проекции открывают карточку тем же путём, открытая карточка, которой на сервере уже нет, закрывается с `cli_cancelled`. Сервер не работает, а ввод уже стал сообщением: ход закрывается итогом последнего `idle`, а терминал того же периода, если он ещё шёл по новому потоку, отбрасывается до следующего `session.execution.started`. Ввод в очереди или ещё не дошедший до снимка не закрывается. Подписка заново идёт с паузами 0, 200 мс, 1 с и 3 с; ввод в это время не ждёт, потому что сервер жив. Если подписаться не вышло, остаётся прежний путь: `event_stream_lost`, SIGTERM, SIGKILL и `ProcessExited`.

Перезапуск воркера адаптера не касается: сопровождение живёт дальше, журнал докатывается. Смерть супервизора закрывает stdin, сервер уходит сам и успевает дописать проекцию: текст остаётся, инструмент становится `error` с `aborted`. SIGKILL сервера оставляет текст пустым, инструмент в `running`, а его `shell` живыми. Новое исполнение с той же сессией читает те же проекции: блоки приходят с прежними идентификаторами, и хаб отбрасывает уже известные, а новые принимает без привязки к вводу, потому что команда принадлежала старому исполнению; результат садится под вызов прежнего исполнения, поэтому родитель блока проверяется в пределах разговора. Инструмент в `running` без работы сервера закрывается как `interrupted`, настоящий `session.tool.failed` следующего ввода уже ничего не меняет. Ввод, оставшийся в `.../inbox`, снимается `DELETE` с блоком-предупреждением: хаб считает его неопределённым, а следующий ввод исполнил бы его вместе с собой. Расход прерванного хода никому не приписывается. Сироты: пока жив супервизор, `shell` убитого сервера остаётся в его дереве через subreaper и снимается обычным путём; на случай смерти обоих после каждого `shell.created` снимок `(pid, время старта)` из `GET /api/shell` пишется в `<data_root>/shells/<сессия>.json`, а новый запуск снимает эти группы раньше старта сервера, сверяя время старта.

Инструкции. «Как у владельца» запускает сервер с настоящим `XDG_CONFIG_HOME` без `OPENCODE_CONFIG_DIR`. «Без инструкций» и пресет получают `OPENCODE_CONFIG_DIR=<каталог исполнения>/opencode-config` и `OPENCODE_DISABLE_CLAUDE_CODE=1`: в каталоге ссылки на всё содержимое каталога владельца, кроме его `AGENTS.md`, поэтому читаются и `opencode.json`, и `opencode.jsonc`, и плагины; `OPENCODE_CONFIG` не подходит, он принимает один файл. Текст пресета лежит в `AGENTS.md` этого каталога с правами `0600`, подменяется целиком. Смена между «Без инструкций» и пресетами не перезапускает сервер: он следит за файлом, а модель получает `<system-update>` на следующем шаге; после записи адаптер ждёт 400 мс, потому что читает файл наблюдатель с дебаунсом 100 мс и публичного сигнала нет. Переход на «Как у владельца» и обратно меняет окружение запуска, поэтому перезапускает сервер с той же сессией (`CliRestarted`), фоновые команды сессии при этом останавливаются; неудачный запуск возвращает прежнюю конфигурацию и отклоняет ввод с `instructions_change_failed`. Отклонённый ввод возвращает прежний текст перед следующим вводом. Разрыв относительно `pilot.md` §4 принят: `~/AGENTS.md` и `AGENTS.md` выше корня репозитория читаются, если рабочий каталог лежит под домом.

Субагент это дочерняя сессия. Её блоки идут в дорожку вызова `subagent` с именем агента из `session.created` и `session.step.started`, расход считается под этим именем, контекст разговора и фазу задаёт только основной агент. Связь с вызовом приходит в `session.tool.progress` раньше первого ввода потомка, после разрыва её даёт `metadata` результата вызова; блоки потомка без связи всё равно показываются. Фоновый потомок работает и между ходами родителя: его блоки приписаны последней команде. Блоки потомка, целиком выпавшие в разрыв потока, не восстанавливаются, проекция читается только у корневой сессии. Список задач включён всегда (`experimental.todo`) и приходит из `metadata.todos` результата `todowrite`, со статусом `cancelled`.

Отказы. `provider.quota` и `provider.free-limit`, а с 2.2.5 ещё `provider.go-limit`, `provider.chatgpt-limit` и `provider.budget-limit` (2.2.5 отдаёт отказ подписки Go не как `provider.quota`, а своим типом) дают `LimitReached` внутри хода со сбросом из `retryAfterMs`: окна в отказе нет, ожидание длиннее пяти часов считается недельным; `provider.model-budget-limit` (потолок трат одной модели) лимитом харнесса не считается и остаётся ошибкой хода; окна вне хода, в том числе месячное, приходят из CodexBar (раздел о лимитах ниже). `provider.auth` останавливает исполнение с причиной `auth_required`. Переполнение OpenCode чинит сам, поэтому дошедшее до конца хода значит, что чинить нечем: `ContextExhausted`; тип ошибки его не отличает, признак берётся из шаблонов версии 2.1.4. Запрос к модели при `session.retry.scheduled` повторяет сервер, адаптер ввод заново не шлёт, в строке активности видна попытка. Один и тот же `provider.invalid-request` дважды подряд значит застрявшую сессию: причина такого отказа не установлена, поэтому это не `ContextExhausted`. Запись `SessionStuck` (возможность `compact_v1`) ставит очередь на паузу `session_stuck`, карточка предлагает `POST /api/v1/conversations/{id}/compact`: команда `compact_session` доходит до `POST .../compact` с идентификатором из команды. Сжатие тратит токены, поэтому оно только по действию владельца, во время хода не начинается, удача снимает паузу. Та же кнопка «Сжать контекст» живёт в индикаторе контекста у поля ввода (в два нажатия) и доступна между ходами живого исполнения без паузы: Claude Code сжимает вводом `/compact`, OpenCode — `POST .../compact` своего сервера, Codex — методом `thread/compact/start` своего app-server. Каждое сжатие — тихая строка ленты (`compaction_started`/`compaction_finished`, переживает перезагрузку), живой расход в ходу идёт записью `ContextProgress`. Вид каждого отказа и шаг отказа запуска видны в листе диагностики, без текста разговора.

Сопровождение добавляет свой MCP-сервер для разрешений, вопросов, чтения лимитов и работы с пресетами: `canterlot_presets_list`, `canterlot_preset_save` и `canterlot_preset_apply` вызывают хаб унарным `WorkerData.AgentCall` и действуют только на свою сессию (у Codex и OpenCode тот же набор без `approve`: лимиты, `share_file`, пресеты и межсессионные инструменты). «Прервать» отправляет CLI управляющий запрос `interrupt`: ход закрывается как прерванный, процесс и контекст остаются, следующий ввод идёт в тот же процесс, а очередь стоит на паузе `user_stop` до продолжения. SIGINT остаётся запасным путём, если квитанции нет в срок: тогда процесс выходит, исполнение получает `stopped(user_stop)`, а продолжение запускает новое исполнение с `--resume` и тем же нативным ID. Отсутствие авторизации даёт `auth_required`, несовпадение ID или несовместимая версия дают `cli_incompatible`, недоступность canterlot MCP даёт `start_failed`.

Фоновая работа Claude Code. Адаптер читает `system/background_tasks_changed`, `task_started` и `task_notification` и шлёт полный список работающих задач, ключ — `task_id`: завершившийся субагент может запуститься снова. Хаб хранит задачи таблицей, число работающих идёт в доказательство `idle`. Ход, который CLI начал сам по завершении задачи, адаптер приписывает последней команде (`RunAdopted`, execution.md §2). Смена инструкций, для которой нужен перезапуск CLI, ждёт конца фоновой работы: сообщение уходит сразу со старыми инструкциями, в ленте появляется предупреждение, а перезапуск происходит между ходами, когда список задач пуст две секунды, иначе он оборвал бы начинающийся пробуждающий ход. Модель и режим разрешений из той же смены этого не ждут: они применяются перед сообщением, а режим, который CLI без перезапуска принять не может, отклоняет сообщение и показывается в настройках как не применённый. Явная остановка владельца работает сразу.

Воркер запускает Claude Code с `CLAUDE_CODE_ENABLE_TODO_TOOLS=true` и `CLAUDE_CODE_ENABLE_TASKS=false`: без первого CLI 2.1.311 прячет список задач от моделей новее `claude-*-4-*`, второй оставляет `TodoWrite` с полным списком (pilot.md §12.2).

Лимиты Claude Code. Адаптер переводит `rate_limit_event` в показания окон (`utilization` × 1000 в промилле, `resetsAt` из секунд в миллисекунды). Настоящий поток присылает только одно окно: то, что CLI считает определяющим (чаще недельное), поэтому пятичасовое окно из потока приходит редко. Окно со `status: "rejected"` или ход, упавший с 429 либо `usage_limit_reached`, дают упор в лимит: окно из `rateLimitType` (иначе самое загруженное), время сброса из `rate_limit_info` кадра ошибки, иначе из последнего события; повтор того же упора в одном ходе второго факта не даёт. 429, который CLI повторяет сам (`system/api_retry`), упором не считается.

Лимиты без живой сессии воркер берёт у CodexBar: `codexbar usage --provider claude|codex|opencodego --format json --no-color` (для OpenCode запуск идёт с `opencodego`, показания хранятся как провайдер `opencode`). Запрос к модели не делается, учётные данные читает сам CodexBar, воркер файлов с ключами не открывает. Исполняемый файл ищется в `[machine].codexbar_path`, затем в `PATH` и в `~/.local/bin`; интервал опроса `[machine].limits_poll_interval` (по умолчанию 15 минут, это же нижняя граница: CodexBar ходит в ограниченную по частоте точку usage), первый опрос через минуту после запуска. У каждого провайдера своя пауза: сбой одного не задерживает остальных. После временного сбоя (таймаут, ошибка запуска или чтения вывода) повтор через минуту, затем через две, дальше обычный интервал; после постоянного сбоя или пустого чтения пауза удваивается от интервала и доходит до часа; первый удачный опрос её снимает. Запуск ограничен 45 секундами и 1 МиБ вывода, идёт с пониженным приоритетом процессора (`nice +10`), повторный запуск раньше 10 секунд не идёт. Окна определяются по `usage.*.windowMinutes` (300 это пятичасовое, 10080 недельное, 43200 месячное у OpenCode Go), а не по именам `primary` и `secondary`: у Claude без пятичасового окна `primary` повторяет недельное. Окна без `windowMinutes` и дополнительные окна (`extraRateWindows`, например по модели) пропускаются, `usedPercent` × 10 даёт промилле, `resetsAt` читается как ISO 8601, время показания равно `usage.updatedAt`, но не позже часов воркера. `usage.dataConfidence` (`exact` или `estimated`) едет с показанием до хаба и PWA; при `estimated` рядом с числами стоит слово «оценка», остальные значения и старые воркеры считаются точными. Полное успешное чтение, где есть другие окна провайдера, но нет строки на 300 минут, воркер отправляет хабу как отсутствие пятичасового окна (`LimitsReport.absent`): так у плана без пятичасового лимита (например, Claude Ultra с 30 октября 2026) счётчик 5ч не показывается нигде. Хаб хранит отметку `provider_limits.five_hour_absent_at`, не трогает историю снимков, не ставит из-за этого окна паузы и подтверждает сброс пятичасового удержания «кранча» отчётом об отсутствии; более позднее показание окна снимает отметку само. Неполное или неудавшееся чтение окно не скрывает: строка на 300 минут без значения, пустой вывод и сбой запуска ничего не отмечают. Оставшиеся значения окна без отметки, у которых сброс прошёл или показание старше порога, остаются «устарело». Если CodexBar нет, он завершился с ошибкой или вывод непонятен, для Codex используется чтение `account/rateLimits/read` через `app-server`, в том числе на время паузы после сбоев, для Claude остаются показания живых сессий; причина пишется в журнал предупреждением `codexbar_poll_failed` один раз, восстановление отмечает `codexbar_poll_recovered`. Проверка пробуждения «кранча» (`PollLimits`) соблюдает тот же интервал и ту же паузу. Интервал и паузу пропускает только кнопка обновления в PWA (`POST /api/v1/limits/refresh`, `PollLimits.owner_refresh`), у неё свой предел: хаб 15 секунд на провайдера, воркер 10 секунд между запусками. `allow_paid_model_poll = true` (платный запрос к модели ради лимитов) в пилоте не поддерживается: воркер не запускается с этой настройкой.

Таблица `[execution]` необязательна и так же строгая. `allowed_workdir_roots` — каталоги,
внутри которых допустим рабочий каталог исполнения (сравнение по каноническому пути);
пустой список отклоняет каждый `start_execution` с причиной `workdir_not_allowed`. Значение `["/"]`
разрешает любой абсолютный путь; пути с `..` и относительные отклоняются в любом случае.
`supervisor_exe` — бинарник процесса сопровождения (по умолчанию текущий исполняемый файл),
`spawn_timeout` — срок, за который запущенное сопровождение должно принять `Attach`.
`build_jobs` — предел параллельной сборки для запускаемых сессий (по умолчанию 6); уже заданный
в окружении воркера `CARGO_BUILD_JOBS` не перекрывается.
`delegate_mcp_servers` — имена серверов MCP владельца, которые делегированная сессия (D24) получает
рядом с canterlot; по умолчанию список пуст, и делегат видит один canterlot. Имя непустое, из
`[A-Za-z0-9_-]`, не `canterlot`, иначе воркер не стартует с ошибкой конфигурации. Ключ задаёт только
владелец в `worker.toml`: ни хаб, ни аргументы инструментов агента его не меняют. Сессии владельца
список не трогает. Каждый харнесс берёт сервер из своей конфигурации владельца:

- Claude Code — запись верхнего `mcpServers.<имя>` пользовательского `~/.claude.json`
  (`$CLAUDE_CONFIG_DIR/.claude.json`, если переменная задана абсолютным путём). Больше из файла
  ничего не читается; серверы проектов и плагинов в делегата не попадают.
- Codex — таблица `[mcp_servers.<имя>]` из `config.toml` владельца вместе с вложенными таблицами
  (`http_headers` и прочими).
- OpenCode — `mcp.servers.<имя>` (вид 2.x) или `mcp.<имя>` (вид 1.x) из `opencode.json` и
  `opencode.jsonc` владельца.
- Antigravity — ничего: делегат получает только canterlot.

Сервер, которого нет в конфигурации харнесса, для него пропускается: запуск идёт как обычно, а
в журнал исполнения уходит одна необязательная диагностика `delegate_mcp_missing` с именем
сервера, без значений. Записи разрешённых серверов несут секреты владельца (заголовок
`Authorization`), поэтому файлы с ними — `mcp.json` исполнения Claude Code, `config.toml`
изолированного дома Codex и копии конфигурации OpenCode — создаются с правами `0600` в каталогах
`0700` и не попадают ни в диагностику, ни в журнал, ни в события.

Пример: делегатам нужна документация библиотек из Context7, у владельца он настроен во всех трёх
харнессах под именем `context7`.

```toml
[execution]
delegate_mcp_servers = ["context7"]
```

Сюда стоит вносить только серверы, которые лишь читают данные (документация, поиск). Сервер,
который что-то меняет или управляет железом, в список не вносится никогда: делегат работает и в
`bypass`, без подтверждения владельца. В частности, `nanokvm` сюда не добавляется.
`[execution.supervisor]` задаёт таймеры сопровождения. `cli_version_probe` — первый срок пробы
`<cli> --version`: успешная проба запоминается по неизменённому бинарнику (путь, размер, mtime и
inode) в общем файле `<data_dir>/.cli-versions.json`, а таймаут повторяется с удвоенным сроком,
всего три попытки; ошибка CLI или неразборчивый вывод отказ не смягчают. Каталоги исполнений лежат в
`data_dir/executions/<execution_id>` с правами `0700`; секрет IPC и `spec.toml` — `0600`.
Второй экземпляр службы на том же `data_dir` завершается с ошибкой блокировки журнала.

Хабу нужны PEM-сертификат и закрытый ключ в `tls_cert`/`tls_key`.
SAN сертификата должен совпадать с хостом в `hub_url` (в примере `hub.example`).
В `ca_cert` воркера укажите CA, подписавший сертификат хаба; проверка TLS обязательна.
Если воркер подключается с другой машины, задайте хабу доступный `grpc_listen`, например `0.0.0.0:7443`.

Запустите хаб и воркер в отдельных терминалах:

```bash
canterlot-hub serve --config ~/.config/canterlot/hub.toml
canterlot-worker run --config ~/.config/canterlot/worker.toml
```

При запуске из исходников используйте `cargo run -p canterlot-hub -- serve --config ...`
и `cargo run -p canterlot-worker -- run --config ...` соответственно.
`serve` сначала проверяет файл манифеста и отсутствие незавершённого восстановления,
применяет миграции под advisory lock sqlx, пишет версию схемы в диагностику,
сверяет манифест с БД и запускает TLS gRPC-сервер до SIGINT/SIGTERM.
Отсутствующий или несовпадающий манифест и незавершённое восстановление запрещают запуск:
команда возвращает ненулевой код и пишет код ошибки, например `manifest_missing`.
Утерянный манифест не создаётся автоматически из восстановленной БД.
`canterlot-worker supervise` — служебная команда: запускается самим воркером для каждого исполнения и вручную не вызывается.
`canterlot-worker synthetic-cli` — скрытый тестовый помощник, доступен только с feature `synthetic-adapter`.
`canterlot-worker lease run --kind gate|build [--label TEXT] -- CMD ARGS...` ждёт слот в очереди тяжёлых задач работающего воркера этой машины и запускает команду с ограничениями ресурсов; `canterlot-worker lease status [--json]` печатает держателей и очередь. Поведение и ограничения описаны в `docs/development.md`, раздел «Очередь тяжёлых задач».

Отзыв и ротация:

```bash
canterlot-hub machine revoke --config ~/.config/canterlot/hub.toml --machine-id <uuid>
canterlot-hub machine rotate-token --config ~/.config/canterlot/hub.toml --machine-id <uuid>
```

`revoke` закрывает оба потока машины с `Unauthenticated`, запрещает новые команды и записи
журналов; неизвестный UUID даёт ненулевой код и `machine_not_found`.
`rotate-token` выводит только `token=<new>` и также закрывает старый сеанс.
Сохраните новый токен в прежний `token_file` с правами `0600` и перезапустите воркер,
сохранив `machine_id`, `data_dir` и остальные UUID. Курсоры и команды сохраняются.
Старый токен больше не действует. Для отозванной машины ротация возвращает
`machine_revoked`; явное включение требует `rotate-token --reactivate`.

Хаб закрепляет `cj_journal_id` при первом принятом control handshake.
Смена журнала без перепривязки даёт терминальный `local_state_reset` и диагностическое событие.
Если локальное состояние намеренно удалено, выполните `machine rotate-token --machine-id <uuid>
--reset-local-state --config ...` и настройте воркер с новым токеном.
Этот флаг очищает привязку CJ; без него ротация сохраняет её. Сверка оставшихся
нетерминальных исполнений относится к следующему этапу; сброс не подтверждает их завершение.
`machine add` создаёт новую идентичность без привязки CJ.
