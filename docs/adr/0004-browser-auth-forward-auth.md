# ADR-0004: вход браузера через заголовок прокси (forward-auth)

Дата: 2026-10-27. Статус: принято для этапа 1.3a.

## Контекст

ТЗ §15 описывает локальный вход владельца: пароль, сессия, cookie. Решение
владельца от 2026-10-26 ([pilot.md](../design/pilot.md) §1.1 и §2) заменяет его
входом через Caddy и Authelia (`forward_auth`): единственный владелец, одна точка
входа, собственный экран входа появится позже, и тогда Authelia снимается.

Хаб слушает обычный HTTP во внутренней сети. Прокси после `forward_auth`
копирует в запрос заголовки Authelia (`Remote-User` и другие) и передаёт запрос
хабу. Для хаба это единственный признак личности, поэтому ошибка здесь открывает
чужому весь API: подделанный заголовок, запрос мимо прокси, запрос с чужого сайта
в браузере владельца.

## Решение

### Личность

Единственный источник личности: заголовок `[http].user_header` (по умолчанию
`Remote-User`). Он принимается, только если одновременно верно всё:

1. Запрос пришёл по соединению, адрес собеседника которого входит в
   `[http].trusted_proxies`. Адрес берётся из сокета (`ConnectInfo`), а не из
   заголовков; `::ffff:a.b.c.d` сравнивается и как есть, и как `a.b.c.d`, чтобы
   двойной стек не обходил список. Если адреса собеседника нет (роутер собран без
   `ConnectInfo`), запрос отклоняется.
2. Если задан `[http].proxy_secret_file`, запрос несёт ровно один заголовок
   `X-Canterlot-Proxy`, равный секрету. Сравниваются SHA-256 значений в
   постоянное время, поэтому ни длина, ни содержимое не влияют на время ответа.
3. Заголовок личности присутствует ровно один раз, не пуст и равен
   `[http].owner_login`. Заголовок с таким именем не должен принадлежать
   служебному набору (`Host`, `Origin`, `Authorization`, `Cookie`,
   `X-Forwarded-*`, `X-Canterlot-*` и другие), это проверяет конфигурация.

`X-Forwarded-*`, `Forwarded`, `X-Real-IP` и подобные не читаются никогда. Личность
владельца в хабе (`owner_id`) всегда берётся из записи установки, а не из запроса.

Недоверенный адрес, неверный или отсутствующий секрет, отсутствующий, пустой и
повторённый заголовок личности дают один и тот же ответ `401 unauthenticated`:
по ответу нельзя отличить подделку недоверенным адресом от отсутствия заголовка и
подобрать секрет. Только доверенный прокси с верным секретом и другим логином
получает `403 forbidden_user`. Причина отказа пишется в журнал как фиксированная
метка (`untrusted_peer`, `proxy_secret`, `user_header_count`, `other_user`) без
значений заголовков.

Барьер личности стоит в слое роутера и действует по умолчанию: личность нужна на
любом пути, кроме точных `GET`/`HEAD /healthz` и `/readyz`, даже если обработчик
не просит экстрактор `Owner`. Экстрактор `Owner` берёт результат барьера и при
его отсутствии проверяет запрос сам. Все проверки в `http/auth.rs`.

Cookie, токенов и сессий в хабе нет.

### Секрет прокси

Одного адреса прокси недостаточно, когда у веб-хоста один адрес на все контейнеры
(NAT): тогда любой контейнер хоста выглядит как доверенный прокси и мог бы
прислать `Remote-User: owner`. Необязательный секрет `X-Canterlot-Proxy` закрывает
этот случай: его знают только Caddy (директива `header_up` после `forward_auth`) и
хаб. Секрет хранится в файле (`proxy_secret_file`, не короче 32 байт,
видимые ASCII), значение не попадает в журнал и ответы. Caddy обязан сначала
убрать из запроса клиента `Remote-*` и `X-Canterlot-Proxy`, затем выполнить
`forward_auth`; конфигурация и проверка в README и `scripts/check-proxy.sh`.

### CSRF

Cookie у хаба нет, но браузер владельца автоматически прикладывает к запросам
cookie Authelia, а прокси превращает их в заголовок личности; поэтому запрос с
чужого сайта выглядел бы как запрос владельца. Защита из двух условий:

- любой запрос, кроме `GET` и `HEAD`, несёт `Origin`, точно равный записи
  `[http].allowed_origins` (один заголовок, без подстановки и нормализации), и
  заголовок `X-Canterlot-Client: 1`. Чужой сайт не может добавить этот заголовок
  без предварительного запроса CORS, а хаб на предварительный запрос отвечает
  `405` и не отправляет заголовков `Access-Control-*`;
- запрос с `Upgrade` (WSS) несёт разрешённый `Origin`; пользовательский заголовок
  браузерный WebSocket добавить не может, поэтому для него Origin единственная
  защита от межсайтового захвата соединения.

Нарушение даёт `403 origin_rejected` до проверки личности и до обработчика.
`OPTIONS` всегда `405 method_not_allowed`.

### Повторная проверка WSS

Прокси проверяет личность один раз, при установке соединения, а WSS живёт долго.
Поэтому соединение живёт не дольше `[http].ws.max_connection_age` (30 минут по
умолчанию) и закрывается кодом 4401: клиент переподключается, и прокси заново
проверяет сессию Authelia. Закрытая или отозванная сессия перестаёт действовать
не позднее этого срока. Реализация в задаче 7b.

### Транспорт

HTTP хаба обычный, без TLS: TLS завершает Caddy, а хаб слушает во внутренней сети.
Порт хаба не должен быть доступен снаружи сети прокси; доверие по адресу и секрет
рассчитаны на это, а не заменяют его. Канал воркер и хаб остаётся на проверяемом
TLS (ADR-0001).

HTTP обслуживается через hyper-util с `TokioTimer`: `[http].header_read_timeout`
(10 секунд) ограничивает чтение заголовков с момента приёма сокета и ожидание
следующего запроса в keep-alive. `[http].max_connections` (256) ограничивает все
открытые соединения до аутентификации; лишний сокет закрывается сразу.
`[http].body_read_timeout` (30 секунд) — общий срок чтения тела, без продления
на очередной фрагмент. После полного чтения тела обработчик не ограничен этим
сроком. Успешный upgrade освобождается от HTTP-дедлайнов, но сохраняет место в
лимите соединений до закрытия. При shutdown приём прекращается, обычным запросам
даётся 10 секунд, затем оставшиеся сокеты, включая upgraded, закрываются.

### Журнал и ошибки

Строка журнала запроса содержит метод, шаблон маршрута, статус, задержку и
`correlation_id`. Заголовки, query, тела и значения параметров пути не попадают ни
в журнал, ни в сообщения ошибок. Ошибки базы данных описываются через SQLSTATE и
имя ограничения (`dberr::describe`): текст драйвера не читается, потому что
DETAIL содержит значения строк. Чужой идентификатор неотличим от отсутствующего
(`404 not_found`). При запуске `serve` panic hook заменяется без вызова
стандартного hook: событие `kind=panic` содержит только место `file:line` и имя
потока; payload не форматируется и не попадает в stderr.

## Последствия

- Замена Authelia собственным входом меняет только `http/auth.rs` (источник
  личности и способ повторной проверки); CSRF, формат ошибок, идемпотентность и
  контракт API остаются.
- Секрет прокси нужно создать и положить в оба места (файл хаба и секрет Caddy);
  его ротация требует одновременного перезапуска обоих.
- Конфигурация развёртывания проверяется `scripts/check-proxy.sh`: запуск при
  развёртывании и после каждого изменения Caddy.
- Хаб остаётся на одном процессе: нет ограничения частоты запросов, кроме размеров
  и лимитов параллелизма; для единственного владельца за SSO это принято.
