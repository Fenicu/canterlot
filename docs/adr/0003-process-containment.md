# ADR-0003: удержание процессов исполнения

Дата: 2026-10-26. Статус: принято как временное решение для Stage 1.2b.

## Контекст

ТЗ §9.5 требует проверяемую принадлежность всех управляемых процессов и
запрещает запуск нового CLI или resume после потери владельца до подтверждённой
остановки старой группы. Исследование [этапа 0](../stage0/README.md#5-выводы-для-воркера)
показало: инструменты создают собственные группы и сессии и переживают SIGKILL
CLI. Одна группа процессов, PID, имя процесса или рабочий каталог не доказывают
принадлежность и остановку исполнения.

Для эксплуатационного решения нужна cgroup v2 на исполнение. На хосте
разработки и CI воркер находится в системном service cgroup, принадлежащем root,
без делегирования. `/proc/self/cgroup` указывает на системную службу;
`cgroup.procs` соответствующей группы недоступен для записи. Рабочее подключение
к пользовательскому D-Bus отсутствует: `busctl --user` не получает адрес шины.
Наличие файла сокета само по себе не означает доступную пользовательскую сессию.
Реальную cgroup-реализацию здесь нельзя проверить без привилегированной подготовки.

## Решение для 1.2b

Ввести `Containment` с операциями `kind`, `prepare_command`, `members`,
`populated`, `terminate`; адаптер получает интерфейс и не знает реализацию.
Поставить временную реализацию `TreeContainment`. Диагностика содержит
`containment = "tree"`.

Каждому исполнению соответствует отдельный живой процесс сопровождения с
единственным CLI. `TreeContainment::new` сохраняет PID и время старта
сопровождения и устанавливает `PR_SET_CHILD_SUBREAPER` безопасной обёрткой
`rustix`. `prepare_command` назначает CLI собственную группу процессов без
`pre_exec`. После spawn адаптер сразу вызывает `members`, фиксируя идентичность
прямого CLI до передачи ввода. Его статус выхода забирает `tokio::process::Child`.

Члены группы удержания определяются обходом `/proc/*/stat`: PID, поле 22
`starttime` в тиках и цепочка PPID до сопровождения. Проверяется также время
старта каждого предка. Номер POSIX-группы не ограничивает принадлежность:
отделившиеся через setsid и двойное порождение потомки остаются внутри дерева,
а после смерти промежуточных родителей усыновляются subreaper. Синтетический
CLI проверяет этот случай через безопасные spawn/spawn/setsid вместо fork.

Зомби не считаются живыми членами. Усыновлённые зомби забираются адресно через
`waitpid(Some(pid), NOHANG)`; `waitpid(None)` не используется. Прямой CLI
исключён из этого reap, чтобы не отнимать его статус у Tokio. Сопровождение
должно оставаться отдельным процессом исполнения; общий процесс для нескольких
исполнений нарушил бы границу дерева.

`terminate(grace)` посылает SIGTERM только проверенным членам и повторяет обход
в пределах grace. Затем посылает SIGKILL, снова проверяет дерево и повторяет
до пустоты либо до истечения дополнительного интервала grace. Перед каждым
сигналом заново проверяются цепочка принадлежности, PID и start ticks.
Исчезнувший процесс или несовпавшая идентичность не сигнализируется.
При нулевом grace выполняется попытка TERM/KILL без ожидания и возвращается
консервативный `Survivors` для процессов, наблюдавшихся перед KILL. Следующий
вызов проверяет фактическую пустоту. `Survivors` не разрешает терминальное
состояние исполнения. Терминальное состояние допустимо только при
`populated() == false`, с исключениями, явно заданными общими ограничениями.

## Ограничения

`tree` не является релизным выполнением §9.5. Он удерживает потомков только
пока живо сопровождение. После его смерти отделившиеся процессы переподчиняются
другому родителю, и старое дерево больше нельзя достоверно восстановить. Это
ограничение критично для восстановления R3/R4. Перезапуск управляющей службы
при живом сопровождении не разрушает дерево.

Проверка `/proc` и отправка сигнала являются разными системными операциями.
Проверка PID + start ticks отсекает устаревшую идентичность, но без pidfd не
даёт атомарности при гонке между проверкой и сигналом. Частично прочитанное
дерево также требует повторной проверки; недоступный `/proc` даёт ошибку,
а не доказательство пустоты. Нельзя объявлять разрешённым resume после смерти
сопровождения по одной сохранённой паре PID/start ticks. Владение каталогом
и неопределённый статус сохраняются до достоверного разрешения ситуации.

## Переход в 1.2c

Добавить `CgroupContainment` за тем же интерфейсом, делегированную
пользовательскую systemd scope/cgroup v2 на исполнение и привилегированно
подготовленный тестовый хост. Сохранять идентичность загрузки ОС и ресурсной
группы вместе с ID/поколением исполнения и идентичностью сопровождения.
Проверять пустоту через `cgroup.events populated`, останавливать все процессы
через `cgroup.kill`, адресные операции защищать pidfd. Покрыть смерть
сопровождения и восстановление R3/R4, включая отделившиеся инструменты и
запрет нового CLI до подтверждения пустоты старой cgroup. Замена реализации
не должна менять контракт адаптера, доменную модель хаба или UI.
